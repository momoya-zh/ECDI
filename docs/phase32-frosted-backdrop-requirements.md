# Phase 32 · 窗口雾面衬底（Frosted Backdrop）—— 需求确认（v1.0）

> 来源：用户 2026-10-09 提出——DesktopNest M1 观感里程碑暴露「框体是纯不透明深色，缺少现代桌面应用的雾面质感」；用户明确**这是框架能力（功能），进 Phase 序列，暂时脱离 DesktopNest**。
> 状态：**v1.0 待评审**（本文档只做需求确认与现状勘察；技术方案留初设）
> 定位：把「**整窗雾面衬底 + 不透明控件**」做成 ECDI 的**框架级能力**——应用声明一次即可获得系统级背景模糊，控件（文字/图标/按钮）保持不透明清晰。

---

## §1 动机

### 1.1 用户需求原话（2026-10-09）

> 「整体的雾面效果，也就是整个程序的底部是雾面的，包括标题栏，**控件是正常的不透明样式**」
> 「整框统一雾面，透明度 0.8f，兼容，半透明白色，要做」
> 「圆角用系统圆角即可，浮层雾面可以接受，我们只需要位置、图标是清晰的即可」

**拆成可判的四条**：

| # | 要求 | 说明 |
|---|---|---|
| **R-a** | **整窗**雾面 | 含标题栏在内，整个窗口底面统一材质（不是局部区域） |
| **R-b** | **控件不透明** | 文字 / 图标 / 按钮照常清晰绘制，不受雾面影响 |
| **R-c** | **降级到半透明白 0.8** | 系统不支持材质时，退化为「半透明白 alpha = 0.8」——**不是裸透**（见 §2 K4） |
| **R-d** | **用系统圆角** | 圆角沿用既有 Phase 12 的 `DWMWCP_ROUND`，本 Phase 不新增自绘圆角 |

### 1.2 触发场景（但不是本 Phase 的范围）

DesktopNest M1 的三个框当前是**纯不透明深色**（实测 `#2B2F38` 铺满），在现代桌面环境里缺少质感。用户明确：**本 Phase 只做框架能力，DesktopNest 的观感应用留到能力交付后**（用户将先出低保真模型作为结构参考）。

### 1.3 为什么值得进 Phase 序列

- **是通用能力**，不是某个应用的特例：任何常驻型 / 工具型窗口（ModelProbe、托盘应用、未来的 DesktopNest）都可用
- **框架侧当前零能力**（§2 K1 实测）
- 与既有 Phase 12（WindowChrome）**同族**：都属「窗口形态 / 系统合成」范畴，且**强依赖** Phase 12 的三件套（§2 K2）

## §2 现状勘察（K1–K8，全部带行号实测 2026-10-09）

> 取证方式：**五个独立探针**（`%TEMP%\dn_acrylic\probe*.cpp`，**零仓库侵入、未改任何框架文件**），按条 105 的「先取证再设计」执行。探针结论见 §2.9。

### K1 ★ 框架侧**零**雾面/合成能力（实测）

全仓扫描（`ECDI/src` + `ECDI/include`）**零命中**：`WS_EX_LAYERED` / `SetLayeredWindowAttributes` / `UpdateLayeredWindow` / `WS_EX_NOREDIRECTIONBITMAP` / `DwmEnableBlurBehindWindow` / `SetWindowCompositionAttribute` / `ACCENT_ENABLE_*` / `DirectComposition` / `DCompositionCreate`。

DWM 只用了**两处**（均在 Phase 12）：`DwmExtendFrameIntoClientArea`（阴影，`Win32PlatformWindow.cpp:1518` 起 `ApplyDwmEnhancements`）与 `DWMWA_WINDOW_CORNER_PREFERENCE`（圆角，`:1540`）。

### K2 ★★ 雾面**依赖** Phase 12 的 Borderless 三件套（**探针 4→5 的教训**）

这是我方探针**先失败后成功**得出的关键事实：雾面**不是**「调一个 API 就完事」的独立特性。

| # | 依赖项 | 框架现状 | 出处 |
|---|---|---|---|
| ① | 保留 `WS_OVERLAPPEDWINDOW`（不切 `WS_POPUP`） | ✅ 已有 | `Win32PlatformWindow.cpp:115-120` |
| ② | `WM_NCCALCSIZE` 拦截（客户区铺满全窗） | ✅ 已有 | `:472-494` |
| ③ | `SWP_FRAMECHANGED`（通知系统重算非客户区） | ✅ 已有 | `:1072-1073` |
| ④ | 系统圆角 `DWMWCP_ROUND` | ✅ 已有 | `:1540` |
| ⑤ | **亚克力材质** | ❌ **缺（本 Phase 要做）** | — |

★ **反证**：探针 4 复刻了 ①④ + 亚克力，**漏了 ③** ⇒ 客户区未铺满、原生标题栏盖住材质，**材质完全看不见**（探针 4 截图四个窗口全是原生 chrome）。补上 ③ 后（探针 5）立即成立。

⇒ **结论：本 Phase 是在既有 Borderless 能力上「加一层」，不是重造窗口形态。** 这大幅降低了风险与改动量。

### K3 ★ 清屏通道**无 alpha 语义**（实测，本 Phase 必须解决）

`GDIBackend::BeginFrame`（`:251-277`）用 `CreateSolidBrush` + `FillRect` 清屏，源码自注（`:269`）：

> 「决策 21/23：`ToColorRef` 内含 `ToByte` Clamp；★ **alpha 被忽略（`COLORREF` 无 alpha 通道）**」

⇒ **即使应用把背景色设成 `alpha = 0`，GDI 也会当成不透明色填满**，材质永远透不出来。这是本 Phase **唯一必须修改的既有渲染路径**。

同处另一事实（`:270`）：画刷每次创建/销毁（无缓存），与 `DrawRect` 同款——改动时需保持这一习惯。

### K4 ★★ 「透明但无模糊」是**最差**结果——降级**必须**是半透明白（探针实测）

探针 3 的受控对照（同位置、同底衬、逐次切换）：

| 模式 | 配置 | 实测 |
|---|---|---|
| m0 | 亚克力 + 背景 `alpha=0` + `AlphaBlend` | ✅ 雾面透出 |
| m1 | 亚克力 + 背景 `alpha=0` + `BitBlt` | ✅ 与 m0 **几乎无差** |
| **m3** | **无亚克力** + 背景 `alpha=0` | ❌ **透明但锐利**——桌面文字/色块直接透过来 |

⇒ **R-c 的技术依据**：降级路径若也用 `alpha=0`，会得到「透明但没模糊」的**视觉事故**（比不透明更难看）。**降级必须是「半透明白 alpha=0.8」**（用户指定值，探针 1 窗口 F 与探针 3 的 m2 均已验证可出白雾面）。

### K5 ★ 提交方式**不影响**材质（推翻我方初判）

**更正我方上一轮的判断**：最初怀疑「GDI 的 `BitBlt(SRCCOPY)` 整块覆盖会盖掉材质」。探针 3 的 m0/m1 对比**否定**了这一点：

- `AlphaBlend` 提交（m0）与 `BitBlt` 提交（m1）**结果几乎一致**
- 真正的开关是**背景像素的 alpha 值**，**不是**提交函数

⇒ **不需要**分层窗口（`UpdateLayeredWindow`）、**不需要** DirectComposition、**不需要**换渲染架构。改动面因此显著缩小。

### K6 系统圆角会**连材质与自绘内容一起裁**（探针 5 实测）

探针 5（完整复刻框架流程）窗口 A（亚克力 + `DWMWCP_ROUND`）：材质与自绘内容**都被系统圆角裁切**，圆角外为桌面，**无方形材质溢出**。

⇒ 两条设计约束：
1. **正面**：系统圆角对雾面天然友好，无需应用侧做圆角遮罩
2. ★ **反面**：应用侧若**自己**画不透明圆角背景（如 DesktopNest 的 `BoxRoot::OnPaint` 画 `DrawRoundedRect` 铺满），会**盖住材质**且与系统圆角**错位** ⇒ 雾面模式下应用侧**必须撤销自绘底**（这是应用侧适配纪律，留详设/应用侧文档）

### K7 GL 路径与本 Phase 的关系（用户已拍板）

用户 2026-10-09：「**GL 短期先不做，先做 GDI，GL 保证正式 V1.0 库的时候能功能和 GDI 一致即可**」。

⇒ **本 Phase 范围 = GDI**；GL 路径的雾面支持**记为独立账**（不在本 Phase 验收内），但**接口形态须为 GL 留位**（不可做成 GDI 专用而无法扩展）。

## §3 范围

### 3.1 做（倾向）

| # | 内容 |
|---|---|
| **S1** | 框架新增「窗口衬底模式」能力：应用可声明启用**雾面亚克力**，并可指定 **tint 色（含 alpha）** |

| **S6** | 接口形态**为 GL 留位**（K7）——本 Phase 只实现 GDI |
| **S7** | 新增能力**带默认实现的 virtual**（K8）——**10 个既有实现者零改动** |

### 3.2 非目标（本轮明确不做）

| # | 非目标 | 理由 |

## §4 关键决策点（D1–D5，待初设解决）

| # | 决策点 | 倾向 / 待定 |
|---|---|---|
| **D1** | **API 语义归属**：① `SetBackgroundColor` 的 `alpha == 0` ⇒ 跳过清屏（**沿用既有 API**）vs ② 新增独立 `SetBackdrop(mode, tint)`（**正交新 API**） | ★ **待初设**——①语义经济但要复用既有 API 的表达力；②显式但两来源可能打架（backdrop 与 background 同时设置时谁赢？） |
| **D2** | **衬底模式枚举的取值域**：仅 `None / Acrylic` 两项，还是含 `Mica` / `Blur` 等 | ★ 待初设——注意探针 1 已证 **Win11 官方材质 API 本机不生效**，取值域不宜照抄系统枚举 |
| **D3** | **降级行为的判定时机与可观测性**：应用能否查询「当前实际生效的是雾面还是降级」 | ★ 待初设——`Show()` 前无法预判系统能力，可能需要「尝试 → 记结果 → 可查」 |
| **D4** | **tint 色的通道序与预乘语义**：`ACCENTPOLICY.nColor` 是 **ABGR**（非 RGBA），且探针用 `alpha` 直接表达「不透明度比重」 | ★ 待初设——必须实测锁定，否则应用传 `Color` 会得到错误颜色 |
| **D5** | **与 `Window::SetBackgroundColor` 的既有契约关系**：Phase 18 定了「窗口底色的单一真相在 `Window`」，雾面 tint 是否复用同一字段 | ★ 待初设——涉及「一个概念一个词」（条 95①） |
