## §1 核心机制

### 1.1 六个几何结论 ← 两个厚度源（逐站点 before / after）

| # | 站点 | 结论 | 现读 | 改为 |
|---|---|---|---|---|
| **S1** | `NeedsVerticalBar()`（`:208` / `:218`） | 竖条是否出现（第二轮要扣**高度**） | `t = BarThickness()`（竖条） | `BarFootprint(HorizontalBarThickness())` |
| **S2** | `NeedsHorizontalBar()`（`:232` / `:239`） | 横条是否出现（第二轮要扣**宽度**） | 竖条 ✔ | `BarFootprint(VerticalBarThickness())`（语义不变，仅换名） |
| **S3** | `ViewportWidth()`（`:248`） | 可用宽 = 宽 − 竖条占位 | 竖条 ✔ | `BarFootprint(VerticalBarThickness())` |
| **S4** | `ViewportHeight()`（`:255`） | 可用高 = 高 − 横条占位 | 竖条 ❌ | `BarFootprint(HorizontalBarThickness())` |
| **S5** | `ApplyLayout()` 竖条（`:272-273`） | 竖条 `SetSize(t_v, H−2s)` / 位置 `W−t_v−s` | 共用 `t` | `t_v = VerticalBarThickness()` |
| **S6** | `ApplyLayout()` 横条（`:279-280`） | 横条 `SetSize(W−2s, t_h)` / 位置 `H−t_h−s` | 共用 `t` ❌ | `t_h = HorizontalBarThickness()` |

★ **S1 与 S4 是「同一根因的两个面」**：S1 决定「要不要扣」，S4 决定「扣多少」——两处都用错轴，才会出现「横条厚度设 4 却按 12 扣高度」。S5/S6 则是「条本身画多厚」，是 R84-A「设置被整体丢弃」的直接来源。**实质改动共四处（S1 / S4 / S5 / S6），S2 / S3 只换名**；四处必须同时改，只改其中一处会让「条尺寸」与「视口扣减」**互相不一致**（比现在更糟）。

★★ **短路陷阱（v1.1 补——本 Phase 最容易骗过测试的一点）**：`NeedsVerticalBar` 的 `return nV1 || (m_contentH > tH)`（`:220`）与 `NeedsHorizontalBar` 的 `return nH1 || (m_contentW > tW)`（`:241`）都用了 `||` **短路**：

- `nV1 = m_contentH > h0`、`nH1 = m_contentW > w0` 只要成立，`tH` / `tW` **根本不参与求值** ⇒ 在「双轴都溢出」的夹具里，**S1 与 S2 改不改都是同一个结果**；
- 因此 **S1 / S2 只能被「单轴溢出且落在临界带」的夹具暴露**：S1 需要 `contentH ∈ (h0 − BarFootprint(t_v), h0 − BarFootprint(t_h)]`，S2 需要 `contentW ∈ (w0 − BarFootprint(t_h), w0 − BarFootprint(t_v)]`（12/4 时分别是 `(86, 94]` 与 `(186, 194]`）；
- ⇒ 测试必须含 **P3（contentH = 90）/ P4（contentW = 190）** 两相，否则「四处同改」的兜底里 **2/4 是空的**（§4 相表已按此重排）。

### 1.2 为什么这不会引出一个「布局环」

Phase 38 的软折行必须解决真环（`可用宽 → 折行结果 → 内容高 → 是否需要竖向滚动条 → 可用宽`）。**本相不同**：

- `ScrollBar::GetThickness()` 读的是 `m_style.thickness`（`ScrollBar.h:61`），**只由主题 / `SetStyle` 写入**，与视口、内容 extent、偏移**全无关**；
- 因此 `t_v` / `t_h` 在 `ApplyLayout → ClampOffset → SyncBars` 的整段里是**常量**，`NeedsVerticalBar` / `NeedsHorizontalBar` 的两轮判定仍然**单调、最多 2 轮收敛**（既有结论，`ScrollView.cpp:206-241` 注释）；
- ⇒ 本 Phase **不引入任何不动点迭代 / 时序约定**，只把「一个常量」换成「两个常量」。

★ **反过来说**：若将来有人让厚度**依赖视口**（例如「条随容器宽度变细」），这条论证立即失效——那是**另一条需求**，须重新论证收敛性。此句应随代码注释留在 `ApplyLayout` 上方。

### 1.3 可见性**绝不**参与厚度读取

`ApplyLayout`（`:270-281`）对两条**无条件** `SetSize` / `SetPosition`，**不判 `IsVisible()`**——不可见条的控件几何仍是自身厚度。因此：

- 两个助手**只读样式**，**不得**出现 `IsVisible()` / `m_barsVisible` 判断（否则可复现「隐藏后尺寸变 0、再显示跳变」类缺陷）；
- 「扣多少」由 `NeedsVerticalBar` / `NeedsHorizontalBar` 决定（`m_barsVisible == false` 时恒 `false`），与厚度读取正交。

### 1.4 交叉区与绘制序（不动）

竖条占满 `H−2s`、横条占满 `W−2s`，二者在右下角**继续重叠**（L2 记账）：重叠矩形 `t_v × t_h`。绘制序由 `AddChild` 序决定（竖条先、横条后，`ScrollView.cpp:35-41`）⇒ 横条盖竖条，与今日同构。**本 Phase 不碰这条路径**（红线 3）。

### 1.5 与 Phase 41 失效管线的接缝

| 面 | 本 Phase 的处置 |
|---|---|
| 重绘失效 | **零新增** `Invalidate()`（改的是「读哪个数」，不是「何时失效」） |
| 布局失效 | **零新增**布局脏源（`m_layoutDirty` 不参与） |
| `Arrange` 期抑制 | 无影响（`ApplyLayout` 仍只在既有 4 个入口被调） |
| **R84-C′**（改厚度不重排 ⇒ C7 可破） | **本期不修**（闸门 2 已裁）：需求稿 §7 L43-2 已记「唯一现成出口 = 同值也重算的 `SetSize`」；本 Phase 只在助手注释里写提醒，**不加**回调、不加隐藏重算 |

### 1.6 可测性裁决：助手保持 `private`

| 方案 | 判定 | 理由 |
|---|---|---|
| **保持 `private`（采纳）** | ✅ | T43-1/2/3 的判据全部可经**公开几何**观测（`GetWidth/GetHeight/GetAbsolutePosition/GetMaxOffset*`），无需直调助手；`ScrollBar::m_style` 那类 `protected` 是**给派生控件**用的（`ScrollBar.h:85` 先例），不是给「读一个数」用的 |
| 降 `protected` 供测试直调 | ❌ | 为测试放宽封装（与 `window-ownership` D9 拒 `friend` 同一条理由），且本缺陷的判据本就**端到端更可信**（几何 = 用户可见后果） |
| 加 `public` 查询接口 | ❌ | 违红线 2（公共 API +0） |

## §2 头文件规范

### 2.1 `ECDI/include/ECDI/Widget/ScrollView.h`（`:173-174` 段落）

```cpp
	/// @brief 竖条厚度（读**竖条自己**的样式；为 `nullptr` 时 0）
	/// @details 两轴厚度**各取各的**——不要用「一个厚度代表两条」（审计 M5 的原始缺陷形态）。
	/// ⚠️ 改厚度（`GetHorizontalScrollBar()->SetStyle` 等）**不会**触发本容器重排；
	///    调用方须在改后调一次 `SetSize(GetWidth(), GetHeight())`（**同值也会重算**，
	///    而 `SetContentExtent` 在 extent 未变时早退，救不了——R84-C′ / 审计 M6）。
	[[nodiscard]] int VerticalBarThickness() const noexcept;

	/// @brief 横条厚度（同上，读**横条自己**的样式）
	[[nodiscard]] int HorizontalBarThickness() const noexcept;
```

**三条注释要求**（缺一不算完成）：① 「读自己那条」；② 空指针退化；③ 改厚度后需 `SetSize`（且写明 `SetContentExtent` 救不了）。

### 2.2 旧名 `BarThickness()` 必须**删掉**，不留 alias

留一个 `BarThickness() { return VerticalBarThickness(); }` 会让下一个调用点在补全提示里**优先命中**旧名——本缺陷的成因正是「名字里没有轴」。删掉后编译器会把所有残留调用点报出来，**用编译器代替 grep 做搬移检查**。

### 2.3 为什么「公共面零增量」成立

- 两个助手是 **private 成员函数**：不进公共 API 清单、不改对象布局（无数据成员）、不改 vtable（非虚）、不改头文件数量（同 `ScrollView.h`）；
- `ScrollBar.h` / `ScrollBarStyle.h` **零改动**（需求稿 1.5 节：`ScrollBar` 本体不碰）；
- 公共头的**内容**变了（声明段），故 README 的「Public 头 **101**」**计数不变**；下游工程若按**头文件哈希**做增量构建会重编一次，**无需改代码**（v1.1 订正：原稿「ABI 指纹会变 ⇒ 需重链接」无依据——两个 private 非虚成员函数既不进类大小、也不进 vtable，仓内亦无任何 ABI 指纹工具）。
