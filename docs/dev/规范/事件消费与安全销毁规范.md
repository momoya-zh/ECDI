## §1 术语与定位

### 1.1 三个**不同层**的「消费」

| 名称 | 所在层 | 手段 | 效果 |
|---|---|---|---|
| **命中消费** | 命中测试（WM_NCHITTEST） | `Widget::SetConsumesMouseInput(bool)` | 控件「吃」鼠标输入，不让它落到窗口 caption 拖拽区 |
| **事件消费**（本文 §2） | 冒泡派发 | `event.SetHandled()` / `event.IsHandled()` | 当前事件**停止向祖先冒泡** |
| **移除请求**（本文 §3） | 控件树 | `Widget::RequestRemove()` | 派发期间只「摘树」，析构延迟到派发结束 |

⚠️ 三者互不代替：`SetConsumesMouseInput` 不阻止冒泡；`SetHandled` 不改变命中；`RequestRemove` 不消费事件。

### 1.2 事件**不**被消费时的既有语义（不变）

`Application` 把一次鼠标/滚轮/拖入事件派发给「命中目标 → 根」的**冻结链**，逐级调用控件回调。默认全部冒泡到位——这条默认语义在 Phase 35 **没有任何改动**。

## §2 事件消费语义（需求稿 F1 / F2）

### 2.1 规则（唯一形状，代码位置：`Application::BubbleAlongChain`，`Application.h:196-217`）

冒泡循环 `for (Widget* node : chain)` 有**三个**终止条件：

| # | 条件 | 判定位置 | 效果 |
|---|---|---|---|
| 1 | 链走完 | 循环自然结束 | 正常结束（默认语义） |
| 2 | `node->IsRemovedDuringDispatch()` | **调用回调之前** | `continue` —— 跳过该节点，**其祖先照常收到事件** |
| 3 | `event.IsHandled()` | **回调返回之后** | `break` —— 停止向祖先冒泡（消费） |

> 条件 2 与条件 3 的顺序是有意的：被摘掉的节点**不再收到**后续事件，但「摘树」不等于「消费」——它的祖先仍要拿到这条事件（与「子控件不消费 ⇒ 冒泡照常」同一规则）。

### 2.2 应用层如何消费

在任意控件的鼠标/滚轮回调里调用 `event.SetHandled()` 即可（`Event.h` 早已提供，Phase 35 起真正接线）。按 phase 分别消费 —— 见 §2.4 的一致性要求。

### 2.3 内建控件的自动消费（★ 维护者问题 1 的答案）

**`Button` 在按下时（`OnMouseButtonDown`）与释放时（`OnMouseButtonUp`）**自动消费** 左键序列的两个阶段 —— 与是否触发 `OnClick` **无关**。**

| 阶段 | 是否消费 | 理由 |
|---|---|---|
| Down | 总是 | 按钮按下即宣告「这次点按归我」，父容器不进入按下态 |
| Up（按钮内松开，触发点击） | 总是 | 点击已在本按钮完成，父不得因同一次点击再次触发（验收 1） |
| Up（拖出后松开，不触发点击） | 总是 | 父从未收到 Down ⇒ 不能收到「孤立的 Up」（验收 2 / F2③） |

**为什么不能「事后反悔」**：若允许在 `OnClick` 里取消消费，父控件就会处于「收到 Up、没收到 Down」的状态——正是需求稿 F2③ 要消灭的状态异常。⇒ 消费必须在 Down 时刻就确定，且与 Up 对称。

**由此产生的「设计红线」**：

> 「父行可点击、子按钮可点击」的复合控件（如会话列表项 + 删除按钮）里，**父行的业务动作不能放在父行自己的点击回调里** —— 点中删除按钮时，Down/Up 都被 Button 消费，父行**必然**收不到。正解二选一：
> 1. **父行不做点击控件**：行只负责绘制与命中，动作由子控件回调发出；
> 2. **父行动作放进子按钮回调**：删除按钮的 `OnClick` 里先 `RequestRemove()`、再执行「切换选中行」等父级语义。
>
> 现有样例 `examples/DesktopNest/MemberListPopup.cpp` 属第 1 类（成员行/拆出行/加入行都是 `Button` 且互不嵌套），**行为零变化**。

其他内建控件的自动消费情况：`TextBox` / `StateWidget`(CheckBox) / `CollapsingPanel` 等**不**自动消费——它们沿用「不消费则照常冒泡」的默认语义（未在需求稿范围内改动，避免扩大回归面）。

### 2.4 按下 / 释放的一致性

**规则：应用层自定义的可点击控件若要让「子先于父响应」，必须**同时**消费 Down 与 Up。** 框架**不强制**——`Event` 的 handled 状态是**每事件一份**、框架不记录「上一次谁消费了什么」；只消费一个阶段是**合法但危险**的：

- 只消费 Up：Down 已冒泡到父控件（父进入按下态、点亮）→ Up 被吞 ⇒ 父永远收不到 Up，`m_pressed` 卡在 true（实测见 `Events.Consume.AppLevelConsumesUpOnly`，断言的就是这条半截状态）；
- 只消费 Down：父在「没收到 Down」的情况下收到 Up；按「Down ∧ Up」判定的父无害，按「Up 即点」判定的父会误触发。

`Button` 因此把两个阶段都定为「总是消费」（§2.3），这也是框架推荐的形状（`Events.Consume.AppLevelConsumesBothPhases`）。

### 2.5 不消费时的行为（需求稿「子控件未处理 ⇒ 父控件是否响应」）

**允许父控件响应**——即「子控件不消费 = 明确交给父控件处理」。这条规则由回归测试固定：

- `Events.Consume.UnconsumedBubblesToAncestors`：子行不消费 ⇒ 父行收到 Down 与 Up；
- `Events.Consume.ParentBlankAreaStillResponds`：点父行空白区 ⇒ 父行照常响应。

### 2.6 **刻意不支持**的微调：「本按钮只消费 Up、Down 放行」

若业务方希望「子按钮吃掉 Up、父行吃掉 Down 以进入按下态」，本题**不提供**该模式。原因：它使父控件停在「按下态未释放」——F2③ 明令排除。需要「父行高亮的按下反馈」时，用**视觉反馈**（`:hover` 外观 / `OnMouseEnter/Leave`）实现，而不用事件消费。

## §3 派发期安全销毁（需求稿 F3）

### 3.1 API

```cpp
bool Widget::RequestRemove();   // ★ 唯一的「派发中删控件」入口
```

| 调用时机 | 行为 | 返回值 |
|---|---|---|
| **不在**派发中（含无窗口、无头控件），且**有父** | 立即脱树**并析构**（`Widget.cpp:251-256`） | `false`（调用后 `this` 已失效） |
| **不在**派发中，但**无父**（已脱树的非根控件） | `DetachFromParentNow()` 空操作 ⇒ **不析构、不入队**（所有权在脱树那一刻已交还给摘树调用方，本控件无法回收它自己） | `false` |
| **在**派发中（含无窗口控件——判据是「所属 Application 正在派发」，不是「本控件在链上」） | 立即脱树（命中/绘制/焦点/捕获/hover 同步清理），**不析构**；对象由 Application 的延迟队列接管（`m_parent->RemoveChild(this)` → `DeferDestroy`） | `true`（调用后对象仍存活） |
| 目标是根控件（`m_parent == nullptr && m_window != nullptr`） | 拒绝（`FRAMEWORK_ASSERT`），摘根应走 `Window::Release` | `false`（对象未动） |

返回值**刻意不标 `[[nodiscard]]`**：「删自己」的最常见写法是回调末尾一句 `RequestRemove();` 不取返回值。

> ⚠️ **`RemoveChild()` 与 `RequestRemove()` 的分工**：`RemoveChild(child)` 把子控件的 `unique_ptr` **同步交还**调用方——调用方一丢弃返回值，子树**立刻析构**。在事件回调里用它删除回路上的控件就是 UAF。⇒ **回调里删控件一律用 `RequestRemove()`**；`RemoveChild` 只用于不在派发路径上的结构性增删（如 `MemberListPopup::ClearRows`）。

### 3.2 存活保护：冻结链 + 引用计数

1. 每次派发开始时，`Application` 为「命中目标 → 根」整条链上的**每个节点** `m_dispatchRefCount += 1`（`Widget::PrepareDispatchChain`）；
2. 派发期间 `RequestRemove` 只摘树、不析构（对象由延迟队列持有所有权）；
3. 派发结束（含**异常**退出，RAII `DispatchGuard`）`ReleaseDispatchChain` 平衡计数，**最外层**（嵌套深度归零）才排空延迟队列。

### 3.3 「删自己」与「删祖先/整个子树」两种形态

- **删自己**：`this` 被钉住 ⇒ 摘树后回调体内**后续语句照常执行**，`this` 内成员仍可读（测试 `Events.Deferred.RemoveSelfInClickCallback`、`Events.Deferred.RemoveSelfInKeyDown`）。
- **删祖先/包含自身的子树**：`RemoveChild` 在**摘树当刻**注销该子树上的焦点/捕获/hover 登记，并把摘下的节点标记 `m_removedDuringDispatch` ⇒ 冒泡循环跳过它，不会再访问已摘节点；整棵子树在派发结束后一次性析构（测试 `Events.Deferred.RemoveAncestorInClickCallback`、`Events.Deferred.DeferredUntilOutermostDispatchEnd`、`Events.Deferred.TreeStillPaintsAfterRemoval`）。

### 3.4 键盘通道

键盘是**单收件人**派发（不冒泡），但同样要求「回调里可删自己」。因此 **`Application::OnKeyDown` 也开钉住区**（链 = 焦点控件 → 根），见 `Application.cpp` 的 `OnKeyDown` 与 `Window::HandleKeyDown` 注释。

> ⚠️ **回归历史**：`Window::HandleKeyDown` 的公开方法可以直接被调用（不经 `Application` 入口）。若应用/测试绕过 `Application` 直接调它，派发中并没有钉住区 ⇒ `RequestRemove` 会走「立即析构」分支，回调体内后续语句踩已析构对象（实测 0xC0000005）。**结论：控件级键盘派发必须经 `Application::OnKeyDown`（`app.OnEvent(KeyDownEvent(...))`）。** 本规范以此为准，`Window::HandleKeyDown` 视为**内部实现**，应用代码不应直接调用。

## §4 延迟销毁的边界（★ 维护者问题 4 的答案）

**边界 = 整个事件派发结束（最外层），而不是单次回调结束、也不是单次冒泡结束。**

- **选「整个派发」而不选「单次回调」**：父/祖父控件仍在当前冒泡链上，回调结束后它们还要被调用（若未消费）；若在回调返回时析构，冒泡循环手里的 `node` 就是悬垂指针。
- **选「最外层」而不选「本层」**：应用回调可能在派发内部**再触发一次派发**（`PostToUi` / 直接 `SendEvent`）。内层派发结束时，外层派发栈仍持有该控件或其祖先 ⇒ 必须等外层也结束。
- **兜底排水**：`Application::ProcessDeferredDestroy`（消息循环**每条消息后**由平台层回调）额外调用一次 `DrainDeferredRemoval()`（幂等），覆盖「请求在派发上下文之外产生」的残余队列。
- **析构顺序**：逆序（后入队先亡），与「先删子、后删父」的自然调用序一致；排水循环到队列为空。

**延迟期内「已脱树、未析构」的语义（验收 4）**：

| 项目 | 状态 |
|---|---|
| 命中测试 / 绘制 | **不含**它（已从父节点摘除） |
| 焦点 / 捕获 / hover 登记 | 摘树当刻已清除（不补发 `OnFocusLost` / `Up` / `Leave`——脱树是异常失效） |
| 控件对象本身 | 存活，`GetParent() == nullptr`，成员可读（**唯一**合法的「对象还在」证据） |
| 兄弟 / 祖先子树 | 完全不受影响，派发结束后整树仍可正常绘制与命中 |

## §5 验收对照

| 验收项 | 用例 |
|---|---|
| 1. 子按钮点击只触发子回调 | `Events.Consume.ChildClickDoesNotReachParent` |
| 2. 子控件未消费 ⇒ 父响应（且可稳定复现） | `Events.Consume.UnconsumedBubblesToAncestors`、`Events.Consume.ParentBlankAreaStillResponds`、`Events.Consume.AppLevelConsumesUpOnly`、`Events.Consume.AppLevelConsumesBothPhases` |

## §6 维护者问题答复汇总

| # | 问题 | 结论 |
|---|---|---|
| 1 | `Button` 是否应在有效点击后自动 `SetHandled()`？ | **是，且不止 Up**：Down 与 Up 都自动消费，与是否触发 `OnClick` 无关（§2.3）。 |
| 2 | 消费按事件类型分别定义，还是控件自行决定？ | **按事件（phase）分别定义 + 控件自行决定**：`Event` 自带「每事件一份」的 handled 状态，框架不跨阶段记忆；框架只把「Down/Up 必须成对消费」写为**一致性约定**（§2.4），并让内建 `Button` 示范这一形状。 |
| 3 | 控件树修改 API 是否自动延迟析构？ | **是，由框架自动延迟**：`Widget::RequestRemove()` 在派发中自动入延迟队列；非派发中保持「立即脱树 + 析构」原语义。⚠️ **`RemoveChild()` 本身不延迟**——它把 `unique_ptr` 直接交还调用方；在回调里 `RemoveChild` 自己的容器是**应用侧**的 UAF（§3.1、§3.3）。 |
| 4 | 延迟边界 = 单次回调 / 完整冒泡 / 整个派发？ | **整个事件派发结束（最外层）**，含嵌套派发；消息循环轮次另有幂等兜底（§4）。 |

### 6.1 公共 API 面（Phase 35 净增量）

| 名称 | 可见性 | 用途 |
|---|---|---|
| `Event::SetHandled()` / `IsHandled()` | 既有公共 | 回调里消费当前事件（§2） |
| `Widget::RequestRemove()` | **新增公共** | 派发中删控件（§3） |
| `Application::IsDispatching()` / `Application::DeferDestroy()` | **private**（框架内部） | 仅 `ApplicationAccess` 可调；`ApplicationAccess::IsDispatching/DeferDestroy` 又只向 `Widget` 开放 ⇒ 应用侧不可达 |

> ⚠️ **实现备注（访问权限的编译器差异）**：`Widget` 虽在 `Application.h` 里声明为 friend，但 MSVC / clang-cl **不**据此授予 Widget 的**成员函数体**访问权限（`'IsDispatching' is a private member of 'ECDI::Application'`，实测），GCC 会。故二者之间有一条 `struct ApplicationAccess`（成员私有、`friend class Widget`、定义在 `Application.cpp`）。**新增跨类访问一律走它**——直接 `app->Xxx()` 会在 clang-cl 链上编译失败。
