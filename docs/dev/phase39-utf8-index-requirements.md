## §1 输入与问题陈述

### 1.1 #78 原文主张的逐条对码结论

| # | 原文主张 | HEAD 对码结论 |
|---|---|---|
| ⓐ | `TextBox::RecalculateLines` 循环体内**每码点两次** `CodepointIndexToByteOffset`（每次从串首全扫）⇒ 整体 O(N²) | ★★ **属实，且比原文更精确**：现 `TextBox.cpp:481-489` 的 `for` 体中 `:482` / `:483` 各一次；`CodepointIndexToByteOffset`（`Core/UTF8.cpp:35-43`）从 `byteOffset = 0` 起逐字节推进，代价 **∝ 码点索引本身**（§1.3 的线性度读数：20k 串上 index=5000 → 3.1 µs、index=20000 → 12.6 µs ⇒ ~0.63 ns/走过的码点） |
| ⓑ | 同循环 `m_text.substr(...)` **每码点一次堆分配**（10k 码点 = 10k 次分配） | ★★ **不属实（订正）**：切片长度 = **1–4 字节**，落在 `std::string` 的 **SSO** 范围内 ⇒ **零堆分配**。探针以全局 `operator new` 计数实测 **分配 = 0**（§1.3 表 1 的 `分配` 列）。⇒ 本条的成本**全在 CPU，不在分配器**；把它当「分配器压力」去修会修错方向 |
| ⓒ | `TextMeasurer` 默认 `FitText` 的二分体**每一步**同样调它 | ★ **属实但定性错**：默认体（`Render/TextMeasurer.h:68-117`）**是兼容 fallback，不是生产路径**——该头 `:62-67` 自己写明「**非** GDI / FT 生产性能路径」，且 `GDITextMeasurer::FitText`（`GDITextMeasurer.cpp:148-152` 自述「不走默认二分体」）与 `FontEngine::FitText`（`FontEngine.cpp:505`，经 `FreeTypeTextMeasurer.cpp:40-51` 转发）**均已原生覆写**。⇒ 它的成本只对**测试替身 / 第三方 measurer** 成立（本 Phase 顺手做零风险的循环不变量外提，见 R2；**不把它当主战场**） |
| ⓓ | 单点调用（`TextBox.cpp` 的 caret / 选区 / 命中 / IME 锚点）**不在本条范围** | ★ **属实**：这些是每次交互**一次** O(N) 换算（20k 串上 ~6–13 µs），不构成放大项。本 Phase 沿用该边界（N5） |

### 1.2 ★★★ 原文未提、且量级更重的一条：折行支**每行一次「整串预备」** ⇒ O(L·N)

Phase 38 把折行接进编辑器后，`TextBox::RecalculateLines` 的折行支走基类引擎（`TextBox.cpp:466`），而引擎的每行适配都**把整串传进去**：

```cpp
// TextWidget.cpp:270 —— 每「视觉行」调一次，text 是整串
const TextFit fit = measurer.FitText(font, text, scan, limit);
```

两个生产测量器在这个入口内部各自做一次 **O(N) 的整串预备**：

| 测量器 | 每行固定成本（与行宽无关） | 行号 |
|---|---|---|
| GDI | `ByteOffsetToCodepointIndex(text, text.size())`（整串数一遍码点，**只为了知道 `totalCp`**） | `GDITextMeasurer.cpp:153` |
| GDI | `CodepointIndexToByteOffset(text, startCp)` + `UTF8ToWide(text.substr(byteStart))` ⇒ **整条尾部拷贝 + 宽字符转换** | `:170-171` |
| FreeType | 同上第一项 `ByteOffsetToCodepointIndex(...)` | `FontEngine.cpp:509` |
| FreeType | `DecodeUtf8(text)` ⇒ **整串解码成 `vector<char32_t>`**（且 `reserve(utf8.size())` 对 CJK 是 **3× 过预留**，`Render/Utf8Decode.h:20`） | `FontEngine.cpp:529` |

⇒ 折行 L 行 = **L 次整串解码 / 计数 / 拷贝**。20k 码点（60 KB）的 CJK 串在**约 400 DIP 宽**（14px 字 ≈ 28 字/行）下 L ≈ 770 ⇒ 仅 `totalCp` 计数一项就是 770 × 14.9 µs ≈ **11 ms**，FT 侧再加 770 × 38.7 µs ≈ **30 ms**，并伴随 **770 次 × 240 KB** 的 `vector` 分配/释放（≈ 185 MB churn）——**每次按键重建都付一遍**。

★★ **但本稿建议：B 不在本 Phase 做**（D39-3）。理由是它的修法要动**测量器接缝**（要么给 `FitText` 加「带游标的增量接口」= 改契约 + 3 个实现 + 测试替身；要么在 measurer 内部按 `(data 指针, size)` 缓存偏移表 = 引入一个「同一个串被反复传入」的隐式假设），风险档与 A 完全不同，混在一起会让「零 API、可逐位对拍」的 A 失去干净的判据。⇒ **建议新立 #83**（§6），本稿只把读数与机理落档。

### 1.3 现状量化（探针实测，2026-10-29）

**采集方式**：两个独立 TU 的微探针（`probe.cpp` 只链 `Core/UTF8.cpp`，不依赖 Window / 测量器），**不写盘进 CMake、不入库**，命令与 flag 如下；`-O2`、MinGW g++ 16.1、本机 i7 级 20 线程。

```bash
g++ -std=c++20 -O2 -I ECDI/include probe.cpp ECDI/src/Core/UTF8.cpp -o probe.exe
```

**表 1 · 复刻 `RecalculateLines` 非折行支的循环体（每码点 2 次换算 + 1 次 1–4 字节 `substr`）**
取 n 次重复的**最小值**（CJK = 每码点 3 字节的 `字`；ASCII = `a`）：

| 内容 | 码点 | 现状循环 | 单趟推进（候选修法） | 倍率 | 分配次数 |
|---|---|---|---|---|---|
| CJK | 1 000 | **0.641 ms** | 0.0030 ms | 214× | **0** |
| CJK | 5 000 | **15.461 ms** | 0.0140 ms | 1 104× | **0** |
| CJK | 10 000 | **63.130 ms** | 0.0280 ms | 2 255× | **0** |
| CJK | 20 000 | **257.194 ms** | 0.0560 ms | 4 593× | **0** |
| ASCII | 1 000 | 0.342 ms | 0.0010 ms | 342× | **0** |
| ASCII | 5 000 | 9.039 ms | 0.0050 ms | 1 808× | **0** |
| ASCII | 10 000 | 36.320 ms | 0.0100 ms | 3 632× | **0** |
| ASCII | 20 000 | 143.043 ms | 0.0210 ms | 6 812× | **0** |

★ **二次性判读**：CJK 1k→2k…20k 时 0.64 → 15.5 → 63.1 → 257.2 ms；**n 翻倍耗时 ≈ ×4**（5k→10k = 4.08×，10k→20k = 4.07×）⇒ 实测就是 O(N²)，不是「常数大」。

**表 2 · 单点换算的线性度**（20 000 码点 CJK，`CodepointIndexToByteOffset`，mean of 20 000 次）

| index | 每次耗时 |
|---|---|
| 0 | 0.6 ns |
| 5 000 | 3 108.8 ns |
| 10 000 | 6 556.2 ns |
| 20 000 | 12 626.0 ns |

⇒ **∝ index**，与 `Core/UTF8.cpp:38-41` 的 `while (byteOffset < text.size() && cpIndex < codepointIndex)` 逐字节推进完全一致。

**表 3 · B 的每行固定成本**（20 000 码点 CJK，mean of 200 次）

| 量 | 读数 | 备注 |
|---|---|---|
| `ByteOffsetToCodepointIndex(text, size)` | **13.8–14.9 µs** | GDI / FT 的 `FitText` 每行各调一次 |
| `DecodeUtf8(text)` | **38.7 µs** + **1 次分配** | FT 每行一次；`reserve(3N)` = 240 000 字节 |

### 1.4 触发面与用户可感知后果

| 场景 | 走的支 | 每次重建代价（20k CJK） |
|---|---|---|
| 日志窗 / JSON 预览（**无折行**、单段落） | 非折行支（A） | **257 ms** ⇒ 按键明显卡顿，输入延迟肉眼可见 |
| 聊天输入框（**折行**、短文本） | 折行支（B） | 短文本下两者都可忽略（< 0.1 ms） |

★ **为什么先修 A 而不是 B**：A 的触发面是**「无折行长文本」= 最常见的既有用法**（JSON / 日志 / 配置框），且修法**零 API、零结构改动、可逐位对拍**；B 只在折行 + 长文本下才压过 A，且要动测量器契约（D39-3）。

## §3 范围与非目标

### 范围（R1–R2）

- **R1（主体）** `TextBox::RecalculateLines` 非折行支改**单趟推进**：按前导字节推进 byte 指针、同趟累计码点索引，判 `\n` 只看首字节；**消灭循环体内的两次换算与一次 `substr`**。要求：行表（`startCp` / `cpCount` / `width` / `ownedEnd` / `totalHeight`）**逐位不变**。
- **R2（顺手，零风险）** `TextMeasurer::FitText` 默认体的**纯等价变换**：`byteStart` 提到二分循环外、首码点切片的三次重复换算合并为一次。仅影响 fallback 路径（生产走覆写），**行为逐位不变**。

### 非目标（N1–N8）

| # | 不做 | 理由 |
|---|---|---|
| **N1** | 折行支每行「整串预备」（§1.2 的 B） | 要动测量器接缝，风险档不同 ⇒ **建议新立 #83**（§6） |
| **N2** | `OnPaint` / `DrawTextContent` 的每行换算 | 与 B 同量级同解；单修一节等于拆半 | 
| **N3** | 给 `Core/UTF8` 加「码点 → 字节」随机访问索引表（`vector<uint32_t>`） | ★ 第二次真实消费者未出现（YAGNI）；R1 根本不需要它（单趟推进天然给出顺序访问） |
| **N4** | `BuildDisplayText()` 的整串拷贝（K11） | 20k 串 ≈ 2 µs，比 A 小 5 个数量级；且改签名会影响 3 个调用点 + 派生类 |
| **N5** | 单点换算（caret / 选区 / 命中 / IME 锚点 / 行内逐码点） | 每次交互一次 O(N)（≤ 13 µs @20k），不是放大项；#78 原文也划在范围外 |
| **N6** | `DecodeUtf8` 的 `reserve(utf8.size())` 3× 过预留 | 属 B 的账（#83） |
| **N7** | 任何 public API 签名 / 文件布局 / CMake 目标改动 | R1 只动一个函数体；R2 只动一个 inline 体的三条语句 |
| **N8** | 性能阈值式的「X 倍」承诺 | 沿 Phase 28 纪律：只承诺复杂度 + 分配次数 + 记录制读数 |

## §4 决策点 D39-1..6（倾向 ≠ 定案；每项初设必须给论证）

| # | 决策 | 倾向 | 理由 / 初设必答 |
|---|---|---|---|
| **D39-1** | R1 的形态：**单趟推进**（`byte` + `cp` 双游标）vs 保留换算但加索引表 | **单趟推进** | 循环天然顺序访问（0→N），单趟是唯一不需要额外存储的形态；索引表要随 revision 失效（多一份缓存、多一处失效责任），而收益只是把 O(index) 变 O(1)——**本循环不需要随机访问** |
| **D39-2** | 单趟推进的**代码位置**：写在 `TextBox.cpp` 里 vs 抽到 `Core/UTF8.h` 成新 API | **写在 `TextBox.cpp`**（局部静态辅助或直接内联） | 只有一个消费者（YAGNI）；且它只需要「按前导字节跳过 + 判 0x0A」，不需要通用的「解码」。★ 若初设发现 `TextWidget` / `DrawTextContent` 也要用同一游标 ⇒ 再抽（那是第二次消费者） |
| **D39-3** | B（每行整串预备）是否并入本 Phase | **不并入，新立 #83** | §1.2 的修法要改测量器契约（增量接口）或引入「同串复用」隐式假设；混做会让 A 的「零 API + 逐位对拍」判据失去干净性。★ 若你要合并，初设必须同时给「`FitText` 契约怎么改 + 3 个实现 + 测试替身」的完整方案 |
| **D39-4** | R2（默认 `FitText` 循环不变量外提）做不做 | **做** | 纯等价变换、零风险；★ 但它改的是**公共头** ⇒ 编译代价高（K12），必须与 R1 同批编一次 |
| **D39-5** | 验收的基准形态 | **「行为 + 计数」进测试，「耗时」进探针** | 测试里断时序必然 flaky（Phase 23 有 flaky 先例）；⇒ 测试断言「行表逐位相同」+「换算调用次数」（后者用**机检** `grep` 而非运行时插桩，避免给产品码加计数器）；耗时不设阈值，只做**改前/改后记录制**（A7） |
| **D39-6** | 是否顺手把 `GetCodepointCount()` 的 O(N) 也省掉（单趟顺带得到 count） | **做**（R1 的自然结果） | 单趟本来就要累计 cp 计数 ⇒ `count` 免费；★ 但要注意 `count` 在循环**之前**被用于上界——改造后循环条件应改为「`byte < size`」而非「`i < count`」，初设需给出逐行骨架 |

## §7 初设闸门（移交初设的必答项）

1. **单趟推进的逐行骨架**：`byte` / `cp` 双游标的初值与推进式；循环条件为什么可以从 `i < count` 改成 `byte < size`；`count` 从哪里来（顺带累计 vs 调 `GetCodepointCount()` 一次）。
2. **非法 UTF-8 的等价性证明**：`SequenceLength`（`UTF8.cpp:9-15`）对非法前导按 1 字节推进 ⇒ 单趟必须**逐字复刻**该规则，否则行表在脏字节上与改前分叉（A6 的非法字节样本）。
3. **`\n` 判定为什么可以只看首字节**：`0x0A` 不可能出现在多字节序列的续字节位（续字节 ∈ 0x80–0xBF）⇒ 需在初设写出这条论证，作为「不解码也能判 `\n`」的依据。
4. **R2 的等价性论证**：`byteStart` 外提后，二分体对 `MeasureText` 的调用序列是否**逐次相同**（A5 的判据基础）。
5. **批 0 基准的采集口径**：A5 的常量表必须在 HEAD 上、**改代码之前**采完（Phase 38 的批 0 先例），并写明「采不到就不得动 R2」。
6. **耗时探针的形态**：是继续用一次性临时探针（命令写进文档），还是落成 `tools/phase39_*_probe.cpp`（要定是否进 CMake）——初设给结论。
