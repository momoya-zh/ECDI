### 1.2 为什么这是 ECDI 侧缺陷，而不是「调用方用法不当」

判据只看一件事：**框架自己的文档承诺了什么**。

| 承诺落点 | 原文 | 与实现是否一致 |
|---|---|---|
| `Theme/ScrollBarStyle.h:12` | 「**thickness 放在 Style 而非控件常量**：它不是视觉细节，而是**参与 viewport 计算**的几何量」 | ❌ 对横条不成立 |
| `Theme/ScrollBarStyle.h:20` | `StyleField<int> thickness;` ——「条厚度（占用视口的宽/高——**参与 viewport 计算**）」 | ❌ 对横条不成立 |
| `Widget/ScrollBar.h:58-61` | 「厚度**不是本控件私有视觉量**，`ScrollView` 要用它扣 viewport；**必须单点可查**」 | ⚠️ 「单点可查」实现成了「**只查竖条**」 |
| `Theme/DefaultTheme.cpp:103` | 「⚠️ thickness 不是纯视觉量——它参与 viewport 计算（详设 §3.3 双轴判定要扣它）」 | ❌ 同上 |

四项承诺都指向「**每一条的厚度都参与计算**」；而实现只读 `m_vBar`。这不是「调用方误解了 API」，是**框架实现了它的注释的反面**——按本仓条 1（命名即语义 / 契约单源），归 ECDI 侧。

★ harness 的处置是**绕行**（两条同薄 4px），代价是可量化的：为把横条从 12 降到 4，竖条被迫一起降到 4 ⇒ **竖条命中宽度只剩 4px**（`ScrollBar.h:115` 的 `kMinThumbLength = 24` 保的是滑块**长度**，管不了厚度方向的命中宽）。

## §2 方案选型

### 2.1 候选对比

| 方案 | 内容 | 改动面 | 公共面 | 判定 |
|---|---|---|---|---|
| **A 双轴拆分（采纳）** | `BarThickness()` 拆成 `VerticalBarThickness()` / `HorizontalBarThickness()`；**5 个调用点各取对轴**（覆盖 6 个几何结论，见 D43-2） | `ScrollView.h` 声明 + `ScrollView.cpp` 5 处站点 + 测试 | **0** | ✅ 让既有承诺成立；同厚路径逐位等价 |

### 2.2 为什么选 A（机理）

`ScrollView` 的「条占多少」本来就该是**两条各自的事**：竖条占**宽**、横条占**高**。现在的单值 `t` 是 Phase 15 引入时的**同厚假设残留**（v1.6 内缩改造时用 `BarFootprint(t)` 把四处公式收口，收口本身是对的——把「一个厚度」收进了一个函数，问题是那个厚度**来源只有一条**）。A 方案 = **保留收口、只把「一个厚度」拆成「按轴两个厚度」**，5 个调用点仍然是「各自调一次 `BarFootprint`」，结构不变、语义归位。

★ **关键的自证**：K10 保证默认路径两条恒同厚 ⇒ 拆分后**默认行为逐位不变**；红线 1 由此可被既有断言直接守住（不需要新的等价性证明）。

## §3 核心设计决策

### D43-1 · 助手拆分与命名（`VerticalBarThickness` / `HorizontalBarThickness`）

`BarThickness()`（单数）是**误导源**本身：调用方读不出「哪一条」。拆成两个对称的助手，并且**删掉单数名**（不留别名——留着下一个人还会用错，这正是本缺陷的成因）。二者语义：读**自己那条**的 `ScrollBar::GetThickness()`；对应条为 `nullptr` ⇒ 返回 `0`（与现 `?: 0` 逐位等价）。

### D43-2 · 四个站点的轴向归属（逐点钉死）

| 站点 | 该读哪条 | 理由 |
|---|---|---|
| `NeedsVerticalBar` 的 `tH`（`:218`） | **横条** | 扣的是**高度**，高度被横条吃掉 |
| `NeedsHorizontalBar` 的 `tW`（`:239`） | **竖条** | 扣的是**宽度**，宽度被竖条吃掉（**现状即对，不改语义**） |
| `ViewportWidth`（`:248`） | **竖条** | 同上（现状即对） |
| `ViewportHeight`（`:255`） | **横条** | ⚠️ 现状错的正是这里 |
| `ApplyLayout` 竖条尺寸（`:272-273`） | **竖条** | 厚度 = 自身厚度 |
| `ApplyLayout` 横条尺寸（`:279-280`） | **横条** | 同上 |

★ 三个「错轴读取点」（K4 / K6 / K7）全部落在这张表里，**没有第四处**：`BarThickness()` 全库 = 定义 **1** 处（`:193`）+ 调用 **5** 处（`:208` / `:232` / `:248` / `:255` / `:263`），对上表 6 个几何结论。

### D43-3 · 空指针退化保持原语义

`m_vBar` / `m_hBar` 当前恒非空（构造必建，`ScrollView.cpp:35-41`），但助手仍按「该条为空 ⇒ 0」写：这是**契约层面的退化保护**，不是防御性编程的猜测——`BarThickness()` 的原实现就这么写，不改变它会让本 Phase 多一个「未定义行为」入口。

### D43-4 · 交叉区不缩角（红线 3 的落地）

`ApplyLayout` 里竖条占满 `H - 2s`、横条占满 `W - 2s`（`:272` / `:279`），二者在右下角**重叠**——这是 **L2 既有记账**（「交叉区仍不做缩角」）。双轴异厚后重叠矩形变成 `t_v × t_h`，仍是**重叠**（不会出洞）。绘制顺序 = `AddChild` 序 ⇒ 横条后画、盖住竖条（`:39-41`），与今日同构。**本期不改**。

### D43-5 · `ScrollBar` 本体零改动

K8 已证明 `ScrollBar` 的绘制与命中都不读 `thickness`（只读自身矩形），所以「厚度」在 `ScrollBar` 侧**只是被容器查询的一个数**。本 Phase 不碰 `ScrollBar.h/.cpp`。

### D43-6 · R84-C′（改厚度不重排 ⇒ C7 可被破坏）本期不修，但必须写进注释

修它需要一条**从条到容器的通知通道**（`ScrollBar` 目前只有 `SetOnOffsetChanged`，厚度变化没有回调）。新增回调 = 新公共 API + 生命周期约束（回调内不得析构宿主），而当前**零运行期消费者**（harness 在构建期一次性设样式，之后必有一次 `SetSize`）⇒ 记入 §7 L43-2，并在 `ScrollView.h` 的两个助手注释里写明两件事：① 「**样式类厚度变更需由调用方触发一次尺寸 / 内容变更**」；② ★ **别写成「调 `SetContentExtent` 即可」**——它在 extent 未变时早退（`:85-89`），**必须用 `SetSize`**（`:328-351` 同值也重算）。

## §6 闸门裁决落盘记录（2026-11-01 审核裁决）

- [x] **闸门 1 · 契约口径 —— 取 A（双轴独立）**
  理由：B 是把「实现说谎」**文档化**，与仓内条 1（命名即语义 / 契约单源）直接冲突；且四处注释承诺（`ScrollBarStyle.h:12` / `:20` · `ScrollBar.h:58-61` · `DefaultTheme.cpp:103`）均已对码核实存在。
- [x] **闸门 2 · R84-C′（效果 = 审计 M6）—— 本期不做**
  理由：零**运行期**消费者（harness 在构建期一次性下发样式，之后必有一次 `SetSize`）＋ 修它需新增公共回调通道；D43-6 的处置（写进注释 + 记账重启条件）足够。★ 但 v1.1 已把该条的**后果**从「滞后」升级为「**C7 被破坏、offset 可越界**」，并把「唯一现成出口 = 同值 `SetSize` 也会重算」写进 §7 L43-2——**不做 ≠ 不知情**。
- [x] **闸门 3 · 命名 —— 取对称命名 `VerticalBarThickness` / `HorizontalBarThickness`**
  ★ **为何不采审计 M5 的原案 `BarThickness(orientation)`**（v1.1 补，四条理由）：
  1. **参数化把「读哪条」从编译期常量降级为运行期实参**——本缺陷的原始成因正是「一个函数代表两条」，参数版给了它一个合法的默认值，下一个调用点复制粘贴即回原点；
  2. **5 个调用点里 3 处已经对了、只有 2 处待改**：这种「大多数正确」的分布最容易被默认参数静默带偏（写错不报错、测试也不响，与 R84-A 同类）；
  3. **语义层级**：`ScrollView` 的轴概念不该用 `ScrollBar` 的 `Orientation` 枚举表达——容器对条的依赖应停在「读一个数」，不是「把条的自描述枚举引进来当轴标」；
  4. **可审计性**：对称命名使 `grep VerticalBarThickness` 直接枚举出全部「读竖条」的站点——本缺陷恰是**审计可见性不足**导致的漏网（M5 早已写过，却没人把 5 个调用点逐个对轴）。
  代价 = 多两行声明（`+7 / −3`），已含在 §5.2 预算内。
