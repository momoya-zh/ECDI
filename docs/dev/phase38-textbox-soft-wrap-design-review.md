## §1 P0-1 · 显示串穿透漏了 `TextWidget.cpp:269`（决定断点的那一处）

**文档主张**（§1.5、§3 PD38-2、§6 影响面）：落点"两处"——`:210` 的 `DecodeUtf8` 与 `:228-230` 的补测三连；"只改落点一 = 索引按显示串、宽度按真实串"。

**实测**：`BuildTextLayout`（`:202-310`）函数体内 `m_text` 共 **4 行 5 处**：

```
$ sed -n '202,310p' ECDI/src/Widget/TextWidget.cpp | grep -n "m_text"
 9:  const std::vector<char32_t> cps = DecodeUtf8(m_text);                    → :210
27:  CodepointIndexToByteOffset(m_text, lineStart)                            → :228
28:  CodepointIndexToByteOffset(m_text, end)                                  → :229
29:  return measurer.MeasureText(font, m_text.substr(b0, b1 - b0)).width;     → :230
68:  const TextFit fit = measurer.FitText(font, m_text, scan, limit);         → :269   ★ 漏
```

**为什么这一处最要紧**：`:269` 是**决定断在哪**的那次调用。`FitText` 的默认体（`TextMeasurer.h:68-117`）在传入串上做 `CodepointIndexToByteOffset` + `MeasureText(切片)`，宽度口径完全由传入串决定。若只改 `:210` 与 `:228-230` 而留 `:269` 用真实串：行表起点按显示串推进、`fitCp` 按真实串宽度算 ⇒ 掩码框（`•` 3 字节 vs ASCII 1 字节）折行位置偏移，正是文档自己警告的"混合口径"，只是方向相反。

**连带**：需求稿 §6 与初设 §1.5 都把落点写成"两处"，等于**把缺口写进了上游**；只有 C38-4 的 `grep m_text == 0` 能兜住，但它是"实施完的自检"，不是"落点表的完备性"。

**修法**：PD38-2 改为五处（`:210 / :228 / :229 / :230 / :269`）；§1.5 的"两处落点"改述为"三处语义落点：解码 / 补测 / `FitText`"；C38-4 的定位从"验收手段"升为"落点表的完备性检查"，并要求详设逐行列出改后函数体内 `m_text` 命中为 0 的截图式证据。

## §2 P0-2 · A4 的负对照在给定数字下是**假绿**

文档 §1.2 的夹具：`padding=0` · `width=40` · 文本 `"abcdefgh"` · 两态 `H=64 / H=32`，并断言"回退谓词 ⇒ 40/2 vs 26/3 ⇒ **红**"。

**按 HEAD 源码实算**（`ScrollBarInset = max(p,2) = 2`，条厚 12 ⇒ 常驻扣 14；`GetMaxScrollOffset = max(0, n·16 − H)`，`need = !singleLine && maxScroll > 0`）：

| 实现 | H=64 | H=32 | H=24 |
|---|---|---|---|
| **本方案**（`IsVisible() \|\| WrapRequested()`） | `wrapWidth 26` / `n=3` / 条隐藏 | `26` / `3` / 条可见 | `26` / `3` / 条可见 |
| **负对照**（回退为仅可见才扣） | `40` / `n=2` / 条隐藏 | **`40` / `n=2` / 条隐藏** | `26` / `n=3` / 条可见 |

⇒ 取 `(H=64, H=32)` 两态：本方案 `26/3 == 26/3` 绿；**回退实现 `40/2 == 40/2` 也是绿**。文档 §1.2 表第二行给的 `26/3` 在 `H=32` 下**不是旧谓词的不动点**——旧谓词下 `H=32` 时内容高恰等于视口（`32−32=0`），条**永远不出现**，所以"条可见态"在该 H 下不存在。

⇒ 这恰恰是 P0-3 要求消灭的"假绿"，只是换了个位置复现：**判据本身不具判别力**。

**修法**：第二态改 `H=24`（或任意 `H < 32`）。此时旧谓词 `H=24 → 26/3/可见`，与 `H=64` 的 `40/2/隐藏` 不同 ⇒ 负对照变红 ✓；本方案 `26/3 vs 26/3` 仍绿 ✓。§1.2 表、T38-8 的夹具数字一并改，并在正文加一句"**两态必须都落在各自实现的不动点上**，否则负对照失效"。

**S7 的第二断言没有判别力**（这条比 S3/S5 更值得改）：`FakeTextMeasurer::MeasureText` 按**码点数 × 8** 计宽（`TextBoxTests.cpp:34-40`），而掩码串与真实串**码点 1:1**（`TextBox.cpp:231-254`）⇒ 无论实现喂 `m_text` 还是 `BuildDisplayText()`，行表**逐字段必然相等**。文档称"等值即证走的是显示串"是反向推理：等值在两态下都成立，恒真断言不判别任何东西。要真判 K9，需二选一：① 换一个**按字符宽度区分**的测量器（`•` 记 8、ASCII 记 4）⇒ 喂错串时行数必变；② 用记录型测量器，断言传给 `FitText` / `MeasureText` 的串**含 U+2022 的字节**（`E2 80 A2`）。

**修法**：S3 补空格并改回 12 码点；S5 的 L1 宽度改 w16；S7 的判别手段换成 ①/② 之一，并把"等值即证"的说法删掉。

## §4 P1（4 项：需在详设里改判据或显式登记）

### P1-1 · 键解决"算得对"，不解决"何时算"：`SetSingleLine` 不触发重绘

`TextBox.cpp:162-167`：

```cpp
void TextBox::SetSingleLine(bool singleLine){
	if (m_singleLine == singleLine) return;
	m_singleLine = singleLine;
	// 键盘语义开关（Enter 不换行）——无需重绘，但保持与 SetReadOnly 同构
}
```

只改标志位，**不 `Invalidate()`、不 `SyncScrollBar()`**。折行后 `singleLine` 进了激活判据（D38-D）⇒ 切换它会同时改行表、内容高、条显隐，但**没有任何重绘请求** ⇒ 界面停在旧状态直到下一次无关失效。D38-E 的"失效只经键"与 C38-6 的"禁止 setter 置脏"都只管"重算正确性"，不管"重算触发"。这是 11 维键**结构性覆盖不到**的一个面（键只在被调用时才比对）。建议：`SetSingleLine` 补 `Invalidate()` + `SyncScrollBar()`，或在 §7 新增一条"已知触发缺口"并配用例。

### P1-2 · R38-5 把"整字不可见"写成了"悬挂微超"

S4 实测：行宽 32、折行宽 24 ⇒ 被裁 8px = **一整个码点**（`。` 全在 clip 外），而 `scrollOffsetX ≡ 0` ⇒ 该标点**永久不可见**，但光标可停、选区可选中。这不是"微超不可达"，是"看得见光标、看不见字"。

而 harness 的 `ComposerBox` 正是**中文聊天输入框**，行尾悬挂闭标点是中文排版的高频形态 ⇒ 这条大概率在首个真实消费者上就命中。建议在 §7 补一个备选：`PushClip` 的宽度取 `GetWidth() − 2·padding`（而非折行宽），只裁到控件内边界 ⇒ 悬挂字符可见、且不需要放开 `scrollOffsetX`；若判为不做，需在需求层显式接受该观感缺陷（现在只写在 R38-5 的缓解列里，容易被读成"轻微"）。

### P1-3 · "棘轮从代码结构上不可达"过强：`0 < W ≤ 2p+14` 窄带仍可达

D38-F/PD38-6② 断言棘轮"不是算错，是进不去"。但闸是 `IsWrapActive()`，它要求 `GetTextAreaWidth() > 0`；而基类的 `IsWrapLayoutActive()` 只要 `m_wordWrap && GetWidth() > 0 && GetWindow() != nullptr`（`TextWidget.cpp:123-129`）。当 `0 < W ≤ 2p + 14` 时：本类判据**假** ⇒ 落到 `:199` 基类调用 ⇒ `:433` 为真 ⇒ 返回 `{GetWidth(), totalHeight}` ⇒ `:201` 再 `+2p` ⇒ **棘轮照旧**（直到 W 越过阈值）。窄，但可达，且 `AutoSize` 恰恰是从小宽往大宽爬。建议把闸写成 `WrapRequested() && ResolveMeasurer() != nullptr`（不依赖 `width > 0`），或在正文把"不可达"降级为"在 `GetTextAreaWidth() > 0` 区间内不可达"。

### P1-4 · PD38-7 的"11 站全表"不是读取点的超集

`m_lineStarts` 的真实读取点是 11 处：`:461/465/468`（`LineIndexFromCodepoint`）、`:480-481`（`LineRange`）、`:515`、`:529`、`:565`、`:684`、`:778`、`:1251`、`:1370`。而 PD38-7 表里 C4/C5/C9 是**惰性门**（不是读取点），真正要改二分的 `LineIndexFromCodepoint`（`:460-474`）**不在表内**，只在 PD38-5 顺带一提；`CaretIndexFromLineX`（C8）反而被列为"零改动"。表自称"11 站全表 = 唯一防漏装置"，但它的口径混了"读取点"和"失效门"两类东西，且与需求 §2.1 的编号不一致（需求 C1 = `LineIndexFromCodepoint`，初设 C1 = `GetTextTopInset`）。建议按"读取点"重排并与需求编号对齐，把惰性门单列一栏。

## §8 复算脚本与命令

样本表与 A4 夹具的实算由 `tools/phase38_wrap_probe.py` 产出（HEAD 源码的一比一复刻：硬段切分 → `FitText` 码点二分 → `FindLastSoftBreak` → ④⑤ 禁则 → ⑦ 跳空格 → 尾部空白裁剪），关键输出：

```
S1   'ab cd ef'    w48 -> 2 lines: [0,5) w40 own6 | [6,8) w16 own8      ✅ 与文档一致
S3a  'ab cd\nef gh' w40 -> 2 lines: [0,5) w40 own5 | [6,11) w40 own11   ❌ 文档写 3 行
S3b  'ab cd \nef gh' w40 -> 3 lines: [0,2) w16 own3 | [3,5) w16 own6 | [7,12) w40 own12  ← 文档期望的真实串
S5   '一二三（四'   w32 -> 2 lines: [0,3) w24 own3 | [3,5) w16 own5      ❌ 文档 L1 写 w32
A4   H=64 -> (26,3,hidden)   H=32 -> NEW (26,3,visible) / OLD (40,2,hidden)   ← 负对照绿
     H=24 -> NEW (26,3,visible) / OLD (26,3,visible)                          ← 两态都可见
```
