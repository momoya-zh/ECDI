## 2. 核心决策结论

### 2.1 D8 定案：形状装配选 A（3 条实心带 + 4 个角补丁）

**结论：选 A。B（扫描线）的唯一优势在既有代码中不存在。**

**论证**：`DrawRoundedRect` 现有实现已把半径钳制到 `[0, min(w,h)/2]`（`GDIBackend.cpp` 既有 `std::clamp`）：

```text
R <= min(w, h) / 2   =>   2R <= w  且  2R <= h   =>   w - 2R >= 0  且  h - 2R >= 0
```

即**三条带的尺寸永不为负**——A 方案无需任何退化分支。而 B 方案（扫描线）需按行组织，`O(h)` 次绘制调用（710px 高的面板 = 710 次 FillRect）对比 A 的 **7 次固定绘制原语**。

| 维度 | A · 3 带 + 4 角补丁 | B · 扫描线 |
|---|---|---|
| 绘制原语调用数 | **7（固定；3 FillRect + 4 AlphaBlend）** | O(h) |
| 退化分支 | **不需要**（钳制已消除） | 不需要 |
| 与 GDI 原语契合 | 高（FillRect + AlphaBlend） | 低（需逐行组织 + 端点部分覆盖） |
| 实现复杂度 | 低 | 中高 |

> **计数口径（v1.1 统一——评审 §七）**：本节及全文的「调用数」一律区分三层，不再混用：
> - **高层几何绘制**：3 条实心带 + 4 个角补丁 = **7 个几何单元**
> - **GDI 绘制原语**：3 × `FillRect` + 4 × `AlphaBlend` = **7**
> - **GDI 资源操作**：1 × 建刷 + 1 × 释放刷（**+ ScratchDIB 管理，已复用故非每调用**）= **2**
>
> 故 `a == 1` 路径相对现状的对比是：**1 次 `RoundRect` → 7 次绘制原语 + 2 次资源操作**。

→ **A 在两项上不劣于 B，在一项上显著更优。定案 A。**

### 2.2 D11 定案：语义统一 + 实现分路（并给出等价性证明）

**问题重述**（需求 D11）：若只给 `a < 1` 加 AA，则「不透明 Button 有锯齿、半透明 Button 无锯齿」——同一 API 两种视觉质量。

**初设结论**：

```text
✅ 视觉语义统一：三条路径（legacy / a==1 / a<1）中，凡 R > 0 且 AA 开启，
   覆盖度一律被应用 —— 不存在「有 AA」与「无 AA」并存
✅ 实现分路保留：a==1 与 a<1 用不同 GDI 原语，但已证明数学等价
```

**等价性证明（`a == 1` 之路的「数学等价快路径」）**：

需求 D11 候选③要求「先统一语义 → 再寻找数学上等价的快路径」。本设计找到的等价点如下：

| 几何部位 | 覆盖度 | 若走统一混合路径的结果 | 快路径 | 是否等价 |
|---|---|---|---|---|
| 3 条实心带 | **恒为 1**（整数像素对齐，见需求 §1.3） | `out = color·1 + dst·(1-1) = color` | `FillRect(color)` | ✅ **恒等** |
| 4 个角 | 由掩码给出 `c ∈ (0,1]` | `out = color·c + dst·(1-c)` | 同（无快路径） | — |

**关键**：直边处的覆盖度**恒为 1（不是「近似 1」）**，因此对实心带用不透明 `FillRect` 与走覆盖度混合路径**结果逐位相同**。这不是性能折衷，是数学等价。

**副作用说明**：`a == 1` 路径由现状的 **1 次 `RoundRect`** 变为 **7 次绘制原语 + 2 次资源操作**（`3 FillRect + 4 AlphaBlend`；建刷/释放各 1 次）。这是 D11 要求实测的性能代价（§11 R-1）。

**性能不达标时的处理（v1.1 修订——评审 §十一）**：

⚠️ **本阶段不预设第二条实现方案。** 「3 带 + 4 角补丁」与「全矩形 DIB」哪个更快，取决于圆角大小、窗口尺寸、CPU、GDI driver、AlphaBlend 实现与 DIB 填充成本——**在实测数据出来之前把它写成正式降级预案属于过度设计**，且会诱发详设阶段重新展开「方案 A/B/C」的架构讨论。

因此正式表述为：

```text
语义：覆盖度必须统一（本节已证）
实现：当前定为 3 条带 + 4 个角补丁（§2.1 已定案）
性能：§8.4 实测 —— 若不可接受，则【回到本文档修订】再改实现，
      不允许在详设/实现阶段静默切换方案
```

这与 §7 B10（小半径不做阈值降级）是**同一条纪律**：实现路径的变更必须留下设计文档的修订痕迹。

### 2.3 D3 定案：超采样 S = 8（并纠正需求阶段的成本隐含假设）

**需求 v1.1 写「倾向 4×」，并注明「只生成一次、缓存后不进每帧热路径」。本初设指出：这个理由本身排除了「为省成本而选低倍率」的动机。**

- 掩码**按半径缓存、一次性生成**（需求 D4）→ 生成成本 **O(S²·R²) 只付一次**，与帧率无关
- 因此倍率选择应只看**量化质量**，不看生成成本
- 量化质量：`S×S` 子样本 → `S²+1` 个覆盖度级别

| S（倍率） | 样本/像素 | 覆盖度级别 | 相邻级别 alpha 步进 |
|---|---|---|---|
| 4（4×） | 16 | **17** | ≈ 15/255 ≈ **5.9%**（大半径下可能可见「阶梯」） |
| **8（8×）** | **64** | **65** | ≈ 4/255 ≈ **1.6%** |
| 16（16×） | 256 | 257（饱和 8-bit） | ≈ 1/255 ≈ 0.4% |

**结论：默认 S = 8。** 理由：4× 的 17 级量化步进约 5.9%，**在大半径（R ≥ 16，弧横跨数十像素）下预计会暴露出量化台阶**；8× 的步进约 1.6%，**预计能显著降低该台阶**。

⚠️ **v1.1 措辞修订（评审 §四）**：v1.0 写「8× 已低于视觉阈值」——这是**把经验判断写成了工程事实**。最终视觉质量不只由量化步进决定，还与圆弧半径/曲率、像素位置、相邻像素的覆盖度分布、AlphaBlend 后的颜色差异、显示器与缩放比例有关。因此正式表述为：

> 8× 在当前目标 UI 尺寸范围内**预计**能显著降低 4× 的量化台阶；**最终是否采用 8× 由 §8.3 V2 的目视对比确认**。

16× 的生成成本同样一次性可接受，作为 V2 的对照候选保留。

**S 是实现参数，不是契约**（与 D3「生成器可替换」一致）——日后若视觉实测发现 8× 仍有台阶，改为 16× 或换 Analytic，**上层零改动**。

**Analytic（解析覆盖度）作为可替换升级记录在案**：圆—矩形交集面积有闭式解，**每像素 O(1)**（对比 S=8 的每像素 64 次采样），既精确又更快——但需要推导并验证面积函数。**L1-a 面积守恒正是它的安全网**（公式写错会被直接测出）。本阶段不实现，仅记录路径。

## 3. `CornerCoverageMask` 离散几何定义（本阶段的核心规格）

> 需求 v1.1 只写了「缓存对象 = 单象限覆盖度掩码」；本节把**离散坐标模型定死**（需求评审 §六 点名要求）。

### 3.1 定义（以左上角为例）

```text
坐标系：掩码局部整数像素网格
    i = 列（0 .. R-1，向右）
    j = 行（0 .. R-1，向下）

掩码像素 (i,j) 对应方格：[i, i+1) × [j, j+1)      ← 单位像素面积（见下方离散模型声明）
圆心：掩码局部坐标 (R, R)                          ← 象限的内侧顶点（掩码右下角）
子样本：(i + (sx + 0.5) / S,  j + (sy + 0.5) / S)      sx, sy ∈ [0, S)
判定：  dx = px - R;  dy = py - R;   inside = (dx*dx + dy*dy <= R*R)
覆盖度：c[i][j] = round(255 * insideCount / (S * S))
```

**⚠️ 离散模型声明（v1.1 新增——评审 §三，本定义的核心）**：本掩码采用 **pixel-square coverage** 模型，**不是**「像素中心是否在圆内」的二值判定：

> **每个掩码像素 `(i, j)` 代表单位像素方格 `[i, i+1) × [j, j+1)`；`coverage` 定义为该方格与圆盘相交的面积占该方格面积的比例，用 `S×S` 个子样本估计。**

这条声明使整条链路闭合（**单位口径在此显式切换，L1-a 的公式据此而定——见 §8.1**）：

```text
连续几何（半径 R 的四分之一圆盘）
     ↓  与像素方格求交
方格内的圆盘面积          ← 单位：像素面积（pixel-area）
     ↓  S×S 子样本估计（面积占比，无量纲）
归一化覆盖度 c ∈ [0, 1]   ← 几何覆盖度
     ↓  round(c · 255)
uint8_t 字节存储 c_byte ∈ [0, 255]   ← 存储域
```

⚠️ **必须与既有代码的模型区分**：现状 `BlendAlphaSolid` 用的是 `(dx²+dy²) <= R²` 的**像素中心二值判定**（`cx = col + 0.5f`），即「像素中心是否落在圆内」模型。两者在小半径下结果**不同**——例如 `R = 1`：方格模型给出 `π/4 ≈ 0.785`（该 1×1 方格只有约 78.5% 落在圆盘内），而中心判定给出「中心距圆心 0.707 < 1 → 全覆盖 1.0」。**本阶段采用方格模型**（它是「面积正确」的模型，也是 L1-a 面积守恒能成立的前提）。

**规格要点（逐条写死，避免详设再产生二义）**：

| # | 项 | 取值 | 理由 |
|---|---|---|---|
| 1 | **掩码尺寸** | **`R × R`**（不是 `(R+1)×(R+1)`） | 圆角弧的两个端点相对角原点为 `(0,R)` 与 `(R,0)`，象限包围盒恰为 `R×R` 像素——尺寸精确，无过覆盖/欠覆盖 |
| 2 | **圆心位置** | `(R, R)` | 即象限内侧顶点；所有样本的 `dx,dy ≤ 0`，只用到圆的第三象限 |
| 3 | **像素方格** | `[i, i+1) × [j, j+1)`（边长 1、面积 1） | **方格模型**（见上方声明）——coverage 是面积占比，不是中心点判定 |
| 4 | **采样** | `S×S` 规则网格，子样本中心 `(sx+0.5)/S` | 规则网格可预测、无 RNG 抖动 → 结果确定（测试可复现） |
| 5 | **边界判定** | `<= R*R`（**含**圆周） | `R` 为整数 → `R*R` 精确无浮点误差；`<=` 与 `<` 对面积测度无影响，但**必须写死**以保证确定性 |
| 6 | **存储** | `std::vector<uint8_t>`，`stride = R`（行连续、无对齐填充），长度 `R*R` | 最小够用；`R` 是整数故无需 padding（不对齐优化的 YAGNI） |
| 7 | **取值域** | `0 <= c_byte <= 255`；几何覆盖度 `c = c_byte / 255 ∈ [0,1]` | 单通道覆盖度（**两个域都要在文档中明确标注**，见 §8.1 单位口径） |
| 8 | **方向复用** | **只存 1 份 canonical 象限掩码**；四个角共享它，通过 **x/y 索引变换**映射到各自位置（右上 = 列索引反转 / 左下 = 行索引反转 / 右下 = 双轴反转） | 四角几何相同（§3.2），生成 4 份是纯冗余；详设落成 `maskIndexX(...)` / `maskIndexY(...)` 一类的索引辅助 |

### 3.2 为什么四角可复用同一掩码

圆角矩形的四个角、真圆的四个象限、ProgressBar 胶囊的两端——**它们的内切弧都是半径 R 的四分之一圆盘**。

**表述修订（v1.1——评审 §十三）**：不要把「镜像」当作几何层的核心概念，而是：

> **四个角共享同一份 canonical 四分之一圆盘掩码；通过 x/y **索引变换**映射到各个角。**

这样详设可以直接落地成索引辅助函数（`maskIndexX(...)` / `maskIndexY(...)`），实现者不必在脑子里维持「旋转/镜像」的几何想象。几何上「四象限互为镜像」是**这条索引变换之所以成立的原因**，而不是实现手段本身。

### 3.3 前提与失效边界

- **前提**：`R` 为整数、矩形边缘整数对齐。这一前提由现有实现保证（`DrawRoundedRect` 内部 `lround`，需求 §1.3 已论证）。
- **失效边界**：若 Phase 8 R4「渲染坐标浮点化」落地，矩形边缘与圆心将带亚像素偏移 → 掩码必须携带亚像素偏移量（键从 `R` 变为 `(R, 偏移)`）。**本阶段不做**（需求 D10），但掩码的键设计为该扩展留位（§6.1）。
- **`R = 0`**：不生成掩码、不进入 AA 路径（§5.1）。

### 3.4 已知离散化事实（L1 容差的前提）

- **`R = 1`**：掩码 1×1。**几何覆盖度**连续解 = `π/4 ≈ 0.7854`（对应字节域 `255·π/4 ≈ 200`）；方格模型的采样实现给出 `k/S²`（字节 `round(255·k/S²)`，S=8 时约 199~203），偏差计入 L1-a 容差——**不写死为 200**。
- ⚠️ **单位口径（v1.1 修正——评审 §二）**：`0.7854` 是**几何覆盖度（无量纲）**，`200` 是**字节域存储值**——两者不可混用于同一条公式。L1-a 的公式必须选定一个域（§8.1 选定归一化域）。
- 小半径（`R = 1, 2`）离散化误差相对最大 → L1 用例必须覆盖（§8.1）。

### 3.5 canonical 几何原则（v1.1 新增——评审 §八 / 必改项 4）

```text
AA 关闭 → legacy 路径（GDI RoundRect / BlendAlphaSolid）→ 与改造前逐位一致
AA 开启 → 本阶段定义的 canonical 整数像素几何（3 带 + 4 角补丁）
```

**原则（正式写入）**：

> **Phase 8.6 的 canonical rounded geometry 是本阶段自定义的整数像素几何，不要求与 Win32 `RoundRect()` 的内部栅格化算法逐像素一致。**

**为什么必须显式声明**：两者虽然都表示「半径 R 的圆角矩形」，但 GDI `RoundRect` 的坐标边界语义、椭圆包围盒解释、inclusive/exclusive 像素归属、以及 radius 与 width/height 的关系都可能有 ±1 像素的差异。若把「AA 开启后与旧 `RoundRect` 完全一致」写成期望，就会产生一个**无法满足的契约**。

**两条独立的断言口径**（不要混为一谈）：

| 断言 | 含义 | 可满足性 |
|---|---|---|
| `(AA 关)` 与 `(改造前)` **逐位一致** | legacy 路径零回归 | ✅ 必然成立（legacy 代码原样保留） |
| `(AA 开)` 与 `(AA 关)` 存在差异 | AA 确实生效 | ✅ 必然成立（角部覆盖度不同） |
| ~~`(AA 开)` 与 `(AA 关)` **逐位一致**~~ | — | ❌ **不是契约**（§3.5 原则） |

对应到 §8.2 的用例：**L2-c 只对 `R == 0` 断言逐位一致**（此时 AA 路径根本不启用，两条路径同为 legacy）；`R > 0` 时只断言「存在差异」与「存在过渡像素」（L2-a / L2-b）。

## 4. 形状装配（第二层）规格

### 4.1 装配公式

```text
输入：整数对齐的矩形 (x, y, w, h) + 钳制后的整数半径 R（0 <= R <= min(w,h)/2）

三条实心带（覆盖度恒为 1）：
    B_mid = Rect{ x,     y + R,     w,      h - 2R }
    B_top = Rect{ x + R, y,         w - 2R, R      }
    B_bot = Rect{ x + R, y + h - R, w - 2R, R      }
    （宽 <= 0 或高 <= 0 → 跳过该带）

四个角补丁（覆盖度取自掩码，方向见 §3.1 #8）：
    C_tl = 位置 (x,         y        )  方向：原样
    C_tr = 位置 (x + w - R, y        )  方向：列反转
    C_bl = 位置 (x,         y + h - R)  方向：行反转
    C_br = 位置 (x + w - R, y + h - R)  方向：双向反转
```

### 4.2 覆盖完备性与无重叠证明

| 命题 | 论证 |
|---|---|
| **带尺寸非负** | `R <= min(w,h)/2` ⇒ `2R <= w` 且 `2R <= h` ⇒ `w-2R >= 0`、`h-2R >= 0` |
| **角补丁互不重叠** | 列区间 `[x, x+R)` 与 `[x+w-R, x+w)`：因 `w >= 2R` ⇒ `x+R <= x+w-R` ⇒ 不重叠；行区间同理 |
| **带与角不重叠** | `B_top` 的列区间是 `[x+R, x+w-R)`，与两侧角补丁的列区间不相交；行区间 `[y, y+R)` 与角的行区间一致但列不相交 |
| **无空洞** | 带覆盖「十字」区域，角补丁覆盖四角 —— 并集 = 全矩形；且各块的覆盖度与「距最近弧的几何关系」一致（带内恒 1、角内由掩码给出） |

### 4.3 退化情形（全部由「跳过零尺寸带」自然处理，无专门分支）

| 形状 | 条件 | 装配结果 |
|---|---|---|
| 普通圆角矩形 | `w > 2R` 且 `h > 2R` | 3 带 + 4 角 ✓ |
| **ProgressBar 胶囊** | `w > 2R`、`h == 2R` | `B_mid` 零高 → 跳过；`B_top`/`B_bot` 存在（`w-2R > 0`）；上下两组角补丁分别合成上下两个半圆端 ✓ |
| **ProgressBar 胶囊（另一向）** | `w == 2R`、`h > 2R` | `B_top`/`B_bot` 零宽 → 跳过；`B_mid` 存在；左右两组角补丁分别合成左右两个半圆端 ✓ |
| **Radio 真圆** | `w == h == 2R` | 三条带全部零尺寸 → 只剩 4 个角补丁；因 `w == 2R` ⇒ 圆心全部落于 `(x+R, y+R)` ⇒ 四象限拼成**完整圆** ✓ |

> **这是本初设的一个关键结论**：需求 D8 担心的「`2r >= min(w,h)` 退化需专门分支」**被现有钳制消除了**。A 方案对普通圆角矩形 / 胶囊 / 真圆**同一套代码、无分支**——正好覆盖需求评审 §四点名的三组核心几何用例。

## 5. 合成路径分解

### 5.1 路径选择

```cpp
void GDIBackend::DrawRoundedRect(const Rect& rect, float cornerRadius, const Color& color)
{
    if (rect.width <= 0.0f || rect.height <= 0.0f) return;                       // 既有守卫（不变）

    const LONG w = ...; const LONG h = ...;
    const LONG R = std::clamp(std::lround(cornerRadius), 0L, (std::min)(w, h) / 2);   // 既有钳制（不变）

    if (R == 0 || !m_antiAliasing) {
        DrawRoundedRectLegacy(rect, R, color);        // ← 现状行为原样保留（R4 零回归 + D6 开关）
        return;
    }

    const CornerCoverageMask& mask = m_cornerMaskCache.Get(static_cast<int>(R));   // R2 / §6.1

    if (color.a >= 1.0f) {
        DrawRoundedRectOpaqueAA(rect, R, color, mask);      // §5.2 —— 3 FillRect + 4 角补丁
    } else {
        DrawRoundedRectBlendedAA(rect, R, color, mask);     // §5.3 —— 全矩形 DIB + 1 次 AlphaBlend
    }
}
```

**`DrawRoundedRectLegacy`** = 现状的 `a==1`（`RoundRect`）/ `a<1`（`BlendAlphaSolid`）两条分支**原样搬入**，逻辑零改动。这样：
- `R == 0` → 与改造前逐位一致（R4）
- `AA 关` → 与改造前逐位一致（D6，供 L2 对照）

### 5.2 `a == 1` 路径（新增）

```text
① 1 次 CreateSolidBrush(color)                    ← 一个刷服务三条带（避免 3 次建销）
② FillRect(B_mid) / FillRect(B_top) / FillRect(B_bot)   ← 尺寸 <= 0 则跳过
③ 对 4 个角，依次：
     a. 在 ScratchDIB（R×R）内按方向填充着色补丁：
            A  = c[i][j]                 （color.a == 1）
            B  = color.b * c / 255       （预乘，约束 1）
            G  = color.g * c / 255
            R  = color.r * c / 255
     b. AlphaBlend(目标 DC, 该角位置, 源 = ScratchDIB, 尺寸 R×R)
④ 释放刷
```

- **预乘合规**：`B/G/R` 已乘 alpha，符合 9.5 约束 1（该约束由需求 D1 声明继续有效并被复用）
- **ScratchDIB 复用**：同一个小缓冲串行服务 4 个角（§6.2）
- **调用计数（v1.1 修正——评审 §七 必改项 5）**：v1.0 写「`1 + 3 + 4 = 12` 次内部调用（其中 7 次为 GDI 原语：1 建刷 + 3 FillRect + 4 AlphaBlend）」——**自相矛盾**：`1+3+4 = 8`，且把「建刷」这个资源操作计进了绘制原语。按 §2.1 的三层口径重新表述：

| 层 | 内容 | 次数 |
|---|---|---|
| 高层几何绘制 | 3 条实心带 + 4 个角补丁 | **7** |
| **GDI 绘制原语** | `FillRect` × 3 + `AlphaBlend` × 4 | **7** |
| **GDI 资源操作** | `CreateSolidBrush` × 1 + `DeleteObject` × 1 | **2** |
| （ScratchDIB） | 复用，**无每调用分配** | 0 |

→ 合计 GDI API 调用 **9 次**（对比现状的 1 次 `RoundRect`）。

> ⚠️ **关于建刷是否该进热路径（评审 §七 末段）**：现状惯例是「GDI 对象每次创建/销毁」（决策 24，避免 10,000 句柄上限；字体是唯一例外）。本设计**沿用该惯例**——1 次建刷服务 3 条带，比现状 `DrawRect` 每次建销更省。**是否引入 color→HBRUSH 缓存归详设决定**（§11.2 待定项 10），倾向**不引入**（与既有惯例一致 + YAGNI）。

### 5.3 `a < 1` 路径（在既有实现上做最小改动）

**保留现状结构**：整张 `w×h` 32bpp 顶降预乘 DIB → 逐像素填充 → **1 次** AlphaBlend。只把角部的判定从二值改为覆盖度：

| 部位 | 现状（v1.0 前） | 本阶段 |
|---|---|---|
| 带内像素 | `(B,G,R,A) = (b·a, g·a, r·a, a)` | **不变** |
| 角内像素 | `inside` 二值 → 全色 或 全透明 | **`A = a·c`，`B/G/R = b·a·c`（等）** |

- **性能**：DIB 尺寸与调用次数**与现状完全相同** → **零回归**
- **实现代价**：约 5 行改动（把 `inside` 的 bool 换成 `c` 并乘进 alpha 分量）

### 5.4 三路对照

| 路径 | 触发条件 | 覆盖度是否应用 | 相对现状的性能 |
|---|---|---|---|
| legacy | `R == 0` 或 AA 关闭 | 否（不需要——直角/无 AA） | **零变化** |
| `a == 1` + AA | `R > 0` 且 AA 开 | ✅ | 1 次 `RoundRect` → **7 绘制原语 + 2 资源操作**（**待实测**，§11 R-1） |
| `a < 1` + AA | `R > 0` 且 AA 开 | ✅ | **零变化** |

> **D11 的兑现**：凡 `R > 0` 且 AA 开启，覆盖度一律应用（无「有/无 AA 并存」）；两条 AA 路径的差异**仅在 GDI 原语选择**，且 `a == 1` 的带状快路径已给出等价性证明（§2.2）。

## 6. 缓存与 ScratchDIB 规格

### 6.1 `CornerMaskCache`（几何数据缓存）

```cpp
class CornerMaskCache {
public:
    /// @param radius 整数半径（> 0）；重复请求同一 radius 直接命中
    const CornerCoverageMask& Get(int radius);

    /// @param samples 超采样倍率 S（默认 8，见 §2.3）
    void SetSamples(int samples);

    std::size_t Size() const noexcept;   ///< 条目数（测试/诊断用）

private:
    std::map<int, CornerCoverageMask> m_masks;   ///< 键 = 整数 radius
    int m_samples = 8;
};
```

| 项 | 规格 |
|---|---|
| **缓存对象** | `CornerCoverageMask`（单象限，§3） |
| **键** | **effective 整数半径 `R`**（`lround` **且** `clamp` 之后——见下方「键的规范化」） |
| **失效** | **永不主动失效**；后端析构时随成员销毁（需求 D4） |
| **生命周期** | 随 `GDIBackend`（跨帧复用） |
| **增长控制** | **本阶段不设淘汰策略**；详设确定一个**轻量条目数诊断阈值**（超出预期记 Debug）——见下方「关于条目数上界」 |
| **未来扩展位** | 若 R4 浮点化落地，键扩为 `(R, 亚像素偏移)`；**本阶段不做**（D10），但键类型选择（`std::map` 而非数组）已为多字段键留位 |

**键的规范化（v1.1 新增——评审 §五 必改项 3）**：v1.0 写「现有实现已 `lround` → 天然整数，无需额外离散化」——**这个说法不够严谨**。缓存的键不应是「调用者传入的 radius」，而是**规范化后的 effective 半径**：

```text
调用者传入的 logical radius（float）
        ↓  DrawRoundedRect 内的 GDI 像素几何量化
effective integer radius  R = clamp(lround(callerRadius), 0, min(w, h) / 2)
        ↓
cache key = R
```

**为什么必须取规范化后的值**：`3.1 / 3.2 / 3.3` 三个入参在当前量化下对应**同一个几何对象**（`R = 3`）。若键取原始 float，会出现「同一几何被重复生成多份」的浪费，且缓存条目数的统计将失去意义（同一几何被计成多条）。

**关于「条目数上界」（v1.1 修订——评审 §六）**：v1.0 写「半径取值是离散小集合 → 条目数上界极小」——这对**当前 Widget/Theme 的实际用法**成立，但 **`GDIBackend` 面对的是 `float radius` 参数，理论上未来可能出现大量不同半径**，因此「天然不会很多」**不是一个真正的上界证明**。

本阶段的处理（**不引入 LRU 等复杂淘汰**——那会违背 YAGNI）：

> 当前实现不设复杂淘汰策略；缓存键为 effective 整数半径。考虑到当前 Widget/Theme 的半径集合有限，预计条目数很小。**详设阶段确定一个轻量的条目数上限或诊断阈值**，避免异常调用导致缓存无限增长。

（v1.0 已有的「超出预期值记 Debug」正是这个方向，v1.1 把它从附注**提升为正式规格**。）

**为什么放 Internal 头而非 GDIBackend 私有**：`CornerMaskCache` 与 `GenerateCornerMask` 是**纯几何、零 GDI** 的（不碰 HDC/HBITMAP）→ 可被 L1 层直接单测（R7）；且与 `GDIBackend`（GDI 实现）职责正交。

### 6.2 `ScratchDIB`（绘制工作缓冲）

| 项 | 规格 |
|---|---|
| **用途** | **仅服务 `a == 1` 路径的角补丁**（`R×R`）；`a < 1` 路径沿用其全矩形 DIB（§5.3，零改动） |
| **复用方式** | 单个实例，串行服务 4 个角（同尺寸、同格式，只换内容与方向） |
| **格式** | 32bpp 顶降（负 `biHeight`）预乘 BGRA —— 与 §5.2/§8.3 既有链路一致 |
| **扩容策略** | `required > current` → 重建；**只增不减**，**不设增长倍率** |
| **理由（只增不减）** | GUI 后端生命周期内半径集合小且稳定（主题常量 + 少量动态值），反复缩放无意义（需求评审 §八 ①） |
| **重入声明** | ⚠️ **仅用于同步、顺序的 `GDIBackend` 绘制流程；不保证并发/重入安全**——当前 Renderer 顺序执行，未来若引入并行绘制必须重新设计（需求评审 §八 ②） |
| **归属** | `GDIBackend` 私有成员 |

## 8. 测试方向

> 分层依据：需求 D9（L1 = 算法层零窗口依赖 / L2 = 后端合成层真窗口）。**用例表归详设细化，本节给方向与断言形式。**

### 8.1 L1 · `CornerCoverageMask` 数学测试（新建，无窗口）

| 用例 | 断言 | 备注 |
|---|---|---|
| L1-a **面积守恒** | `abs( Σ(c[i][j] / 255.0) − πR²/4 ) <= tol(S, R)`（**归一化域**——见下方单位口径） | **测试对象 = `GenerateCornerMask(R)` 的掩码，不是 `DrawRoundedRect`**（需求 D9 明确） |
| L1-b 值域 | 所有像素 `0 <= c_byte <= 255`；几何覆盖度 `c = c_byte / 255 ∈ [0,1]` | — |
| L1-c 存在部分覆盖 | 存在 `0 < c_byte < 255` 的像素 | 硬边掩码只有 0/255 → 此条必失败（AA 生效的判据） |
| L1-d 单调性 | **机械规则**（见下方 L1-d 规则） | 不用「沿外法向」这种需要解释的表述 |
| L1-e 方向对称 | 经 x/y 索引变换读取的结果与按对应方向手工读取的结果一致 | 验证 §3.1 #8 的 canonical 掩码 + 索引变换 |
| L1-f 边界判定确定性 | 同参数两次调用结果完全相同 | 规则网格采样 → 无 RNG |
| L1-g 缓存命中 | 同 **effective R** 二次请求返回**同一对象地址**（或条目数不增） | `CornerMaskCache` 行为 |

**L1-a 的单位口径（v1.1 修正——评审 §二 必改项 1）**：

v1.0 写 `abs(Σcoverage − πR²/4) <= tol(S,R)` —— **单位错误**：`coverage` 的存储域是 `0~255`（字节），而 `πR²/4` 的单位是**像素面积**，两边量纲不一致。（v1.0 自己在 §3.4 写「`255·π/4 ≈ 200`」时用的是字节域，恰好暴露了这个不一致。）

**修正为归一化域（本文档采用）**：

```text
abs( Σ(c[i][j] / 255.0) − πR²/4 ) <= tol(S, R)
      ↑ 归一化后 = 几何覆盖度之和，单位 = 像素面积（与右侧同域）
```

**等价的字节域写法（供实现者参考，二选一）**：

```text
abs( Σc_byte[i][j] − 255 · πR²/4 ) <= 255 · tol(S, R)
```

**选归一化域的理由**：`c ∈ [0,1]` 才是**真正的几何覆盖度**，字节只是**存储编码**（§3.1 的链路图已把两者显式分层）。让几何层与编码层的概念分离，公式的可读性与可审性都更好。

**L1-d 的机械规则（v1.1 新增——评审 §九）**：「沿外法向单调不增」是数学表述，**测试代码无法直接实现**（离散格点上「外法向」需要额外解释）。落成可直接编码的规则：

```text
圆心位于掩码局部坐标 (R, R)（即象限右下角）：

对每一行 j：固定 j，c(i, j) 随 i 减小而【非递增】
              （i 越小 = 越远离圆心 = 覆盖度不应变大）

对每一列 i：固定 i，c(i, j) 随 j 减小而【非递增】
```

即「从圆心向左、向上扫描时覆盖度单调不增」。**两轴分别验证，不做对角线方向判定**——后者在离散格点上无明确定义。

**半径覆盖**：`R = 1, 2, 3, 4, 8, 16`（含小半径——离散化误差高危区，§3.4）。

**容差推导（`tol(S, R)`）**：

> **容差单位与 L1-a 左侧同域（像素面积）**——故 tol 与 `R` 同比增长，而不是固定常数。

```text
误差来源 = 每个边界像素的覆盖度量化误差，上限 ≈ 1/S
边界像素数 ≈ O(R)
=> tol(S, R) ≈ R / S        （保守估计，单位 = 像素面积）

校验（S = 8）：
    R = 1  → tol = 0.125 ；连续解 π/4 ≈ 0.785 → 相对 16%（小半径相对误差天然偏大，绝对误差极小）
    R = 32 → tol = 4.0   ；面积 ≈ 804 → 相对 0.5%
```

- **容差必须随 S 变化**（需求 D9 明确）——测试用例应对 `S = 8` 与 `S = 16` 分别取 `tol`，防止「写死一个大容差掩盖量化缺陷」
- **详设可按实测收紧**（本文档给的是保守上界）

### 8.2 L2 · `GDIBackend` 集成测试（新建，真窗口）

复用 `RendererTests.cpp::TestGDIBackendAlphaBlend` 的「真窗口 + `GetPixel` 像素读回」模式。

⚠️ **既有坑（原测试已注释）**：该模式要求窗口在**屏幕内**——屏幕外窗口的 DC 裁剪区为空，`GetPixel` 恒返 `CLR_INVALID`。沿用「屏幕右下角 + `SW_SHOWNOACTIVATE`」的既有做法。

| 用例 | 断言 |
|---|---|
| L2-a AA 开 / 关差异 | 同几何、同颜色下，开/关两帧像素**存在差异**（证明 AA 确实生效） |
| L2-b 过渡像素存在 | 角部存在 `0 < alpha < 255` 的像素 |
| L2-c **`R == 0` 零回归** | `(AA 关, R=0)` 与 `(AA 开, R=0)` **逐像素一致** —— **不引入 Golden Image / 基准截图**（需求 D9） |
| L2-d 预乘正确性 | 半透明圆角（`a = 0.5`）叠加已知底色 → 期望混合值 ±3 容差（沿用既有 AlphaBlend 测试的期望值算法） |

> **L2-d 的 ±3 验证的是什么（v1.1 补充——评审 §十）**：必须注明它验证的是 **`coverage × color.a → 预乘 BGRA → AlphaBlend` 这条合成链路**，**不是 coverage 掩码的精度**。否则后来者看到 `±3` 会误以为「coverage 误差 ≤ 3/255」——两者不是一回事。
>
> **层次划分**：`coverage 几何正确性` → L1（§8.1）；`coverage × color.a 的预乘合成正确性` → L2-d。
| L2-e 三形状合成 | 普通圆角矩形 / 胶囊 / 真圆三种几何各渲染一次 → 中心与四角像素符合预期（覆盖 §4.3 退化） |

## 11. 待定项与风险（归详设）

### 11.1 风险

| ID | 风险 | 等级 | 应对 |
|---|---|---|---|
| R-1 | **`a == 1` 由 1 次 `RoundRect` 变 7 绘制原语 + 2 资源操作** → 性能回归（尤其 `R` 小时补丁只有几像素，blit 开销 > 计算开销） | **中高** | §8.4 实测；**不预设第二条实现方案**——若结果不可接受，**回到本文档修订**再改（§2.2） |
| R-2 | **小半径（`R = 1, 2`）**：AA 视觉收益可忽略但固定成本（4 次 blit）存在 | 中 | **本设计不做阈值降级**（B10）以保语义一致；若实测为瓶颈，**回到本文档修订后再改** |
| R-3 | 覆盖度量化台阶（`S = 8` → 65 级）在大半径下可见 | 低 | 升 `S = 16`（一次性生成，成本可接受）；或切 Analytic（§2.3） |

### 11.2 待定项（详设定稿）

1. `ScratchDIB` 的封装形态——独立小类 vs `GDIBackend` 私有成员 + 辅助函数（倾向后者，YAGNI）
2. 角补丁的**方向变换实现**——索引反向读取 vs 预生成 4 份（倾向索引反向，省 3/4 内存；详设比较实现复杂度）

## 12. 实现顺序

1. **`CornerCoverageMask.h/.cpp`**（纯几何，先做——L1 可立即独立验证）
