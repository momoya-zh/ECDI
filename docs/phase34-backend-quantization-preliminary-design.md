### △1 `src/Render/GDIBackend.cpp`（唯一生产代码改动文件）

#### △1-a 引入取整助手（文件内匿名 namespace）

**新增**（约 12 行，紧跟 `BackendContract.h` 的 include 之后）：

```cpp
/// @brief **普通矩形边界量化**的唯一实现（★ v1.8 收窄——评审第九轮 P2）
/// @details 契约 = `BackendContract.h:77-81`。**普通矩形**的 `Rect → RECT` 一律走它，
///          ★★ **适用范围与选择规则（v1.9 明确——评审第十轮 P2-2）**：① **只需要边界**的消费者 ⇒ 调 `ToPixelRect(rect)`；② **同时需要边界与宽高**的消费者 ⇒ **只调 `ToPixelBox(rect)`**，边界取 `box.left/top`，右边/下边由 `box.left + box.width` / `box.top + box.height` **导出**；③ ★★ **同一消费者不得同时声明 `RECT bbox = ToPixelRect(...)` 与 `PixelBox box = ToPixelBox(...)`**——`ToPixelBox` 内部已复用 `ToPixelRect`，再单独调一次会产生**两份量化结果来源**，正是本阶段要消灭的形态；④ 带特殊几何变换者（焦点框外扩）**先用本函数取基础边界、再套常量**，**不得**绕开本函数直接对 `Rect` 调 `QuantizeEdge`。
///          ★ 为什么不做成成员：`BlendAlphaSolid` 等在匿名 namespace（自由函数），
///          且它无状态 ⇒ 自由函数最省（不引入新抽象，条 22）。
inline RECT ToPixelRect(const Rect& rect) noexcept
{
    const int left   = QuantizeEdge(rect.x);
    const int top    = QuantizeEdge(rect.y);
    const int right  = QuantizeEdge(rect.x + rect.width);
    const int bottom = QuantizeEdge(rect.y + rect.height);
    RECT rc{};
    rc.left   = static_cast<LONG>(left);
    rc.top    = static_cast<LONG>(top);
    rc.right  = static_cast<LONG>(right);
    rc.bottom = static_cast<LONG>(bottom);
    return rc;
}

/// @brief 同上，但返回**量化后的尺寸**（给「需要 (w,h) 而不是 (right,bottom)」的消费者）
/// @details ★★ 存在的理由（本阶段最容易被写错的一处）：`BlendAlphaSolid` 需要
///          `CreateDIBSection` 的 `biWidth/biHeight`，那是**尺寸**不是边。
///          若继续用 `lround(rect.width)`，则 DIB 宽度与放置位置 `QuantizeEdge(rect.x)`
///          仍会各自取整 ⇒ `left + width ≠ right`，相邻块漏缝/压边。
///          ⇒ **尺寸必须由量化后的两条边相减**得出，这是契约原文的直译。
struct PixelBox
{
	LONG left;          ///< 量化后的**左边界**（= `QuantizeEdge(rect.x)`）
	LONG top;           ///< 量化后的**上边界**（= `QuantizeEdge(rect.y)`）
	int  width;         ///< ★★ **由右边界与左边界相减导出**，**不是**对 `rect.width` 取整
	int  height;        ///< ★★ 同上（下边界 − 上边界）
};

/// @par 前置条件（v1.8 结构重写——评审第九轮 P3）
/// ★★ **本节曾出现「列了五组约束、结论却写『以上四类』」的自相矛盾**，
///    且 ④/⑤ 与 ③ 内部两条**重复**。v1.8 起改为**三类 + 逐项**结构：
///    **A 类：浮点域**（输入与中间和的有限性）
///    **B 类：整数域**（每处实际整数运算的可表示性）
///    **C 类：责任归属**（不满足时由谁保证）
///
///    **A · 浮点域**
///      A1. 输入 `rect.x/y/width/height` **有限**；
///      A2. ★ **中间和有限**：`rect.x + rect.width` 与 `rect.y + rect.height` 也须有限。
///          （★ 两个有限浮点数相加**仍可溢出到 `±inf`**；此时**不满足本前置条件**。
///          ⚠️ 失败点**不是** `floor`——`std::floor(±inf)` 仍得 `±inf`——而是
///          **随后把不可表示于 `int` 的浮点值转成整数**，该转换不受本契约支持）
///
///    **B · 整数域**（★ 每一处**实际发生的**整数运算各占一条，不得合并）
///      B1. `QuantizeEdge` 返回 **`int`**（`BackendContract.h:90`）⇒ `floor` 后的值须可表示于 `int`；
///      B2. `PixelBox::left/top` 是 **`LONG`**——★ 在本项目支持的 Windows ABI 上
///          `int` 与 `LONG` **同为 32 位有符号**，故 `int` 的值域均可由 `LONG` 表示；
///          ⚠️ 这是**平台相关事实**（`LONG` 在别的 ABI 可能 64 位），**不是普遍类型规则**，
///          不得据此推断可移植性；
///      B3. ★ **差值**：`PixelBox::width/height` 取自 `rc.right - rc.left`——
///          该减法**先在 `LONG` 上做**（`RECT` 成员为 `LONG`），**再窄化到 `int`** ⇒
///          须保证**差值本身**在 `int` 范围内（两端各自在 `int` 内**不代表**差值在）；
///      B4. ★ **`DrawFocusRect` bbox 版**（v1.9 按目标代码对齐——评审 P2-3）：
///          目标代码是 `const RECT base = ToPixelRect(rect);` 再 `base.left - 2` 等，
///          ⇒ 该加减**按 `LONG` 的运算规则进行**（`RECT` 成员是 `LONG`），**不是 `int`**；
///          须保证 `base.left/top - 2`、`base.right/bottom + 2` 的结果**可表示于 `LONG`**。
///          ⚠️ 在本项目目标 Windows ABI 上 `LONG` 与 `int` **值域相同**（均 32 位有符号），但**运算类型与数值范围是两回事**——不得用后者替代前者；
///      B5. ★ **`DrawFocusRect` float 版**的 `- 1`（两处）：
///          `fRight = QuantizeEdge(rect.x + rect.width) - 1`、
///          `fBottom = QuantizeEdge(rect.y + rect.height) - 1`；
///          等价表述：**执行 `- 1` 之前的量化结果必须 > `INT_MIN`**。
///          ★★ **为什么不写「不得下溢」**：实测（`t34_intmin.cpp`）当量化结果为 `INT_MIN`
///          （`-2147483648`）时，`q - 1` **回绕成 `2147483647`**（数学真值 `-2147483649` 不可表示）
///          ⇒ 回绕后反而「大于 `INT_MIN`」，**会骗过朴素的溢出检查**；
///          ⇒ 判据必须是**数学可表示性**（量化结果 > `INT_MIN` 且减一后仍在 `int` 内），
///          **不是**「检查算完的值有没有变小」；
///      B6. T34-3b 的 `gRight - fRight == 1` **以 B1–B5 全部成立为前提**——否则该断言无意义。
///
///    **C · 责任归属**
///      C1. **本阶段不新增运行时钳制**（沿条 22 YAGNI / 条 95⑤）；
///      C2. 由**既有上游契约**保证：`Rect` 经 `Renderer::ScaleRect` 与布局链产出，
///          量级受 `Win32PlatformWindow` 的 `GetClientRect` 路径约束；
///      C3. ⚠️ **如实登记**：C2 是**结构性约束、非运行时断言** ⇒ 记为**设计假设**，
///          不是「已证明的保证」；若日后出现无窗口 / 离屏路径（`roadmap #44` 的 M-1），
///          **须重新评估本整节**，而不是默认其继续成立。

inline PixelBox ToPixelBox(const Rect& rect) noexcept
{
	const RECT rc = ToPixelRect(rect);   // ★ v1.1：**复用**同一条边计算，不重复实现（评审 P2-4）
	return PixelBox{ rc.left, rc.top,
	                 static_cast<int>(rc.right - rc.left),    // ★ 相减，不是取整
	                 static_cast<int>(rc.bottom - rc.top) };
}
```

★ **为什么不复用 `ToPixelRect` 再算宽高**：`rc.right - rc.left` 也正确，但会让读者以为「宽高是 `RECT` 的副产品」；单独的类型让「**尺寸 = 边相减**」这条契约在**类型层面**可见（教学型框架，条 95③：理由与结论同等重要）。

#### △1-d `DrawFocusRect` 的 `±2 / +4` 常量语义（职责确认 §4.6 已核，此处落规格）

**现状**：`:1321-1322` = `static_cast<LONG>(rect.x) - 2`；`:1323-1324` = `bbox.left + static_cast<LONG>(rect.width) + 4`。

**语义**（已核）：焦点框在控件**四周各外扩 2 设备像素**。

**目标式**（★ 顺序不可换）：

```cpp
const RECT base = ToPixelRect(rect);          // ★ v1.8：先走统一入口（评审 P2 方案 B）
const int left   = base.left   - 2;
const int top    = base.top    - 2;
const int right  = base.right  + 2;
const int bottom = base.bottom + 2;
```

★★ **v1.8 改为「先走统一入口、再套常量」（第九轮 P2 方案 B）**——并在改动前**实测过**：对 17×17 = **289 组** `x/width` 样本（含负分数、正分数、整数）逐值比较「直接 `QuantizeEdge` 分量后 `±2`」与「先 `ToPixelRect` 再 `±2`」，**differing = 0**（`verify_focus_equiv.py`）。★★★ **该结论的适用范围（v1.9 收窄——评审第十轮 P2-1）**：它证明的是「**把直接量化调用提取成统一助手，前后结果逐值一致**」——即**助手提取是等价重构**。**它不能证明新方案与当前生产代码的旧表达式等价**：两侧都是 `QuantizeEdge` 新口径，而**旧 vs 新**的差异恰恰是本阶段要产生的（见 **T34-3a**：分数输入下新旧左右边界都会变）。⇒ **禁止把本结论表述为「不改变任何像素输出」**——那超出了实验覆盖。旧新差异一律由 **T34-3a / A7** 按 §4.6 三类归因审查。

★ **为什么坚持统一入口**：若允许焦点框绕开 `ToPixelRect` 直接对 `Rect` 调 `QuantizeEdge`，**同一个 `Rect` 就被两套代码各自量化一次**——今天它们恰好等价，但日后改 `ToPixelRect` 的规则时，焦点框会**静默地不跟随**，而这类偏差不会让任何测试失败。


★ **为什么不能写 `QuantizeEdge(rect.x - 2)`**：`-2/+2` 是**设备像素**语义（与外扩像素数有关，与 DIP 无关）。先减后量化 ⇒ 在分数 DPI 下 `rect.x - 2` 的 frac 被 floor 吸收或进位，外扩量变成 1 或 3 px。
★ **为什么 `+4` 变 `+2`**：原式是 `bbbox.left`（= `x - 2`）**再** `+ 4` ⇒ 净效应 `x + 2`。等价改写为「右边 + 2」后，`+4` 自然消失。★ **这是等价变换，不是改语义**——须在用例里用原式对照验证（见 §5 T34-3）。


#### △1-d2 ★★ `DrawFocusRect` **float 版**（`:1204-1215`）——与 bbox 版是**两套独立语义**（v1.1 新增，评审 P1-3）

★★ **最容易被误套的地方**：本函数有**四个**取整结果，语义各不相同，**不能一律当「外扩」处理**：

| 变量 | 表达式 | 语义 | 本阶段处置 |
|---|---|---|---|

1. **`-1` 与焦点框的 `±2` 外扩无关**——前者是**开区间换算**（所有手绘线段都要做，`:1202` 的注释已明写），后者是**控件外扩装饰**。混为一谈会把焦点框整体缩进 1px。
