## 1. 动机

### 1.1 一句话

**框架早已在契约上声明「公共 API 语义恒为 DIP」，但因为进程未声明 DPI 感知、`dpi` 恒 96，这条契约从未被检验过**——本阶段的任务是**让它真正生效**，而不是引入一个新概念。

### 1.2 现状勘察（K1–K12，全部带行号实测）

| # | 事实 | 证据 |
|---|---|---|

### 1.3 为什么现状「看起来能工作」

**K5 是全部原因**：进程未声明感知 ⇒ **系统对整个窗口做 DPI 虚拟化** ⇒ 框架看到的一切（客户区尺寸、鼠标坐标、`GetDeviceCaps` 返回值）都落在系统 DPI 空间的**逻辑像素**上 ⇒ `dpi` 恒 96 ⇒ K2 的公式**恒等** ⇒ 「公共 API = DIP」这条契约**恰好与事实重合**。

⇒ **结论**：现状不是「正确」，是「**两条错误互相抵消**」。三条已知症状都由此而来：

| 症状 | 来源 | 证据 |
|---|---|---|
| **跨屏后矩形 ×0.8**（420×280 → 336×224） | 跨 DPI 空间的坐标换算；已排除 `GetDpiForWindow`（全程 96）/ `WM_DPICHANGED`（未收到）/ 感知级别（=1）⇒ `0.8 = 96/120` 逐位吻合 | `desktopnest-roadmap.md:253`（Phase 16 spike §7.1） |
| **`WM_NCHITTEST` 委托与 widget 几何错位** | K6（Phase 13 实测） | 同上 |
| **无法查询真实 DPI / 屏幕信息** | K12 ⇒ 应用**想自己适配也拿不到数据** | 同上 |

## 2. 目标与非目标

### 2.1 目标（本阶段要达成的）

| # | 目标 |
|---|---|
| **G1** | **进程 DPI 感知**：从「隐式 unaware」升到 **Per-Monitor V2** |
| **G2** | ★ **让既有 DIP 契约真正生效**：公共 API 的尺寸 / 坐标语义**恒为 DIP**，换算**只发生在平台边界**（把 K1 的「换算点唯一」原则从 NCHITTEST 扩展到全部边界） |
| **G3** | **跨屏一致性**：窗口移到另一 DPI 的显示器后，尺寸 / 内容 / 命中全部正确（含 `WM_DPICHANGED`） |
| **G4** | **补查询能力**：面向应用的**屏幕 / DPI 查询 API**（K12 的空缺） |
| **G5** | ★ **100% DPI 下逐位等价**：`dpi == 96 ⇒ px == dip`（K2 公式已保证）⇒ **既有测试与视觉零回归** |

### 2.2 非目标（明确不做）

| # | 非目标 | 理由 |
|---|---|---|
| **N1** | **不做 DPI 无关的「矢量字体缩放」** | `Font::size` 语义变成 DIP 后，字体仍由 GDI 按物理高度栅格化；本阶段不改渲染管线 |
| **N2** | **不做主题 / 布局的 DPI 自适应策略**（如「小屏自动紧凑」） | 那是响应式设计，不是 DPI 感知 |
| **N3** | **不做非 Windows 平台的 DPI 抽象** | 与 #44 后端可替换性解耦；X11/Android 各自的缩放模型不同，届时另议 |
| **N4** | **不重构 `ScrollBar` / `TextBox` 的坐标计算** | 它们拿的是框架坐标（已 DIP），**只要边界换算正确，它们不用改** |
| **N5** | 不做**每屏独立缩放系数**的用户可配（如「某屏设 110%」） | 系统级能力，跟随系统 |

## 3. 技术路线

### 3.1 三条候选

| 路线 | 内容 | 代价 | 判定 |
|---|---|---|---|
| **A** | **保持 unaware**，只补查询 API | 小 | ❌ **否**——unaware 下查询到的也是虚拟化值（K5），解决不了 K6/跨屏；且 `roadmap` 已把目标定为 V2 |
| **B** | ★ **声明 Per-Monitor V2 + 让既有 DIP 契约生效**（G2 贯通全部平台边界） | **中～大**（触面广，见 §4） | ✅ **倾向**——与 K1 既有契约同向，且 G5 提供零回归护栏 |
| **C** | 声明 V2 但**只在 chrome 生效**（DIP 语义不向外扩） | 小 | ❌ **否**——会让「公共 API = DIP」的契约**变成半真**（chrome 是 DIP、窗口尺寸不是），比现状更糟 |

### 3.2 ★ 一个必须先说清的连锁关系（决定分批方式）

**V2 一旦声明，系统停止虚拟化 ⇒ 坐标变物理像素。** 此时若不同时把「窗口尺寸的 DIP 语义」补上：

- `Application::Create(title, 800, 600)` 的 `800` 会被当作**物理像素**直接交给 `CreateWindowEx` ⇒ **150% 屏上窗口视觉缩小 1/3**（`800 DIP` 应变 `1200 px`）；
- 同理**字体**（K9）在 150% 屏上会变小 1/3（`14 px` 应为 `21 px`）。

⇒ **「声明感知」与「DIP 语义贯通」不能分两批做**——单独声明感知是一个**纯破坏性**变更。这两件事**必须在同一批内完成**。

## 4. 触面清单（G2 的实际工作量）

| 面 | 现状（K#） | V2 后需要 | 方向 |
|---|---|---|---|
| **窗口创建尺寸** | 直传 `CreateWindowEx`（隐式逻辑） | **DIP → 物理** | 入 |
| **chrome**（caption / resizeInset） | ✅ 已 DIP（K1/K4） | DPI 来源换成 `GetDpiForWindow`（K3 预留点） | 已就位 |
| **鼠标事件坐标** | 透传（K7） | **物理 → DIP** | 出 |
| **窗口尺寸**（★ **3 个入口**，见 K13） | 三处**均直取物理量** | **物理 → DIP**——① 构造期 `GetClientSize` → `RootWidget::SetSize` ② `OnResized`（**布局几何源头**）③ `WindowResizedEvent` | 出 |
| **`WM_NCHITTEST` 委托** | ★ **错位**（K6） | 统一到 DIP 后**自动闭合 L6** | 出 |
| **字体实例化** | 按像素（K9） | **DIP → 物理**（且**字体缓存 key 必须含 DPI**——否则跨屏复用错字体） | 入 |
| **文本测量** | GDI 像素（K10） | 与 `Font` 语义**同源** | 定 |
| **IME 双通道** | 框架坐标（K11） | **DIP → 物理** | 入 |
| **渲染后端**（`GDIBackend` 的 DIB / `GetClientRect`） | 物理 | ✅ **不需变**（后端本来就工作在最终像素） | — |
| **公共 API 缺口** | 无查询（K12） | **新增屏幕 / DPI 查询** | 新 |

★ **一句可判的总结**：**公共 API 与框架内部（Widget / 布局 / 事件）= DIP；平台边界 = 物理；渲染后端 = 物理。** 换算**只在边界的两个方向发生**。

### 4.1 ★ 双空间共存：同一个 `GetClientRect`，两处要求两种单位（v1.1 新增）

`GetClientRect` 在**平台侧**与**渲染后端侧**各被调用一次，V2 之后**只有一处需要换算**：

| 调用处 | 它要的语义 | 处理后 |
|---|---|---|
| `Win32PlatformWindow::GetClientSize`（`:266-270`）→ 框架（K13 ①） | **框架层客户区尺寸 = DIP** | **必须 `PixelsToDip`** |
| `GDIBackend`（DIB / 绘制目标 / `GetClientRect`） | **渲染目标 = 物理像素** | ✅ **原样不动** |

⇒ ★ **同一个 Win32 API 产出物理值，但只有一处该转换**——**实现时不得把它们合并成一个"尺寸访问器"**，否则必然有一侧单位错。

**可判判据**：`Window` / `Widget` / `Layout` / 事件里见到的尺寸与坐标**恒为 DIP**；`Renderer` / `RenderingBackend` 里见到的**恒为物理像素**；两者在**平台边界**这一条线上互换。★ 这条判据同时是 G2 与 R3 的操作化表述。

## 5. 决策点（D0–D8）

| # | 问题 | 倾向 |
|---|---|---|
| **D0** | **分几批做？** | **一批**：感知声明与 DIP 贯通**必须同时**（§3.2）；但**测试与收口**可分步 |
| **D1** | **换算的唯一入口怎么保证？** | 把 K2 的 `DipToPixels` **泛化**为平台侧一对工具（`DipToPixels` / `PixelsToDip`），并**规定所有边界调用它**——沿用 K1 的「换算点唯一」原则 |
| **D2** | **DPI 来源** | **`GetDpiForWindow`**（per-window）——与 K1/K3 既有理由一致（「跟随窗口比跟随鼠标更一致」） |
| **D3** | **`WM_DPICHANGED` 怎么处理？** | 采纳系统建议矩形（`lParam` 是 `RECT*`）+ 触发重布局 + **清字体缓存** |
| **D4** | **`Font::size` 的语义** | 从「**像素高度**」改为「**DIP 高度**」（K8）——★ **数值不变**，故 100% 下逐位等价（G5）；但这是**公共语义变更**，须写进文档与头注释 |
| **D5** | **文本测量返回 DIP 还是物理？** | ★ **留给初步设计**（见 Q2：DIP ⇒ 浮点误差 vs 物理 ⇒ 布局混合） |
| **D6** | **`WindowResizedEvent` 报什么？** | **DIP**（与公共 API 一致） |
| **D7** | **感知声明放在哪？**（框架是静态库，manifest 得由应用提供） | **两案并存**：① 提供 manifest 片段 / CMake 注入供应用使用 ② `Application::Create` 早期运行时调用 `SetProcessDpiAwarenessContext`（**必须在任何窗口创建前**）。★ **取舍留给初步设计**（Q3） |
| **D8** | **查询 API 的形状** | 候选：`Window` 上的 `GetDpiScale()`（float，窗口级）+ 独立的应用级屏幕查询。★ **形状留给初步设计**（Q4） |

## 8. 留给初步设计的问题（Q1–Q6）

| # | 问题 |
|---|---|
| **Q1** | **DIP 语义的边界画在哪**：`Application::Create(title, w, h)` 之后，`Widget::SetSize` / `Layout` 的参数是否也一律 DIP？（倾向：**是**——但需确认无「物理量」混入，例如 DIB 尺寸） |
| **Q2** | ★ **文本测量的单位**：返回 DIP（浮点，会有累积误差）还是物理（整数，但布局须混合单位）？**这是本阶段最实际的取舍** |
| **Q3** | **感知声明的落点**：manifest（应用侧 / CMake 注入）vs 运行时 API（框架侧）——**两者是否都要**？若走运行时，`Application::Create` 是否是最早的可靠时机？ |
| **Q4** | **查询 API 的形状**：窗口级 `GetDpiScale()` 够不够？要不要屏幕枚举（多显示器信息）？命名如何避免与 `Viewport` 撞概念。★ **YAGNI 护栏（评审第一轮）**：先确定**真实使用场景**再定形状——不得因「既然做 DPI 了」就一次塞入 `EnumerateAllMonitors` / `GetMonitorWorkArea` / `GetMonitorName` 等；**DPI API 极易膨胀成整个 Display 子系统** |
| **Q5** | **`WM_NCHITTEST` 的换算方向**：该消息给的是**物理像素**，而 K1 说「换算点唯一在此」——**A：入参换成 DIP 再比对**（`:372-374` 求出窗口坐标后立刻 `PixelsToDip`，`caption` / `inset` / `w` / `h` 全留在 DIP）**vs B：把 widget 几何换成物理再比对**。两者对 L6 的闭合效果相同，**但影响该函数的契约表述**（K1 注释须改写）。★ **倾向 A**——★ **判据不是「符合 R3」**（B **同样**发生在平台边界内，R3 区分不了二者），而是：**`HitTest` 的入参语义必须恒为 DIP**（既有坐标语义不变量：`HitTest` 加回父偏移、与会话级「鼠标事件坐标为 DIP」同向）——选 B 会让 `HitTest` 在某次调用里收**物理坐标**，**同一个函数出现两种单位**。★ **连带**：走 A 后 `DipToPixels` 在 NCHITTEST 的 2 个调用点（K4）**消失**（改用 `PixelsToDip` 转 x/y），K1 的「换算点唯一」**仍成立但方向反转** |
| **Q6** | **测试如何伪造 DPI**：换算函数可注入 DPI；但**平台层的事件翻译**（`WindowMessageHandler`）怎么在无头测试里注入非 96 的 DPI？沿用 Phase 19 的 `FakeHost` 路径是否足够。★ **判据（评审第一轮）**：**DPI 来源必须与坐标转换解耦**——若翻译器内部直接 `GetDpiForWindow(hwnd)`，则 `Handle(nullptr, nullptr, msg, ...)`（`EventTests.cpp:259` 既有形态，**hwnd = nullptr**）**无从伪造 DPI**。不要求引入 DPI provider 抽象，但至少做到：**① 纯换算独立可测** + **② 翻译器持有可设置的 DPI 成员**（平台层在翻译前写入），**两条路都要验** |
