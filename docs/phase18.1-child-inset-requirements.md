## 1. 背景与现状勘察

### 1.1 现象（Phase 18 A6 目视实测）

A6 把「窗口四周留白」放回 root 一级（`VerticalLayout(0, true, 12)` + `SetBackgroundColor(#222934)`），实测结果：**功能达标、视觉否决**。两条症状相互独立，**只有第二条是本阶段的目标**：

| # | 症状 | 处置 |
|---|---|---|
| **S1** | 留白让出的 12px 显示的是**窗口底色** `#222934`，与页面底色 `#0f1115` 不同 ⇒ 深色窗口上像套了一圈描边 | ✅ **已就地收口**（2026-09-22）：`main.cpp:315` 底色改为与页面同值（视觉无痕；能力**照走** `Window::SetBackgroundColor → Renderer::BeginFrame → GDIBackend` 清屏链路，只是不再显形） |
| **S2** | `CaptionBar` 与 `page` **同属 root 布局的子** ⇒ **标题栏被一起内缩 12px** | 🚧 **本阶段要解决的就是它**。A6 的临时处置 = 把留白下沉到 page 一级（`ModelProbe.cpp:155`） |

**S2 的本质不是"参数没调对"**，而是**留白的归属问题**：留白开在**父**（`Layout::padding` 对全部子一律作用）还是开在**子**（子自己缩进、chrome 不受影响）。

### 1.3 一条会定形态的事实（F-1）

**「让出的窟窿开在谁身上」决定了看不看得见窗口底色**：

- 留白开在 **root**（父）⇒ 窟窿落在 **root 内部**，而 root 不绘制（K10）⇒ **露窗口底色** ✅ **但 chrome 被一起拖下水**（K1 的必然结果）；
- 留白开在 **page**（子）⇒ 窟窿落在 **page 内部**，而 page 自己画背景（`#0f1115`）⇒ **看不见窗口底色** ❌ **但 chrome 贴边** ✅。

⇒ 这两个结果**不是同一件事的两个参数**，而是**两个不同的几何拥有者**。**Phase 18 解掉了「露出来的是不是白的」，没有解掉 S2 的连带。**

### 1.4 本阶段要回答的唯一问题

> **「窗口级留白」能否只作用于内容、不作用于 chrome？**

- "能，且值得做成框架能力" ⇒ **路线 A**（§2.1）
- "用现有积木在应用侧拼" ⇒ **路线 C**（§2.3，零框架改动）
- "不重要" ⇒ **路线 D**（§2.4，不开）

## 2. 技术路线对照（含倾向）

### 2.1 路线 A —— 子节点内缩（Child inset）〔**倾向**〕

**能力**：`Widget::SetInset(int)`（默认 0、非负、单值）——语义为「**本控件在其父布局槽位内，四边再内缩的像素数**」。由**布局在放置子节点时消费**。

**用法（ModelProbe 目标形态）**：

```cpp
root.SetLayout(std::make_unique<ECDI::VerticalLayout>(0, true));   // 父不留白 ⇒ chrome 不受影响
page->SetInset(12);                                                 // 内容自缩 ⇒ 四周留白
win.SetBackgroundColor(ECDI::Color::FromRGBA8(34, 41, 52));         // 留白处露窗口底色 ⇒ Phase 18 能力首次"看得见"
```

**三条诉求为何能同时成立**：`CaptionBar` 槽位 = 全宽贴顶（`inset = 0`）⇒ ① 标题栏贴边；`page` 槽位内缩 12 ⇒ ② 内容四周留白；那 12px 属于 **root 区域**，root 不绘制（K10）⇒ ③ **露窗口底色**。

**代价**：`Widget.h` +2 方法 +1 成员（**非虚 ⇒ 零破坏**）；`Layout.h` +1 **非虚 helper**（**唯一消费点**，未来新布局自动继承）；V/H 两个 `.cpp` 的放置点改走 helper；测试 +N。**公共头 92 → 92**。

**风险**：**低**——`inset = 0` 时**逐位退化**（布局根本不读该值 ⇒ 与现状同一条代码路径），这条可作为硬契约测试。

### 2.2 路线 B —— 布局级"豁免"（父侧名单 / 子侧标志）

**能力**：子节点声明「**不吃父 `padding`**」（或父维护豁免名单）。代码更少，但语义更窄。

**为什么不倾向**：复杂度**全花在定义"部分豁免"的边界**上——豁免子该不该推进主轴游标？序列两端（第一个 / 最后一个）的 `padding` 怎么算？豁免与 `stretch` / `fillCrossAxis` 如何组合？而收益只有"chrome 贴边"**一个 case**，且把**特例**写进通用布局。**倾向否决**：A 的语义更正交（`inset` 是**几何**，豁免是**策略**），且 A 顺带解开"同一父下不同子不同留白"这个普适缺口。

### 2.3 路线 C —— 应用侧零改动组装（**可立即验证**）

**做法**：root 不留白；在 `CaptionBar` 与 page 之间插一层**透明 `Panel`**（K6：默认透明 = 官方语义「隐形布局容器」），由它承接 `padding` 与内层布局：

```cpp
root.SetLayout(std::make_unique<ECDI::VerticalLayout>(0, true));                 // [CaptionBar, contentPanel]
contentPanel->SetStretch(1);
contentPanel->SetLayout(std::make_unique<ECDI::VerticalLayout>(10, true, 12));   // 唯一子 = page
```

**视觉与路线 A 完全一致**（同样露窗口底色：`contentPanel` 透明 ⇒ 其 `padding` 让出的 12px 落在 root 区域 ⇒ 露窗口底色）。**框架改动 0 · 公共 API +0 · 测试 +0 · 只动 `main.cpp`（须单独授权）**。

**⚠️ 一条历史理由需要重估**：Phase 17 曾把"应用侧包裹容器"判为**方案 A 备选**并**选择了框架侧（方案 B）**，理由是「此后每个想留白的 demo 都要重复这套」。但当时该备选的代价包含**为包裹容器 override `SetSize` 同步几何**；这一代价**已因 9.7（布局系统落地）+ Phase 15（坐标不变量）而消失**（现在是**纯组装、零 override**）⇒ 那条理由的**权重须重新评估**（`roadmap-deferred.md` #38 备注中的判断依据已部分失效）。

**倾向**：**作为"先验证"路径**——若目视达标且接受"每个窗口包一层"，则本阶段的必要性大幅下降，可按 **YAGNI 降级为记账**（把 A / B 的结论留档备将来）。

### 2.4 路线 D —— 不做

现状（K9）已满足「标题栏贴边 + 内容四周留白」；缺的只是「**留白处露窗口底色**」这**一条视觉**。若该条不是真实需求 ⇒ **本阶段整段可关闭**。

## 3. 需求条目（**以路线 A 为前提**；若评审选 C，§3–§6 作废，仅保留路线 C 的调用点改动）

### 3.1 能力 · R1–R3

| # | 需求 | 说明 |
|---|---|---|
| **R1** | **子节点级内缩（单值）** | 布局放置子节点时，把**槽位矩形**四边各内缩 `inset` px，作为该子的最终几何 |
| **R2** | **默认 0 = 逐位退化** | `inset = 0` 时布局路径与现状**逐位相同**（根本不读该值）——既有 231 用例零回归的**结构保证** |
| **R3** | **消费点唯一** | 消费逻辑只写在 `Layout` 基类的**一个非虚 helper**，V/H 两实现**只调用**它 ⇒ 未来新布局**自动继承**（避免"每个布局各写一遍"） |

### 3.2 语义与边界 · R4–R7

| # | 需求 | 说明 |
|---|---|---|
| **R4** | **不参与空间分配** | `inset` **不进** `remaining` / `cross` / 主轴游标计算——它是"在**已分配槽位**里再缩"，**不是**"向父要更多空间" |
| **R5** | **与父 `padding` 正交可叠加** | 最终内缩 = `padding` + `inset`（两者不互相覆盖、不互相取消） |
| **R6** | **非负** | 沿用 `padding` / `spacing` 同款纪律：`FRAMEWORK_ASSERT(inset >= 0)` + Release 钳 0。**不做负值**——负值 = 外扩 ⇒ 与相邻子重叠、侵占父预留空间，语义危险，且"用负 inset 抵消父 padding"实质是路线 B 的伪装 |
| **R7** | **实例状态、不自动重排** | 与 `SetStretch` 同型（K3）：普通 setter，**由调用者 `Arrange()` 生效**；不引入隐式副作用链 |

### 3.3 消费验证 · R8

| # | 需求 | 说明 |
|---|---|---|
| **R8** | **ModelProbe 恢复 A6 目标形态** | root 留白归零 + `page->SetInset(12)` + 底色恢复**可辨识值** ⇒ 标题栏贴边 + 内容留白 + **底色可见**。⚠️ **`main.cpp` 须单独授权**（skill 条 2） |

## 4. 决策点（含倾向）

| # | 决策点 | 倾向 | 依据 |
|---|---|---|---|
| **D0** | **是否开本阶段 / 选哪条路线**（A / B / C / D） | **A**；**若 C 目视通过且接受样板 ⇒ D** | §1.4 · §2 |
| **D1** | 能力挂在**子节点**（A）还是**布局策略**（B） | **A（子节点）** | `inset` 是几何、`stretch` 是权重，均属**实例状态**（K3 同类先例） |
| **D2** | 形制：**单值 `int`** vs `Insets` 四边 | **单值** | 与 `padding` 同纪律；本需求的真实形态是**四边等宽**；四边独立属 YAGNI（无消费者） |
| **D3** | 允许**负值**（外扩）？ | **不允许** | R6 |
| **D4** | **主轴游标语义** | **按槽位推进**（游标累加用**槽位**尺寸，而非内缩后尺寸） | 保 R4「不参与分配」；否则 inset 会顺带改变**兄弟节点**的位置（典型失效：给中间子加 inset 把后面所有子顶上去） |
| **D5** | 命名（`SetInset` / `SetMargin` / `SetContentInset`） | 留初设 | 只需与既有 `padding` / `spacing` 术语体系**不撞名**、不产生"容器内边距"歧义 |
| **D6** | 提供 **setter** vs 构造参数注入 | **提供 setter** | Phase 17 的 F3 纪律（构造参数、不设 setter）**只针对 `Layout` 配置**；`inset` 是**控件实例状态**，同类先例 `SetStretch`（K3）。**此点须初设复核对齐** |

## 5. 非目标（N1–N6）

| # | 非目标 | 理由 |
|---|---|---|
| **N1** | 四边独立内缩（`Insets{left,top,right,bottom}`） | 无消费者（D2）；按"第二个真实消费者"驱动 |
| **N2** | 子节点级 `spacing` / 完整 margin 体系 | YAGNI；本阶段只解"**槽位内缩**" |
| **N3** | 把 `padding` 从 `Layout` 迁走 / 废除 | Phase 17 能力**保留、语义不变** |
| **N4** | "只缩某一轴"的开关 | 无消费者；单值四边同缩已够 |
| **N5** | `Window` / root 的"内容区 inset"新 API | 与 9.7 **D4 定案**（`Window` 不替用户决定 RootWidget 布局）冲突 |
| **N6** | 自动重排 / 自动重绘链 | R7 |

## 7. 留给初步设计的问题（Q1–Q6）

| # | 问题 |
|---|---|
| **Q1** | helper 的**精确签名与保形方式**：布局本来只在**三类分支**下 SetSize（stretch 主子 / fillCrossAxis 跨轴子 / 都不满足时不改尺寸，K1 的 `:51-61`）⇒ inset 如何在这三类下保形地应用？**这是唯一的实现难点** |
| **Q2** | D4 的**精确表述 + 用例设计**（"游标按槽位推进"必须用**含 inset 的多子序列**测死，否则与"按内缩后尺寸推进"无法区分） |
| **Q3** | 与 `SetSize` **虚分派**的交互（K8）：`CaptionBar` override 会在其内重排子控件 ⇒ 先缩再 `SetSize` 还是先 `SetSize` 再缩？ |
| **Q4** | 与 **AutoSize / `GetPreferredSize`** 的关系：inset 是否计入"首选尺寸"？（倾向：**不计入**——inset 描述的是父给槽位的内缩，与控件自身首选尺寸无关） |
| **Q5** | 与 **Phase 15 内容偏移**（`ScrollContent`）的关系：两者都改子几何，需确认无叠加歧义 |
| **Q6** | 新增用例的**文件落点**（`LayoutTests.cpp` 增量 vs 新建文件）+ `RunAllTests.h/.cpp` **手工登记两处** |
