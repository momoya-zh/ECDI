# Phase 20.1 · 渲染层 DPI 缩放（render DPI scaling）—— 需求确认（v1.0）

> 来源：**Phase 20 详设 §14「实施记录」的 R1**（2026-09-24 用户跨屏 / 125% 实测发现）+ 子阶段立项
> 状态：**v1.2**（2026-09-24）——✅ **评审通过**（外部评审结论：「**通过，可以进入 Preliminary Design**」，**零阻塞项**）；v1.1 按评审**逐条处置**（见 **§1.4**）；★ **v1.2 = 初设基线勘察的勘误两条**（见 **§9**）
> 定性：**Phase 20 的缺口补完**——**不是新能力**，而是让 Phase 20 已声明的分层（公共 API / 框架内部 = DIP · 渲染后端 = 物理）**在非 96 DPI 下真正成立**
> ★ **Phase 20 的收口依赖本子阶段**：不完成它，Phase 20 的 **A5（125% / 150% 视觉）**与 **A6（跨屏）**无法通过

---

## 1. 为什么需要这个子阶段

### 1.1 现象（用户实测，2026-09-24）

主屏改 **125%** 或窗口跨屏（150% 显示器）后：

> 「绘制变小了，但 **GUI 并没有变小**、**按键控制仍然在原位**、**窗口尺寸也没有变**」

⇒ **窗口尺寸正确、布局（DIP）正确、命中（DIP）正确——只有"进渲染层的那一步"少了换算**，于是几何按 DIP 数值画成物理像素（150% 下内容只占窗口左上约 2/3）。

### 1.2 根因：初设 §2.1 的两条规则**互相打架**

| 规则 | 原文 | 问题 |
|---|---|---|
| **规则 2** | 「`Renderer` / `RenderingBackend` 里见到的**恒为物理像素**」 | 要求几何进渲染层**前**已是物理 |
| **规则 3** | 「两者只在**平台边界**那一条线上互换（R3）」 | 而 `Renderer` / `RenderingBackend` **不在平台边界** ⇒ **这条转换没有任何落点** |

⇒ ★ **设计少写了一条「换算边」**：「**框架内部(DIP) → 渲染层(物理)**」。
本子阶段的**首要产出**就是为它补上落点，并**回填初设规则 3**。

### 1.3 证据（K1–K4）

| # | 事实 | 位置 |
|---|---|---|
| **K1** | `Renderer.cpp`（69 行）· `PaintContext.cpp`（84 行）—— **零 `Dpi` / `scale` 代码** | `src/Render/` |
| **K2** | `GDIBackend` 的绘制方法**直接把几何当像素**：`const LONG x = static_cast<LONG>(rect.x);` | `GDIBackend.cpp` |
| **K3** | 全库 `src/Render/` 的 DPI 代码**只出现在字体路径**（`GetOrCreateFont`） | Phase 20 批五（△20/△21） |
| **K4** | `RenderCommand` 的几何载体全是 **`float`**（`Rect` / `Point` 成员、`width`、`cornerRadius`） | `RenderCommand.h` · `Core/Rect.h` |

★ **后果**：批五已让**字体**按 DPI 换算（物理），而**几何**仍是 DIP ⇒ **两者尺度失调**——这正是"控件框与文字比例不对"的来源。

1. **新增约束 C-6**：`scale` 形参**必须带默认值 `1.0f`**——实测 `Renderer::Execute` 全库仅 **3 个调用点**（`Window.cpp:136` · `RendererTests.cpp:40` · `RendererTests.cpp:91`）、`Renderer::BeginFrame` 仅 **1 个**（`Window.cpp:135`）⇒ 带默认值则**既有调用点零改动**（不破坏 G2）；

3. ★ **运行时自动生效**：`scale` 每帧取自 `Window::GetDpiScale()` ⇒ 跨屏 `WM_DPICHANGED` 后**下一帧自动跟随**，**无需新增通路**（这也是不选"平台层算好再传"的理由之一）。

## 2. 目标与非目标

### 2.1 目标（G）

| # | 目标 | 判据 |
|---|---|---|
| **G1** | **非 96 DPI 下几何按 DPI 比例缩放** | 150% 下窗口物理 1020×1170 时，**内容充满窗口**（不再只占 2/3） |
| **G2** | ★ **100% DPI 下逐位零回归** | 既有 **247** 用例全绿 + 目视与改前一致（`scale == 1.0` ⇒ 折算恒等） |
| **G3** | **几何与字体尺度一致** | 控件框与文字的比例与 100% 下相同 |
| **G4** | ★ **换算落点唯一、可 grep 检** | 与详设契约 **C2** 同族的可检性（新落点亦须唯一） |

### 2.2 非目标（N）

| # | 不做 | 理由 |
|---|---|---|
| **N1** | 不改公共 API 的 DIP 语义 | Phase 20 **Q1** 已定案 |
| **N2** | **不改 `RenderCommand` 的数据结构**，**不改 `CommandBuffer` 的单位（仍 DIP）** | 四层两两不相识的定位不变 |
| **N3** | 不引入浮点几何 / 亚像素布局 | 框架几何语义不变（折算只发生在渲染层内部） |
| **N4** | 不做矢量字体 / 响应式布局 | Phase 20 **N1/N2** 已排除 |
| **N5** | 不重写 `GDIBackend` 的绘制算法 | 只在**入口**折算；`scale == 1` 时**输出逐位不变** |

## 3. 关键约束（来自既有契约）

| # | 约束 | 来源 | 影响 |
|---|---|---|---|
| **C-1** ★★ | **`DipToPixels` / `PixelsToDip` 只允许出现在 `src/Platform/Win32/`** | 详设 **契约 C2** | ⇒ **渲染层的折算不得调用这两个函数**。★ **理由（评审 §6 澄清）**：`DipToPixels(int,int)` 是**平台输入输出契约**（Win32 physical **int** ↔ DIP **int**），而渲染层需要 `DIP float × scale → physical float` ⇒ **两者不是同一个数学接口**。渲染层用 `scale = dpi / 96.0f` 的乘法 |
| **C-2** | `dpi == 96 ⇒ px == dip` | **G5**（Phase 20） | `scale == 1.0f` ⇒ 折算必须**恒等**（G2 的结构性依据） |
| **C-3** | 四层两两不相识 | 核心不变量 | 折算不得让 `Widget` 认识 DPI；`Widget` 几何恒 DIP |
| **C-4** ★ | **渲染几何是 `float`** | `RenderCommand.h` · `Core/Rect.h` | ⇒ **折算是 float 乘法，不适用 C10 的整数对称舍入**——C10 只服务平台层的 `int` 几何（窗口尺寸 / 鼠标坐标 / IME）。★ **补充（评审 §7）**：**不得在 `Renderer` 里提前 `round` / 截断**——量化是**绘图 API 的最后一步**（GDI 端），提前截断会重新引入量化误差 |
| **C-5** | 命令的**相对顺序有语义**（`PushClip` / `PopClip`） | `RenderCommand.h:66` | ★ **只改变几何数值**——**不改变命令顺序 / 类型 / 数量**（评审 §10 展开）；折算**逐条原地**，不得重排 / 合并 |
| **C-6** ★ 我方补 | **`scale` 形参必须带默认值 `1.0f`** | ★ **实测**：`Renderer::Execute` 全库 **3 个调用点** · `BeginFrame` **1 个** | ⇒ 带默认值 ⇒ **既有调用点零改动**（否则会破坏 **G2** 的「逐位零回归」） |

---

### 3.1 ★★ 单位不变式（本子阶段要冻结的链 —— 评审 §16）

```text
Widget / Layout / PaintContext
          │  DIP
          ↓
    RenderCommand                ← ★ 框架内部 DIP 语义的「最后一个载体」（评审 §3）
          │  DIP
          ↓
       Renderer
          │  ★ 唯一 render DPI scaling point（× scale）
          ↓
   physical geometry
          │
          ↓
  RenderingBackend               ← ★ 在此不再做任何 DIP→px 转换
          │
          ↓
      GDI / OpenGL / ...
```

| # | 不变式 | 可检方式 |
|---|---|---|
| **U1** | `PaintContext` 产出的 `RenderCommand` 几何 = **DIP** | 代码结构（`PaintContext` 零 DPI 代码） |
| **U2** | `Renderer` 的**输入**（`CommandBuffer`）= **DIP** | 同上 |
| **U3** ★ | `Renderer` **输出给 Backend** 的几何 = **物理像素** | 新落点唯一 ⇒ **grep 可检**（`scale` 只在一处参与几何） |
| **U4** | **Backend 不做 DIP→px 转换** | `GDIBackend` / `RecordingBackend` 均无 scale / Dpi 几何代码 |
| **U5** ★ | 后端（真 GDI / Recording）**看到同一单位** | 评审 §14：**不得让 `RecordingBackend` 悄悄承担缩放**——否则"测试通过而架构已坏" |

★ **本链的价值**：未来接入 `OpenGLBackend` 时**无需重新决定**「要不要乘 DPI」——架构已规定 **`Renderer` 已做**。

## 4. ★ 折算量清单（"哪些要折算"的完整答案）

| 命令 | 几何载体 | 需折算 |
|---|---|---|
| `DrawRectCommand` | `Rect rect` | ✅ |
| `DrawTextCommand` | `Point pos` | ✅ **仅位置**（★ 字号**不在**此处——它在后端按 DPI 换算 `lfHeight`，批五已做） |
| `DrawLineCommand` | `Point start` · `Point end` · `float width` | ✅ 三个 |
| `DrawRoundedRectCommand` | `Rect rect` · `float cornerRadius` | ✅ 两个 |
| `DrawImageCommand` | `Rect dest` | ✅ **目标矩形**（源图像像素**不变**） |
| `PushClipCommand` | `Rect rect` | ✅ |
| `PopClipCommand` | —（无几何） | ❌ |
| `DrawFocusRectCommand` | `Rect rect` · `float cornerRadius` | ✅ 两个 |

★ **`Font::size` 明确不在折算范围**：它在 `GDIBackend::GetOrCreateFont` 内按 DPI 换算（批五）。把 `pos` 折算为物理、字号亦为物理 ⇒ **两者一致**（正是 **G3**）。

★★ **这是最危险的回归点（评审 §9 特别提示）**：若本子阶段**也**对 `font.size` 乘 `scale` ⇒ **字体双重缩放**（批五已折过一次；GDI 端 `lfHeight` 再来一次）。
⇒ **责任边界必须保持**：**渲染几何 → 本子阶段** · **字体物理高度 → Phase 20 批五**。**初设与详设均须重复强调。**

|---|---|---|
| **Q1** ★★ | **换算落点**：`Renderer` 入口 / `GDIBackend` 逐方法入口 / GDI world transform | ★ **本稿倾向 = `Renderer` 入口**（评审的「方案 A」）。**否决理由（评审 §4）**：**方案 B**（后端逐方法）会把坐标转换规则**泄漏到每个平台后端**——未来 `OpenGLBackend` 还得重实现一遍；**方案 C**（GDI world transform）依赖 GDI、`AlphaBlend` 不受变换影响、且完全不可复用 ⇒ 否决。★★ **落点内部还须区分 A1 / A2（评审 §5，本稿原缺）**：**A1 = 修改 `CommandBuffer` 内的几何**（❌ **禁止**——会让「绘制描述」变成「执行后被物理化的命令」，多后端共用同一缓冲将**语义污染**）；**A2 = 执行期间瞬时转换，只把折算后的几何传给 Backend**（✅ **采纳**） |

| **Q4** | **折算的实现形态** | ★ **评审 §13 明确不建议 `Rect` / `Point` 的 `operator*(float)`**——会把「DIP → physical」降格为 Core 几何的**普通数学操作**，极易在 `Widget` / `Layout` 中被误用（那正是 Phase 20 极力避免的）；⇒ 用**具名 helper**（`ScaleRect` / `ScalePoint`）或**在 `Renderer` 的 visitor 内显式乘** |
| **Q5** | **与批五字体换算的配合**：是否有重复折算风险 | 现状：字号在后端换算 ⇒ 应保持**不重复**（折算只碰几何） |

| **Q7** ★ 我方补 | `PushClip` 的 **`float`** 矩形 vs 后端 `IntersectClipRect` 的**整数**口径 | 折算是 float 乘、后端必然取整 ⇒ 初设须确认「**裁剪边界与绘制边界是否可能差 1px**」（尤其与 AA 路径的一致性）；若确有此现象，须明确是**记为已知近似**还是**统一口径** |

1. **Phase 20 详设 §14 已把本项记为 R1**（实施记录中的缺口），本子阶段即其正式立项；
2. **完成后须回填**：初设 **§2.1 规则 3** 补"第二条换算边"；详设 **§14 的 R1 标 ✅**；
3. ★ **Phase 20 的 A5 / A6 验收依赖本子阶段**——本子阶段未收口前，Phase 20 不能标"全部验收通过"。

### 8.1 ★ 元教训（评审 §17，值得沉淀）

Phase 20 的原则是「**换算只发生在平台边界**」——本意是防止 DPI 泄漏进 Widget / Layout / Event，但它**漏考虑了**：

> `RenderCommand` ↔ `RenderingBackend` **之间也是一个单位边界**。

⇒ ★ **教训（可推广到后续所有设计）**：

> **不要只问「哪个模块知道平台」，还要问「哪个模块第一次要求物理单位」。**

因为 `Renderer` / `RenderingBackend` **都不是**传统意义上的 Platform 模块（目录也不叫 `Platform/`），
但 **Backend 的输入契约明确要求 physical px** ⇒ **真正的转换落点应由「单位契约」决定，而不由「目录名是不是 Platform」决定**。

★ 这条对后续 **Linux / X11 + OpenGL / Wayland** 的设计直接有用（届时同样要问「谁第一次要求物理单位」）。
