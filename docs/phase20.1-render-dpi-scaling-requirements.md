# Phase 20.1 · 渲染层 DPI 缩放（render DPI scaling）—— 需求确认（v1.0）

> 来源：**Phase 20 详设 §14「实施记录」的 R1**（2026-09-24 用户跨屏 / 125% 实测发现）+ 子阶段立项
> 状态：**v1.0**（2026-09-24）——**待评审**
> 定性：**Phase 20 的缺口补完**——**不是新能力**，而是让 Phase 20 已声明的分层（公共 API / 框架内部 = DIP · 渲染后端 = 物理）**在非 96 DPI 下真正成立**
> ★ **Phase 20 的收口依赖本子阶段**：不完成它，Phase 20 的 **A5（125% / 150% 视觉）**与 **A6（跨屏）**无法通过

---

## 1. 为什么需要这个子阶段

### 1.1 现象（用户实测，2026-09-24）

主屏改 **125%** 或窗口跨屏（150% 显示器）后：

> 「绘制变小了，但 **GUI 并没有变小**、**按键控制仍然在原位**、**窗口尺寸也没有变**」

⇒ **窗口尺寸正确、布局（DIP）正确、命中（DIP）正确——只有"进渲染层的那一步"少了换算**，于是几何按 DIP 数值画成物理像素（150% 下内容只占窗口左上约 2/3）。

### 1.2 根因：初设 §2.1 的两条规则**互相打架**

| 规则 | 原文 | 问题 |
|---|---|---|
| **规则 2** | 「`Renderer` / `RenderingBackend` 里见到的**恒为物理像素**」 | 要求几何进渲染层**前**已是物理 |
| **规则 3** | 「两者只在**平台边界**那一条线上互换（R3）」 | 而 `Renderer` / `RenderingBackend` **不在平台边界** ⇒ **这条转换没有任何落点** |

⇒ ★ **设计少写了一条「换算边」**：「**框架内部(DIP) → 渲染层(物理)**」。
本子阶段的**首要产出**就是为它补上落点，并**回填初设规则 3**。

### 1.3 证据（K1–K4）

| # | 事实 | 位置 |
|---|---|---|
| **K1** | `Renderer.cpp`（69 行）· `PaintContext.cpp`（84 行）—— **零 `Dpi` / `scale` 代码** | `src/Render/` |
| **K2** | `GDIBackend` 的绘制方法**直接把几何当像素**：`const LONG x = static_cast<LONG>(rect.x);` | `GDIBackend.cpp` |
| **K3** | 全库 `src/Render/` 的 DPI 代码**只出现在字体路径**（`GetOrCreateFont`） | Phase 20 批五（△20/△21） |
| **K4** | `RenderCommand` 的几何载体全是 **`float`**（`Rect` / `Point` 成员、`width`、`cornerRadius`） | `RenderCommand.h` · `Core/Rect.h` |

★ **后果**：批五已让**字体**按 DPI 换算（物理），而**几何**仍是 DIP ⇒ **两者尺度失调**——这正是"控件框与文字比例不对"的来源。

## 2. 目标与非目标

### 2.1 目标（G）

| # | 目标 | 判据 |
|---|---|---|
| **G1** | **非 96 DPI 下几何按 DPI 比例缩放** | 150% 下窗口物理 1020×1170 时，**内容充满窗口**（不再只占 2/3） |
| **G2** | ★ **100% DPI 下逐位零回归** | 既有 **247** 用例全绿 + 目视与改前一致（`scale == 1.0` ⇒ 折算恒等） |
| **G3** | **几何与字体尺度一致** | 控件框与文字的比例与 100% 下相同 |
| **G4** | ★ **换算落点唯一、可 grep 检** | 与详设契约 **C2** 同族的可检性（新落点亦须唯一） |

### 2.2 非目标（N）

| # | 不做 | 理由 |
|---|---|---|
| **N1** | 不改公共 API 的 DIP 语义 | Phase 20 **Q1** 已定案 |
| **N2** | **不改 `RenderCommand` 的数据结构**，**不改 `CommandBuffer` 的单位（仍 DIP）** | 四层两两不相识的定位不变 |
| **N3** | 不引入浮点几何 / 亚像素布局 | 框架几何语义不变（折算只发生在渲染层内部） |
| **N4** | 不做矢量字体 / 响应式布局 | Phase 20 **N1/N2** 已排除 |
| **N5** | 不重写 `GDIBackend` 的绘制算法 | 只在**入口**折算；`scale == 1` 时**输出逐位不变** |

## 3. 关键约束（来自既有契约）

| # | 约束 | 来源 | 影响 |
|---|---|---|---|
| **C-1** ★★ | **`DipToPixels` / `PixelsToDip` 只允许出现在 `src/Platform/Win32/`** | 详设 **契约 C2** | ⇒ **渲染层的折算不得调用这两个函数**；用 `scale = dpi / 96.0f` 的乘法，或另立中立件（须显式论证并同步修 C2） |
| **C-2** | `dpi == 96 ⇒ px == dip` | **G5**（Phase 20） | `scale == 1.0f` ⇒ 折算必须**恒等**（G2 的结构性依据） |
| **C-3** | 四层两两不相识 | 核心不变量 | 折算不得让 `Widget` 认识 DPI；`Widget` 几何恒 DIP |
| **C-4** ★ | **渲染几何是 `float`** | `RenderCommand.h` · `Core/Rect.h` | ⇒ **折算是 float 乘法，不适用 C10 的整数对称舍入**——C10 只服务平台层的 `int` 几何（窗口尺寸 / 鼠标坐标 / IME） |
| **C-5** | 命令的**相对顺序有语义**（`PushClip` / `PopClip`） | `RenderCommand.h:66` | 折算必须**逐条原地**，不得重排 / 合并 |

## 4. ★ 折算量清单（"哪些要折算"的完整答案）

| 命令 | 几何载体 | 需折算 |
|---|---|---|
| `DrawRectCommand` | `Rect rect` | ✅ |
| `DrawTextCommand` | `Point pos` | ✅ **仅位置**（★ 字号**不在**此处——它在后端按 DPI 换算 `lfHeight`，批五已做） |
| `DrawLineCommand` | `Point start` · `Point end` · `float width` | ✅ 三个 |
| `DrawRoundedRectCommand` | `Rect rect` · `float cornerRadius` | ✅ 两个 |
| `DrawImageCommand` | `Rect dest` | ✅ **目标矩形**（源图像像素**不变**） |
| `PushClipCommand` | `Rect rect` | ✅ |
| `PopClipCommand` | —（无几何） | ❌ |
| `DrawFocusRectCommand` | `Rect rect` · `float cornerRadius` | ✅ 两个 |

★ **`Font::size` 明确不在折算范围**：它在 `GDIBackend::GetOrCreateFont` 内按 DPI 换算（批五）。把 `pos` 折算为物理、字号亦为物理 ⇒ **两者一致**（正是 **G3**）。

## 5. 待决问题（★ 交给初步设计）

| # | 问题 | 备注 |
|---|---|---|
| **Q1** ★★ | **换算落点**：`Renderer::Execute` 入口 / `GDIBackend` 逐方法入口 / GDI world transform | 三方案取舍见 Phase 20 详设 §14；★ **本稿倾向 `Renderer` 入口**（最贴规则 2「Renderer 里见到的恒为物理」、改动面最小、可无头测） |
| **Q2** | **scale 的来源与注入形态**：`Window::GetDpiScale()`（Phase 20 已加）→ `Renderer`，形态取 `Execute(commands, scale)` / `Renderer` 持成员 / `BeginFrame(scale)` | `Window` 已知 DPI；`Renderer` 平台无关（只吃 `float`） |
| **Q3** ★ | **`Renderer` 是否允许"认识 scale"**——是否破坏「Renderer Widget-agnostic / 平台无关」？ | 需论证：只吃 `float`、不碰 Win32 ⇒ 平台无关不破；但它会从"纯转发"变为"携带一个变换参数" |
| **Q4** | **折算的实现形态**：逐字段乘 vs 引入 `Rect`/`Point` 的 `operator*(float)` | 前者显式但改动多；后者进 `Core` 层算子，可能被滥用 |
| **Q5** | **与批五字体换算的配合**：是否有重复折算风险 | 现状：字号在后端换算 ⇒ 应保持**不重复**（折算只碰几何） |
| **Q6** ★ | **测试如何覆盖**：既有 247（无头）如何扩展 | 若落点 = `Renderer` ⇒ 可用既有 `RecordingBackend` **完全无头**断言折算后的几何 ✓ |
