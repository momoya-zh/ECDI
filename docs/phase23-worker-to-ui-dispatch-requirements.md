# Phase 23 · 工作线程 → UI 线程投递（worker-to-UI dispatch）——需求确认（v1.1）

> 来源：`roadmap-deferred.md` **§7.9 待做区顺位 ④** = 审计 `framework-defect-audit.md` **§4 D-4** = `desktopnest-roadmap.md` **§5 G-3**。

### 1.3 现有窗口 / 生命周期边界

| # | 事实 | 证据 |
|---|---|---|
| **K11** | 公共 `PlatformWindow` 接口不暴露 Win32 类型；窗口级能力通过框架类型接缝提供，窗口对象组合平台窗口 | `include/ECDI/Platform/PlatformWindow.h:16-28` |
| **K12** | `Window` 可以取得抽象 `PlatformWindow`，但该入口提供的是 DPI、剪贴板、重绘等平台能力，不提供 HWND；应用层不应通过 HWND 自建投递机制 | `include/ECDI/Window/Window.h:93-105`；`include/ECDI/Platform/PlatformWindow.h:39-73` |
| **K13** | `Application::Create()` 返回窗口引用，但窗口释放会销毁底层 HWND；因此异步投递若携带窗口关联，必须处理「排队后窗口已销毁」的竞态，不能把裸 `Window*` 生命周期当作投递机制的保活手段 | `include/ECDI/Application/Application.h:62-71`；`include/ECDI/Window/Window.h:166-175`；`src/Application/Application.cpp:160-166` |
| **K14** | 框架已有「非拥有 sink 必须在宿主销毁前清空」的异步生命周期先例；G-3 必须沿用同一类边界，而不是让工作线程自行捕获已销毁的 `Application` | `include/ECDI/Platform/PlatformApplication.h:70-85`；`src/Application/Application.cpp:53` |
| **K15** ★ | 既有 `Application::Exit()` **不是跨线程退出入口**：它直接改写 `m_running` 并调用平台 `RequestExit()`；Win32 实现用 `PostQuitMessage(0)`，其消息归属是调用线程。因此 Phase 23 不把 `Run()` / `Exit()` 整体改造成线程安全 API；工作线程需要退出时，应先 `PostToUi([...] { Exit(); })` | `src/Application/Application.cpp:92-97`；`src/Platform/Win32/Win32PlatformApplication.cpp:48-52` |

### 1.4 外部评审处置（2026-09-29）

> 外部评审结论：**Phase 23 Requirements v1.0 通过，可以进入 Preliminary Design**。评审没有指出范围或架构阻塞；本版吸收三类值得进入需求层的补强，保留其余问题到初设 / 详设。

| 评审意见 | 处置 |
|---|---|
| R1 应同时证明「提交线程 ≠ 执行线程」与「执行线程 = UI 消息线程」 | **维持并加严**：R1 与 A1 原样保留三线程身份判据；初设测试必须记录三者，不得用任意 dispatcher thread 冒充 UI 线程 |
| R2 需要明确「即使调用者已经在 UI 线程，也不能 inline 执行」 | **采纳**：新增 **R9 / R10**、**D7**、**A9 / A10**；统一为「提交即入队，callback 不在提交调用栈内执行」 |
| D6 的生命周期应拆成入队前、入队后、取出后、执行中等状态 | **采纳到初设输入**：需求稿补充状态分层要求；具体队列快照与退出时序留初设冻结 |
| Q6 异常边界应尽早回答 | **维持为 Q6**：需求层只规定不得穿出 UI 消息循环；是否逐任务捕获、日志内容与继续策略交给初设定案，不在本版偷冻 |
| 当前两处 `PostMessageW` 不是通用能力 | **采纳并维持**：K4 / 修订记录已按源码复核结果订正，不能把私有唤醒误报为已有 dispatch |
| `Exit()` / `PostQuitMessage` 的线程归属没有被当前稿显式点出 | **采纳为 K15 / N9**：不把现有 `Run()` / `Exit()` 扩成跨线程 API；worker 退出必须先投递到 UI |

### 1.5 真实消费者

| 消费者 | 需要什么 | 当前处置 |
|---|---|---|
| DesktopNest 文件监听 | 独立线程等待 `ReadDirectoryChangesW` 后，把「目录发生变化」通知交给 UI 线程更新模型 / 触发重绘 | 应用层自写等待线程；框架没有通道。`docs/desktopnest-roadmap.md:107,132,180` |
| 图标 / 大图异步解码 | 解码完成后把结果或完成通知交给 UI 线程；不能在工作线程直接触碰 Widget 树 / 窗口状态 | Phase 21 需求稿明确把异步 / 工作线程解码排到 G-3；`docs/phase21-icon-to-image-requirements.md:101-110,149-156` |
| ModelProbe | 目前以 `TimerEvent` 轮询 `probe.exe`，证明存在可接受兜底，但不证明框架已有通用投递能力 | `docs/framework-defect-audit.md:63`；`docs/roadmap-deferred.md:131` |

### 1.5 缺口判定

| 判据 | 命中 | 依据 |
|---|---|---|
| ① 违反既有原则 | — | 当前没有一条既有公共契约声称「工作线程必须能直接投递」；本项是缺失能力，不把能力缺失伪装成契约错误 |
| ② 平台有却被中途丢掉 | — | Win32 有消息投递原语，但现有两处生产 `PostMessageW` 都被具体平台功能私有消费；不存在已承诺、却被翻译器丢掉的公共消息语义 |
| ③ 无替代路径 | **部分命中** | `TimerEvent` 轮询可兜底，但它带来延迟、重复查询和消费者自建状态；对文件监听 / 异步解码，框架没有事件驱动的通用路径。按项目判据，这属于**缺失能力**而非「必须立即修复的契约错误」 |

⇒ **判定：该补能力，立项为 Phase 23；不改写既有 Timer 契约，也不把现有私有 `PostMessageW` 包装成公共 API。**

## 2. 需求（R1–R10）

| # | 需求 | 判据 |
|---|---|---|
| **R1** ★★ | **工作线程提交的工作必须在 UI 消息线程执行**：提交动作发生在工作线程，消费者代码不得在工作线程直接触碰 Widget 树、Window 状态或渲染状态 | 线程身份可在自动化用例中记录并断言；提交线程与执行线程必须可区分 |
| **R2** ★★ | **必须是异步投递语义**：工作线程只提交并返回，不等待 UI 消费完成；UI 线程在消息循环可运行时再执行 | 不允许把第一版做成同步 `Invoke` / 阻塞等待；工作线程不因 UI 暂时繁忙而卡住 |
| **R3** ★★ | **入口归属应用级平台接缝**：调用方通过 `Application` 的框架层入口使用，不需要 HWND、`PostMessageW`、`Windows.h` 或私有宿主句柄 | 公共 API 与核心层不得出现 Win32 类型；应用层不需要知道消息唤醒对象 |
| **R4** | **投递内容必须有明确的所有权与执行语义**：排队期间数据不依赖工作线程栈变量；UI 执行时读取到的是仍然有效的载荷 | 初设必须明确值 / 移动 / 共享所有权中的一种主口径，并覆盖提交失败与排队期间释放路径 |
| **R5** ★ | **默认不绑定具体窗口**：G-3 首版解决「工作线程 → UI 线程」这条应用级通路，不强迫每个工作项携带裸 `Window*`；需要窗口上下文的消费者必须显式、可判定地表达目标 | 不能用一个悬空 `Window*` 作为跨线程生命周期协议；窗口已释放时的行为必须有明确判据 |
| **R6** ★★ | **投递顺序必须可说明**：同一投递源的先后关系不能被框架无故打乱；多工作线程并发提交时，是否承诺全局顺序必须在设计阶段冻结 | 至少保证单源 FIFO；跨源顺序不得在文档中含糊写成「自然有序」 |
| **R7** | **销毁与退出必须安全**：`Application` / 平台宿主 / 队列任一进入销毁或退出阶段后，新提交、已排队工作、正在执行工作三者的行为必须分层定义；不得回调已析构对象 | 需要覆盖 `Run()` 前、`Run()` 中、`Exit()` 后、最后窗口关闭、`Application` 析构五个时机 |
| **R8** | **必须可测且不依赖目视**：至少能自动化断言线程归属、异步时序、顺序、退出 / 销毁路径和既有 Timer 行为不变 | 测试不得只靠 `Sleep` 猜时间；需沿现有消息泵 / 测试替身模式建立确定性推进方式 |
| **R9** ★★ | **提交不得同步执行 callback**：无论提交者是工作线程还是 UI 线程，`PostToUi` 返回前都不得在提交调用栈内执行该 callback | 用例必须覆盖「UI callback A 内提交 B」：B 不得在 A 返回前执行；这条是防止 UI 线程 fast path 造成重入的核心判据 |
| **R10** ★★ | **UI 线程提交与工作线程提交使用同一异步语义**：UI 线程调用也进入队列，不能因为检测到当前线程是 UI 线程就直接调用 | UI 线程提交返回后，callback 只能在后续消息泵处理阶段执行；不得出现调用者无法预期的同步 / 异步分叉 |

### 2.1 需求口径：投递机制与 Event 不是同一个概念

本阶段必须把两个层次分开：

- **投递机制**回答「工作怎样从工作线程到达 UI 线程」；
- **Framework Event**回答「到达后是否把某个已发生事实表达成事件，并沿既有 Router 派发」。

因此，首版不得因为需要投递就顺手新增一个含糊的 `WorkerEvent` / `AsyncEvent` 总类型。若真实消费者需要事件语义，应在初设中按具体事实分别判断；若只是让应用更新自身模型，投递机制可以只承担线程切换，不替消费者虚构事件类型。

## 3. 决策点（D0–D7，待评审拍板）

| # | 决策 | 候选 | ★ 本稿倾向 |
|---|---|---|---|
| **D0** ★★ | **同步还是异步** | ① 异步提交、UI 线程稍后执行；② 同步等待 UI 执行完成 | **①**。G-3 的消费者是文件监听 / 异步解码；阻塞工作线程会把线程切换做成锁，且与 `RequestExit()` 的既有异步语义不一致 |
| **D1** ★★ | **接缝归属** | ① `PlatformApplication → Application` 应用级接缝；② `PlatformWindow → Window` 窗口级接缝；③ 暴露 HWND 让应用自行 `PostMessageW` | **①**。工作线程可能没有窗口、可能服务多个窗口；③ 直接违反「公共 API 不泄漏 Win32」与平台 API 唯一归属；② 会把应用级队列错误地绑到某个窗口生命周期 |
| **D2** ★★ | **公共入口表达什么** | ① 提交一个待执行工作；② 新增一个泛化 Framework Event；③ 仅新增内部平台消息，不给应用入口 | **先定职责为「提交待执行工作」**，具体命名与载荷形态留初设。② 只有真实消费者证明需要统一事实类型时才成立；③ 无法服务应用层文件监听 / 解码完成通知 |
| **D3** ★ | **UI 唤醒方式** | ① 复用应用级消息泵并由平台内部选择唤醒载体；② 借用某个具体窗口 HWND；③ 轮询 `TimerEvent`；④ 暴露平台消息号 | **①**。平台内部可以评估既有隐藏宿主、message-only window 或其他 Win32 载体，但需求阶段不冻结具体消息号；② 受窗口生命周期限制，③ 已被证明是兜底而非等价通路，④ 泄漏平台细节 |
| **D4** | **队列顺序** | ① 单源 FIFO、跨源不承诺；② 所有来源形成全局 FIFO；③ 允许任意重排 / 合并 | **①**。它是最小、可解释的承诺；全局排序会迫使设计暴露线程同步与公平策略，任意重排又会破坏文件变更 / 解码完成的直觉顺序 |
| **D5** ★ | **窗口上下文** | ① 首版不绑定窗口；② 绑定裸 `Window*`；③ 绑定稳定 token / 生命周期句柄；④ 每次投递自动广播所有窗口 | **①**，并把需要窗口上下文的真实需求留给初设回答。② 明显不安全；③ 可能是后续需要，但当前没有证据证明必须先造 token；④ 违反最小投递语义 |
| **D6** ★ | **退出 / 销毁语义** | ① 进入关闭阶段后拒绝新提交并丢弃未执行项；② 尽量排空队列；③ 允许回调继续跑到对象自然失效 | **①**。安全边界优先于「尽量执行」；但「已在 UI 线程执行中的工作」与「正在销毁的宿主」之间的精确顺序必须在初设冻结，不能留到实现期猜 |
| **D7** ★★ | **UI 线程提交的执行时机** | ① 检测到 UI 线程后直接执行；② 仍入队，后续消息泵执行；③ UI 线程提交一律拒绝 | **②**。让 `PostToUi` 始终表示同一个动作：把工作交给 UI 消息线程稍后执行；同时从结构上排除 callback 内联重入 |

### 3.1 本阶段必须守住的命名与抽象纪律

1. 不以 `I` 前缀造 `IUiDispatcher` / `IEventQueue` 等抽象；项目现有公共平台接口没有该命名惯例。
2. 不新增 `ThreadPool`、`Executor`、`Scheduler`、`Future` 等与 G-3 无关的并发框架；一个真实通路不等于一套任务系统。
3. 不把 Win32 `HWND`、消息号或 `WPARAM` / `LPARAM` 放入公共头；平台内部如何唤醒属于实现期问题。
4. 不把 `TimerEvent` 改成「万能异步事件」；它已有明确的周期定时器事实语义，且现有动画 / 光标消费者依赖该语义。

## 4. 非目标（N1–N9）

| # | 非目标 | 理由 |
|---|---|---|
| **N1** | **不实现线程池 / 工作线程管理器** | G-3 只补线程切换通路；线程由消费者创建、命名、停止和回收 |
| **N2** | **不实现 Future / Promise / await / 同步 Invoke** | 这些是任务结果与等待模型，不是 UI 投递的必要条件；会把范围从接缝扩成并发库 |
| **N3** | **不改变 `TimerEvent` 既有契约** | Timer 已有窗口来源、timerId 和焦点派发语义；轮询兜底继续保留，避免零回归被写成迁移要求 |
| **N4** | **不负责 `ReadDirectoryChangesW` 本身** | 文件系统监听属于应用侧工作线程；Phase 23 只提供完成通知进入 UI 的能力 |
| **N5** | **不负责异步图像解码算法 / 缓存 / 取消** | Phase 21 已把异步解码列为 G-3 消费场景，但图像来源、像素转换和资源生命周期仍归 Decode / 消费者各自阶段 |
| **N6** | **不把所有后台结果强制翻译为 Framework Event** | 投递与事实事件是两个层次；没有第二个相同事实消费者前，不造泛化事件层 |
| **N7** | **不支持跨进程 / IPC / 网络消息** | G-3 是同一进程内工作线程到 UI 消息线程的通路 |
| **N8** | **不承诺跨平台后端实现** | 当前唯一平台实现是 Win32；X11 / Wayland 仍按既有 YAGNI 口径留接口，不因 G-3 预建跨平台消息系统 |
| **N9** ★ | **不把 `Application::Run()` / `Exit()` 整体改造成跨线程安全 API** | 既有 `m_running` 与 `PostQuitMessage` 路径没有这样的契约；工作线程需要退出时，先把 `Exit()` 作为 UI 工作投递，不在本阶段扩大线程安全范围 |

## 5. 待实测 / 待定（Q1–Q10）

| # | 问题 | 处置倾向 |
|---|---|---|
| **Q1** ★★★ | `Application` 的公共入口应采用哪种最小载荷形态，才能同时支持文件监听完成与图像解码完成，又不引入泛化 Event / 任务系统？ | 初设第一优先级；先列两个真实消费者的最小共同需求，再定命名与所有权，不先写接口草案 |
| **Q2** ★★ | 应用级接缝的具体落点是 `PlatformApplication` 纯虚能力、基类已有 `std::function` sink 模式的扩展，还是两者组合？ | 倾向沿既有应用级能力惯例；须核对 `Application` / `PlatformApplication` 析构顺序与三个实现 / 测试替身的影响 |
| **Q3** ★★ | Win32 消息泵未运行时提交怎么办：`Application` 构造后但 `Run()` 前、`Exit()` 后、消息循环返回后分别是什么状态？ | 倾向统一为可查询的拒绝 / 丢弃语义；禁止静默保存到会跨越下一次生命周期的全局队列 |
| **Q4** ★★ | 工作项在 `Application` 析构、平台宿主销毁、最后一个窗口关闭之间如何清理？ | 必须画出「提交 → 入队 → 唤醒 → 执行 / 丢弃 → 析构」时序；参考既有 `SetTrayEventSink` 的清空先于宿主销毁纪律 |
| **Q5** | 多工作线程同时提交时，是否需要全局 FIFO、是否允许合并同类通知、是否需要公平性保证？ | 倾向只承诺单源 FIFO；文件监听是否允许合并、图像结果是否必须逐项保留，交给真实消费者场景逐一回答 |
| **Q6** | UI 线程执行工作时若工作抛出异常，框架边界如何处理？ | 初设必须回答「回调异常是否由调用方禁止、框架是否记录并继续、是否终止」；不得把异常穿过 Win32 WindowProc / 消息循环 |
| **Q7** | 工作项是否需要窗口上下文？若需要，如何表达已销毁窗口而不使用裸 `Window*` 保活？ | 当前倾向首版不绑定窗口；若消费者证明需要，先设计稳定 token / 失效判定，再谈公共类型 |
| **Q8** | 如何在四工具链和不同消息泵时序下做确定性测试？ | 倾向显式泵一拍 / 使用测试替身记录线程 ID 与队列状态；禁止以不受控 `Sleep` 作为唯一判据 |
| **Q9** ★★ | callback A 在 UI 线程执行期间提交 callback B 时，B 是否只能在 A 返回后执行？队列 drain 是否允许当前批次内的递归消费？ | 倾向**不允许递归消费**：提交只产生后续消息 / 后续 drain；初设须把「当前批次快照」与「新提交工作」分开描述 |
| **Q10** ★★ | UI 线程自身提交时，如何在 `Run()` 前、`Run()` 中、`Exit()` 后保持同一 `PostToUi` 语义？ | 倾向：Run 前可入队、Run 中异步执行、关闭后拒绝；最终返回值与队列清理时序由初设冻结 |

## 6. 验收方向（A1–A10）

| # | 验收项 | 判据 |
|---|---|---|
| **A1** ★★ | **线程归属** | 工作线程提交后，工作内容只在 UI 消息线程执行；测试记录提交线程 ID 与执行线程 ID，二者不同且执行线程等于消息循环线程 |
| **A2** ★★ | **异步且不阻塞** | 提交调用在 UI 尚未消费时即可返回；不能靠等待执行结果才能返回 |
| **A3** ★★ | **公共面不泄漏平台细节** | 公共头无 HWND / Win32 消息类型；应用调用不需要自行 `PostMessageW` 或取得隐藏宿主句柄 |
| **A4** | **顺序契约成立** | 同一个投递源提交 A、B、C，UI 消费顺序为 A、B、C；多源顺序按设计稿明确判定，不得用未定义的「自然顺序」验收 |
| **A5** ★★ | **生命周期安全** | 覆盖 `Run()` 前、`Run()` 中、`Exit()` 后、最后窗口关闭、`Application` 析构；不执行已拒绝或已失效目标，不访问已析构对象 |
| **A6** | **真实消费者可接入** | 至少用一个「文件监听完成通知」或「异步解码完成通知」样式的测试载荷走通；不要求本阶段实现真实 `ReadDirectoryChangesW` 或解码器 |
| **A7** | **既有 Timer 零回归** | 既有 Timer / 动画 / TextBox 光标闪烁路径的行为不因新增唤醒通道改变；现有测试套件保持通过 |
| **A8** | **四工具链可测** | MSVC、ClangCL、Clang、MinGW 均能构建并运行新增用例；断言启用状态与显示器 DPI 按项目验证纪律记录，不以单链结果代替全链结论 |
| **A9** ★★ | **无同步重入** | callback A 在 UI 线程内提交 B 后，B 不得在 A 返回前执行；A 完成后，B 才能由后续 UI 阶段消费 |
| **A10** ★★ | **UI 线程调用语义一致** | UI 线程调用 `PostToUi` 后，callback 不在该调用栈内执行；Run 前 / Run 中 / 关闭后的接受与拒绝结果符合设计稿 |

> **验收边界声明**：A1–A6 是 G-3 的线程、入口、顺序与生命周期核心判据；A7–A8 是零回归与交付判据；A9–A10 是本轮补入的非重入 / 调用者线程语义判据。A6 只验「真实消费者形态」，不把消费者完整功能塞进 Phase 23。消息唤醒采用哪一种 Win32 内部载体，以及是否发生消息合并，须在初设 / 详设中分别对应到自动化判据，不能在本稿把实现假设写成验收事实。

## 7. 影响面（预估，初设时定稿）

| 项 | 预估 |
|---|---|
| **公共入口** | 可能新增 1 个应用级公共入口；具体名称、参数和返回状态留给初设。**不预先承诺**新增 Event 类型 |
| **公共平台接缝** | 可能修改 `include/ECDI/Platform/PlatformApplication.h`，并同步 `Application` 透传；若采用纯虚能力，必须盘点全部生产实现与测试替身 |
| **平台实现** | 预计落在 `src/Platform/Win32/Win32PlatformApplication.{h,cpp}` 或其现有应用级宿主逻辑；不应修改现有托盘 `WM_NULL`、Desktop 跟随消息或 `TimerEvent` 分支的语义 |
| **生命周期** | `Application` 析构、`PlatformApplication` 宿主销毁、`SetTrayEventSink` 类似的清空时机需要同步设计；这是本阶段的 P0 触面 |
| **事件系统** | 默认不改 `Event` / `EventRouter` / `TimerEvent`；若 Q1/Q7 证明需要窗口事实事件，再单独登记新增类型与路由影响 |
| **测试** | 预计新增一个投递通路测试承载文件，并修改 `RunAllTests.h/.cpp` 登记；若公共接缝新增纯虚，测试替身还需同步实现 |
| **构建系统** | CMake 的 `GLOB_RECURSE ... CONFIGURE_DEPENDS` 通常可自动发现新源；测试登记仍是手工动作，须在详设清单逐项列出。当前不预期改构建声明 |
| **规模与风险** | 需求阶段不报文件总数、API 最终数量或用例最终数量；最大风险是**生命周期竞态**与**把投递通路膨胀成并发框架**，不是 Win32 消息号本身 |

### 7.1 与既有约束的对齐

| 既有约束 | G-3 对齐方式 |
|---|---|
| 平台解耦：每个 Win32 API 唯一归属 | Win32 唤醒原语只留在 `Platform/Win32`；`Application` 只见框架语义 |
| 应用级平台接缝 | 工作线程投递是跨窗口 / 跨宿主的应用级能力，不挂到某个 `PlatformWindow` |
| Event = 已发生事实 | 不用一个泛化异步 Event 掩盖投递机制；是否生成具体事件由真实事实消费者另行决定 |
| 资源类禁拷贝禁移动、地址稳定 | 排队数据不得隐式依赖 Window / Widget 地址；窗口上下文必须有失效语义 |
| 不引入投机抽象 | 只解决两个已出现的真实消费者的共同最小需求，不预建线程池、任务调度器或跨平台事件总线 |
| 测试由用户四工具链执行 | 本稿只定义可自动化判据；实施后的构建与运行由用户在 VS / CLion 完成，AI 侧不代跑 |
