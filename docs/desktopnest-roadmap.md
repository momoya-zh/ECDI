# DesktopNest 阶段拆分与依赖链（v1.1）

> 阶段：规划（跨框架与应用两侧，**不占用 Phase 编号**）
> 日期：2026-09-11
> 状态：待评审
> 一句话：把文件收进程序目录、在桌面上以圆角框呈现的整理器——视图像桌面图标，真身在 storage
> 命名说明：`DesktopNest` 为占位名，取自"桌面上的巢"，**待用户确认**

---

## 1. 需求收敛结果（已拍板）

| 维度 | 决策 | 直接后果 |
|---|---|---|
| 技术栈 | 用 ECDI 自己做（不引其他栈） | 框架侧需新增窗口形态与平台集成能力；应用侧落 `examples/DesktopNest` |
| 文件语义 | 拖入框 = **移动**进 `<程序目录>/storage/` | 全项目唯一有数据丢失风险的决策点；M3 必须配「还原回桌面」+ 卸载保护 |
| 合并语义 | **二态**：展开（标题条 + **当前成员**的内容）/ 折叠（仅标题条）。合并框任何时刻只渲染 **1 个**成员 | 数据模型 = 每个框都是「自身 + N 个被收编成员」的组，`active` 指向当前成员 |
| 合并方向 | **单向「收编」**：当前框吸收别的框成为自己的成员；反方向（当前框被收编）不做 | 列表第二区只需「加入成员」一项，不需要方向选择 UI |
| 合并入口 | **仅**标题栏左侧按钮弹出的列表（**不做**框对框拖拽） | 与「拖文件进框」手势解耦，M1 无任何拖放实现 |
| 嵌套 | **不允许**，恒为一层 | 成员列表扁平无递归，拆出不存在"拆哪一层"的歧义 |
| 窗口层级 | **On Desktop 档**：被应用窗口覆盖，且 Win+D 后仍可见 | 实现路线未验证（见 §7 R-1），**spike 必须前置** |
| 位置存储 | 多屏 + DPI：屏幕标识 + 屏幕内相对比例 + DPI 无关尺寸 | 配置文件格式一次定死，不做后续用户数据迁移 |
| 能力划分 | 需改窗口过程/窗口样式的进框架；纯 API 调用留应用层 | 框架侧 **2 个 Phase**（最初估计是 4 个） |

### 1.1 「置底」与「像桌面图标」是两件事（决策依据留档）

用户原话是「置底……类似桌面上的应用图标」，但这两者**在 Win+D 上行为相反**。Rainmeter 官方文档把它做成了两个独立档位，原文：

- `-1: Bottom` — The skin will **not** stay visible when showing the desktop {Win-D} and stay behind other normal application windows.
- `-2: On Desktop` — The skin **will stay visible** when showing the desktop {Win-D} and stay behind other normal application windows.

Rainmeter 作者 jsmorley 论坛补充：*"the only reason to ever use Bottom is if you want the skin to be hidden when you use Show Desktop / Win-D"*。

| | 被应用窗口覆盖 | Win+D 之后 |
|---|---|---|
| 置底窗口（`HWND_BOTTOM`） | ✅ | ❌ 一起被藏 |
| 桌面图标层（Progman 的子窗口） | ✅ | ✅ 依然在 |

**z 序事实**：普通应用窗口 > 我们的置底框 > 桌面图标层 > 壁纸。由此推出一个副作用：**框会盖住它下方的桌面图标**（按 `HWND_BOTTOM` 语义推定，待实测确认）。

用户已选定 **On Desktop 档**（即"像桌面图标"语义）。

### 1.2 合并框模型：二态 + 左侧成员列表（2026-09-11 修订，**取代最初记录的「三态」**）

v1.0 记录的模型是「三态：折叠 / 紧凑选项卡 / 展开汇总」，**该模型已废除**——用户明确为**二态**，"汇总态"不存在。

**标题栏三个部件各管一件事：**

| 部件 | 行为 |
|---|---|
| 左侧按钮 | 点击弹出**成员列表**（浮层，不改变框尺寸） |
| 中部标题 | 显示**当前成员框自己的标题**（合并框不另造名字——切换成员时框"变成"那个框） |
| 右侧按钮 | **收缩 / 展开**（唯一的二态开关） |

**列表的两个分区：**

1. **显示哪个成员** —— 单选，勾选即切换；切换后标题与内容整体换成该成员的
2. **成员管理** —— 「拆出「<当前成员>」」+「加入成员…」（列出桌面上其他独立框，选中即被本框收编）

**两态：** 展开 = 标题条 + 当前成员的内容；折叠 = 仅标题条。

**统一模型：每个框都是一个「组」，普通框 = 只有自己一个成员的组。**

| 操作 | 语义 |
|---|---|
| 合并 | 把别的框 id 追加进自己的 `members`；被收编者的窗口消失（其 `placement` / `state` 保留，供拆出恢复） |
| 拆出 | 从 `members` 移除该 id → 它重新成为独立窗口 |
| 成员列表含自身 | 自身恒为成员之一 → 普通框与合并框共用同一套列表 UI，**合并入口天然存在** |

**其它已定默认（用户未反对即生效）：**

| # | 项 | 取值 | 理由 |
|---|---|---|---|
| 1 | 拆出的框放哪 | 优先恢复它**被收编前的 `placement`**；无记忆或落点冲突时从父框右下角级联偏移 | 用户授权"由程序定"，取最不反直觉的规则 |
| 2 | 切换成员后框的尺寸 | **不变**，内容超出则滚动 | 尺寸跟随成员会让用户摆好的桌面布局乱跳 |
| 3 | 列表形态 | 浮层弹出（非内联撑高框） | 折叠态下同样可用 |
| 4 | 合并框的视觉标识 | 左侧按钮上加成员数标识（如 `3`） | 否则用户分不清当前框是普通框还是合并框 |

## 2. 定位与复杂度分布

DesktopNest 本质是「**视图在桌面、真身在程序目录**」的映射器。它的复杂度分布和直觉相反：

| 部分 | 占比 | 说明 |
|---|---|---|
| 框的 UI（二态、合并、布局、圆角） | 小头 | ECDI 现成能力基本够：`DrawRoundedRect` + Layout + `AnimationManager` + Theme |
| 桌面常驻（无边框、层级、托盘） | 中头 | 依赖框架侧新增能力 |
| **移动用户真实文件** | **大头** | 同名冲突、跨盘移动、文件被占用、长路径、删除去向、卸载保护——全是不可逆操作 |

**结论：这个项目的成败在文件操作的严谨性，不在界面好不好看。**

## 4. 分层判据：什么该进框架，什么留应用层

一个 Win32 能力是否该进 ECDI 公共抽象，看两条：

1. **它是否需要改动窗口过程 / 窗口样式？** —— 需要则必须进框架，因为应用层**够不着** HWND 的消息循环（`PlatformWindowHost` 无通用消息接缝，这是实证结论，不是推测）。
2. **它是否已经是公共抽象的一部分？** —— 窗口形态（chrome / 层级）本来就是 `PlatformWindow` 的职责范围。

按此判据：

| 能力 | 进框架？ | 理由 |
|---|---|---|
| 无边框 + 自绘标题栏 | ✅ | 改窗口样式 + `WM_NCCALCSIZE`/`WM_NCHITTEST` |
| 窗口层级（Bottom / Desktop） | ✅ | 改 z 序，`WM_WINDOWPOSCHANGING` |
| 托盘 | ✅ | 需窗口过程接自定义消息回调 |
| 拖入（`WM_DROPFILES`） | ✅ | 需 `DragAcceptFiles` + 窗口过程 |
| 图标提取 `SHGetFileInfo` | ❌ | 纯 API 调用，无消息依赖 |
| 双击打开 `ShellExecuteW` | ❌ | 纯 API 调用 |
| 文件监听 `ReadDirectoryChangesW` | ❌ | 纯 API 调用 + 独立等待线程 |

→ 框架侧只需要 **2 个 Phase**，不是 4 个。

## 5. 框架侧

### Phase 12 · WindowChrome（需求稿已有，本规划追加 2 条）

现有 R1–R8 覆盖：chrome API / 无边框客户区 / 命中测试 / 最大化修正 / CaptionBar / DWM / 标题栏事件 / 兼容底线。

本规划追加：

- **R9 · 平台消息扩展接缝** —— 给应用层（或同级平台能力）一个注册自定义 Win32 消息处理者的唯一点。**这是 Phase 13 的前置**，没有它托盘和拖入无路可走。它天然属于 Phase 12，因为 12 已经在改 `WindowMessageHandler`。
- **R10 · 窗口层级能力** —— `WindowLayer { Normal, Bottom, Desktop }` + `Window::SetWindowLayer`。`Bottom` 靠 `WM_WINDOWPOSCHANGING` 强制 `hwndInsertAfter = HWND_BOTTOM`；`Desktop` 档实现路线未验证（见 §7 R-1）。

→ 详细改动见 `docs/phase12-windowchrome-requirements.md` v1.1。

### Phase 13 · 托盘与拖入接缝（全新）

- **托盘**：`Shell_NotifyIcon` 抽象（注册/更新/移除图标）、图标回调消息路由（经 R9 接缝）、左键点击行为、右键菜单、退出路径
- **拖入**：`DragAcceptFiles` + `WM_DROPFILES` → 翻译成框架层"外部文件被拖入窗口"事件（UTF-8 路径列表），**不带任何业务语义**
- **明确不做**：`IDropTarget`（拖拽光标反馈）、`IDropSource`（从框里拖出到资源管理器）。前者要 OLE 初始化，后者是完整拖放协议——**拖出整个砍掉**，需要时另立阶段

## 6. 应用侧 · DesktopNest 里程碑

| 里程碑 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| **M1 观感** | 框二态（展开/折叠）+ 左侧成员列表（切成员 / 收编 / 拆出）+ 拖动；**数据用假数据** | Phase 12 | 低 |
| **M2 内容** | 真实文件列表 + 图标提取 + 双击打开 + 拖入落盘 | Phase 13 | 中（拖入协议） |
| **M3 数据安全** | 移动策略、同名冲突、回收站删除、**一键还原回桌面**、卸载保护 | 无（纯应用层） | **高（不可逆）** |
| **M4 常驻** | 托盘交互、多屏 + DPI 比例存储、配置持久化、`ReadDirectoryChangesW` 同步 | Phase 13 | 中 |

**顺序理由**：M1 只验观感（零风险、最快看到东西）；M3 虽然是最大风险，但它依赖 M2 的真实文件才有意义，所以插在 M2 之后、M4 之前——**M3 未完成前不对外分发**。

## 7. 风险登记

| ID | 风险 | 等级 | 应对 |
|---|---|---|---|
| R-1 | **On Desktop 档实现路线未验证**。业界两条路：① reparent 到桌面层（`WorkerW`/`Progman`，Wallpaper Engine / Fences 路线）② `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` 监测 `WorkerW` 变前台时临时置顶。Win11 较新版本对 `WorkerW` 的处理有变化 | **高** | **前置 spike**：50 行以内的独立验证程序，先确认在你的 Win11 版本上哪条路有效、是否稳定；spike 失败则降级为 `Bottom` 档（Win+D 会消失），**并回写本决策** |
| R-2 | 移动用户真实文件的不可逆性 | **高** | M3 全项完成前不分发；删除走回收站不走 `DeleteFile`；提供批量还原回桌面；卸载时检测 `storage` 非空并阻断 |
| R-3 | 置底/Desktop 框盖住桌面图标 | 中 | 实测确认；若成立，在文档中明确告知用户（框位置避开图标区） |
| R-4 | z 序被其他程序打断（有的程序会强行把自己置顶，把我们的框顶下来） | 中 | `WM_WINDOWPOSCHANGING` 里持续强制，而非只调用一次 `SetWindowPos` |
| R-5 | 拖入协议范围蔓延到完整 OLE DnD | 中 | Phase 13 显式列为非目标 |

## 8. 数据模型草案

**合并 / 拆出的语义已拍板**（见 §1.2：视图分组、零文件操作、恒一层、单向收编）。以下**字段格式**为倾向性提案，尚未经用户确认。

### 8.1 配置结构（`config.json`，置于程序目录）

```jsonc
{
  "version": 1,
  "boxes": [
    {
      "id": "box-a",
      "title": "工作文档",
      "state": "expanded",              // collapsed | expanded（只有二态，无 compact）
      "placement": {
        "monitor": "primary",           // 屏幕标识（多屏）
        "x": 0.02, "y": 0.05,           // 屏幕内相对比例
        "w": 220,  "h": 320             // DPI 无关逻辑尺寸
      },
      "members": ["box-b", "box-c"],    // 被本框收编的成员 id（不含自己；空数组 = 普通框）
      "active": "box-a"                 // 当前显示哪个成员，默认是自己
    },
    {
      "id": "box-b",
      "title": "学习资料",
      "state": "expanded",
      "placement": { /* 被收编前的摆放位置 —— 保留，拆出时按 §1.2 默认 1 恢复 */ },
      "members": [], "active": "box-b"
      // box-b 若已被 box-a 收编，则不作为顶层框渲染；其条目仍保留以便拆出恢复
    }
  ]
}
```

**相比 v1.0 的三处简化**：

| v1.0 字段 | v1.1 | 原因 |
|---|---|---|
| `state: compact` | 删除 | 二态模型里没有紧凑态 |
| `mergedChildren` + `activeChild`（索引） | `members` + `active`（**id**，非索引） | 索引在建/删成员后会错位；用 id 天然稳定 |
| `storageDir` | 删除 | 目录恒为 `storage/<id>/`（§8.2），字段冗余且可与 §8.3「磁盘为准」冲突 |

### 8.2 storage 目录结构（倾向）

`storage/<boxId>/` —— **每个框一个真实文件夹**，而非扁平目录 + 索引映射。

理由：配置损坏时文件不会变孤儿；同名文件跨框不冲突；用户在资源管理器里也能直接管理。

### 8.3 真相源（倾向）

**以磁盘为准**：框内列表由磁盘扫描得出，`config.json` 只存布局与分组关系；配合 `ReadDirectoryChangesW` 让外部改动同步到视图。

若反过来以配置为准，`config.json` 会成为"第二真相源"，用户手删文件后框里仍显示、双击报错。

### 8.4 合并语义：纯视图，零文件操作

**合并与拆出都不触碰 `storage/`**，成员各自保留 `storage/<成员id>/`，目录始终平级、不产生嵌套。

| 操作 | 磁盘 | 配置 | 视图 |
|---|---|---|---|
| 合并（B 被 A 收编） | 无变化 | `A.members += B` | B 的窗口消失 |
| 切换成员 | 无变化 | `A.active = 目标id` | A 的标题与内容整体换成该成员 |
| 拆出 B | 无变化 | `A.members -= B` | 新建 B 的窗口，位置按 §1.2 默认 1 恢复 |

**拖入文件的落点**：拖进合并框的文件，落到**当前 `active` 成员**的目录——合并框不额外拥有目录，它自己也只是成员之一（`active == 自己` 时落到自己的目录）。

**这条设计的价值**：把合并在数据层降级为"只写一行配置"，于是用户最大的一次不可逆风险（§7 R-2 移动真实文件）**不会被合并 / 拆出动作放大**——最容易手滑的操作恰好是最便宜的。

## 9. 待决问题（按优先级）

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | **拖入时同名文件怎么办**（重命名 / 覆盖 / 询问） | 移动语义下的核心冲突策略，直接影响数据安全 |
| 2 | **真相源**：磁盘为准还是配置为准（§8.3 倾向磁盘） | 决定 `config.json` 的职责边界 |
| 3 | **`storage` 结构**：每框一个真文件夹还是扁平 + 索引（§8.2 倾向前者） | 决定外部可管理性与抗损坏能力 |
| 4 | **MVP 能力边界**：框内是否要多选 / 手动排序 / 重命名 / 删除；右键用原生 shell 菜单还是自绘 | 原生 `IContextMenu` 是独立工作量 |
| 5 | **框本身**能否拖动 / 缩放（内容超出已定为滚动，见 §1.2 默认 2） | 用户原需求未提及 |
| 6 | **「落点冲突」如何判定**（§1.2 默认 1 的兜底分支）——与现有框重叠多少算冲突？还是不判定、一律级联偏移？ | 拆出时的位置恢复规则需要可实现的判据，否则会成为实现期的临时拍脑袋 |
| 7 | **应用名**是否采用 `DesktopNest` | 占位名 |
| 8 | **还原回桌面**的具体形态（一键全部 / 按框 / 逐文件） | 本软件最容易被骂的点 |
