## 1. 需求收敛结果（已拍板）

| 维度 | 决策 | 直接后果 |
|---|---|---|
| 技术栈 | 用 ECDI 自己做（不引其他栈） | 框架侧需新增窗口形态与平台集成能力；应用侧落 `examples/DesktopNest` |
| 文件语义 | 拖入框 = **移动**进 `<程序目录>/storage/` | 全项目唯一有数据丢失风险的决策点；M3 必须配「还原回桌面」+ 卸载保护 |
| 合并语义 | **二态**：展开（标题条 + **当前成员**的内容）/ 折叠（仅标题条）。合并框任何时刻只渲染 **1 个**成员 | 数据模型 = 每个框都是「自身 + N 个被收编成员」的组，`active` 指向当前成员 |
| 合并方向 | **单向「收编」**：当前框吸收别的框成为自己的成员；反方向（当前框被收编）不做 | 列表第二区只需「加入成员」一项，不需要方向选择 UI |
| 合并入口 | **仅**标题栏左侧按钮弹出的列表（**不做**框对框拖拽） | 与「拖文件进框」手势解耦，M1 无任何拖放实现 |
| 嵌套 | **不允许**，恒为一层 | 成员列表扁平无递归，拆出不存在"拆哪一层"的歧义 |
| 窗口层级 | **On Desktop 档**：被应用窗口覆盖，且 Win+D 后仍可见 | 实现路线**已验证**＝紧贴桌面窗口正上方（§7.1）；桌面窗口树整条路判死 |
| 位置存储 | 多屏 + DPI：屏幕标识 + 屏幕内相对比例 + DPI 无关尺寸 | 配置文件格式一次定死，不做后续用户数据迁移 |
| 能力划分 | 需改窗口过程 / 窗口样式的进框架；纯 API 调用留应用层 | 框架侧 **2 个 Phase**（最初估计是 4 个）——**v1.7 追加：两个 Phase 已完成，另余 4 项残差 G-1~G-4**（§5） |

### 1.1 「置底」与「像桌面图标」是两件事（决策依据留档）

用户原话是「置底……类似桌面上的应用图标」，但这两者**在 Win+D 上行为相反**。Rainmeter 官方文档把它做成了两个独立档位，原文：

- `-1: Bottom` — The skin will **not** stay visible when showing the desktop {Win-D} and stay behind other normal application windows.
- `-2: On Desktop` — The skin **will stay visible** when showing the desktop {Win-D} and stay behind other normal application windows.

Rainmeter 作者 jsmorley 论坛补充：*"the only reason to ever use Bottom is if you want the skin to be hidden when you use Show Desktop / Win-D"*。

| | 被应用窗口覆盖 | Win+D 之后 |
|---|---|---|
| 置底窗口（`HWND_BOTTOM`） | ✅ | ❌ 一起被藏 |
| 桌面图标层（Progman 的子窗口） | ✅ | ✅ 依然在 |

**z 序事实**：普通应用窗口 > 我们的置底框 > 桌面图标层 > 壁纸。由此推出一个副作用：**框会盖住它下方的桌面图标**（按 `HWND_BOTTOM` 语义推定，待实测确认）。

用户已选定 **On Desktop 档**（即"像桌面图标"语义）。

### 1.2 合并框模型：二态 + 左侧成员列表（2026-09-11 修订，**取代最初记录的「三态」**）

v1.0 记录的模型是「三态：折叠 / 紧凑选项卡 / 展开汇总」，**该模型已废除**——用户明确为**二态**，"汇总态"不存在。

**标题栏三个部件各管一件事：**

| 部件 | 行为 |
|---|---|
| 左侧按钮 | 点击弹出**成员列表**（浮层，不改变框尺寸） |
| 中部标题 | 显示**当前成员框自己的标题**（合并框不另造名字——切换成员时框"变成"那个框） |
| 右侧按钮 | **收缩 / 展开**（唯一的二态开关） |

**列表的两个分区：**

1. **显示哪个成员** —— 单选，勾选即切换；切换后标题与内容整体换成该成员的
2. **成员管理** —— 「拆出「<当前成员>」」+「加入成员…」（列出桌面上其他独立框，选中即被本框收编）

**两态：** 展开 = 标题条 + 当前成员的内容；折叠 = 仅标题条。

**统一模型：每个框都是一个「组」，普通框 = 只有自己一个成员的组。**

| 操作 | 语义 |
|---|---|
| 合并 | 把别的框 id 追加进自己的 `members`；被收编者的窗口消失（其 `placement` / `state` 保留，供拆出恢复） |
| 拆出 | 从 `members` 移除该 id → 它重新成为独立窗口 |
| 成员列表含自身 | 自身恒为成员之一 → 普通框与合并框共用同一套列表 UI，**合并入口天然存在** |

**其它已定默认（用户未反对即生效）：**

| # | 项 | 取值 | 理由 |
|---|---|---|---|
| 1 | 拆出的框放哪 | 优先恢复它**被收编前的 `placement`**；无记忆或落点冲突时从父框右下角级联偏移 | 用户授权"由程序定"，取最不反直觉的规则 |
| 2 | 切换成员后框的尺寸 | **不变**，内容超出则滚动 | 尺寸跟随成员会让用户摆好的桌面布局乱跳 |
| 3 | 列表形态 | 浮层弹出（非内联撑高框） | 折叠态下同样可用 |
| 4 | 合并框的视觉标识 | 左侧按钮上加成员数标识（如 `3`） | 否则用户分不清当前框是普通框还是合并框 |

## 2. 定位与复杂度分布

DesktopNest 本质是「**视图在桌面、真身在程序目录**」的映射器。它的复杂度分布和直觉相反：

| 部分 | 占比 | 说明 |
|---|---|---|
| 框的 UI（二态、合并、布局、圆角） | 小头 | ECDI 现成能力基本够：`DrawRoundedRect` + Layout + `AnimationManager` + Theme |
| 桌面常驻（无边框、层级、托盘） | 中头 | 依赖框架侧新增能力 |
| **移动用户真实文件** | **大头** | 同名冲突、跨盘移动、文件被占用、长路径、删除去向、卸载保护——全是不可逆操作 |

**结论：这个项目的成败在文件操作的严谨性，不在界面好不好看。**

## 4. 分层判据：什么该进框架，什么留应用层

一个 Win32 能力是否该进 ECDI 公共抽象，看两条：

1. **它是否需要改动窗口过程 / 窗口样式？** —— 需要则必须进框架，因为应用层**够不着** HWND 的消息循环（实证结论，不是推测）。注意「够不着」不等于要开一条裸消息接缝：Phase 12 R9 已定稿为「平台消息层**先吸收成框架能力**，应用层只调能力 API」（见 §5 R9 三步惯例）。
2. **它是否已经是公共抽象的一部分？** —— 窗口形态（chrome / 层级）本来就是 `PlatformWindow` 的职责范围。

按此判据：

| 能力 | 进框架？ | 理由 |
|---|---|---|
| 无边框 + 自绘标题栏 | ✅ | 改窗口样式 + `WM_NCCALCSIZE`/`WM_NCHITTEST` |
| 窗口层级（Bottom / Desktop） | ✅ | 改 z 序，`WM_WINDOWPOSCHANGING` |
| 托盘 | ✅ | 需窗口过程接自定义消息回调 |
| 拖入（`WM_DROPFILES`） | ✅ | 需 `DragAcceptFiles` + 窗口过程 |
| 图标提取 `SHGetFileInfo` | ❌ | 纯 API 调用，无消息依赖 |
| 双击打开 `ShellExecuteW` | ❌ | 纯 API 调用 |
| 文件监听 `ReadDirectoryChangesW` | ❌ | 纯 API 调用 + 独立等待线程 |

→ 框架侧只需要 **2 个 Phase**，不是 4 个。

## 5. 框架侧

### Phase 12 · WindowChrome ✅（已实现并验收 2026-09-12 ~ 09-15；本规划曾追加 2 条）

现有 R1–R8 覆盖：chrome API / 无边框客户区 / 命中测试 / 最大化修正 / CaptionBar / DWM / 标题栏事件 / 兼容底线。

本规划追加：

- **R9 · 平台消息扩展接缝** —— 〔**2026-09-12 落地裁决：惯例而非抽象**〕**不新建接缝类、不提供消息注册机制**；后续阶段加能力的模板是三歩：① `PlatformWindow` 加一个能力 `virtual`（接口即契约、零消息号）→ ② `Window` 加公共方法透传（应用层唯一入口）→ ③ 平台消息在具体实现的 `HandleMessage` 内消化（不进 `WindowMessageHandler` 翻译器，除非产生 Framework Event）。**这正是 Phase 14 托盘/拖入的前置**——托盘回调、`WM_DROPFILES` 都按惯例吸收为能力，而非裸露消息号。先例：Phase 12 的 `SetChromeMode`/`SetWindowLayer`/`Minimize`/`Maximize`/`Restore`，Phase 13 的 `IsClientInteractiveAt`。定稿原文见 `docs/phase12-windowchrome-detailed-design.md` 头部 `D-SEAM-1`。
- **R10 · 窗口层级能力** —— ✅ **已出清（2026-09-15）**。`WindowLayer { Normal, Bottom, Desktop }` + `Window::SetWindowLayer` 已落地（Phase 12）；`Bottom` 靠 `WM_WINDOWPOSCHANGING` 强制 `hwndInsertAfter = HWND_BOTTOM`；`Desktop` 档实现路线**已取证**（紧贴桌面窗口正上方 + 前台钩子重插，见 §7.1），六条人工判据全过 ⇒ **R10 在框架侧的可行性问题已闭环**。后续把该档真正实现进 `Win32PlatformWindow`（含「桌面窗口重建自适应」）属于 DesktopNest 实现阶段的工作量，**不在本轮取证范围内**。

→ 详细改动见 `docs/phase12-windowchrome-requirements.md` v1.1。

### Phase 14 · 托盘与拖入接缝 ✅（已实现并验收 2026-09-17）〔编号校正：原记为 Phase 13，但 Phase 13 实际已用于 CaptionBar（2026-09-14 完成）〕

- **托盘**：`Shell_NotifyIcon` 抽象（注册/更新/移除图标）、图标回调消息路由（经 R9 接缝）、左键点击行为、右键菜单、退出路径
- **拖入**：`DragAcceptFiles` + `WM_DROPFILES` → 翻译成框架层"外部文件被拖入窗口"事件（UTF-8 路径列表），**不带任何业务语义**
- **明确不做**：`IDropTarget`（拖拽光标反馈）、`IDropSource`（从框里拖出到资源管理器）。前者要 OLE 初始化，后者是完整拖放协议——**拖出整个砍掉**，需要时另立阶段
- **接缝走法**：按 R9 三步惯例吸收为能力（托盘回调消息 / `WM_DROPFILES` 都在平台实现内消化后抛 Framework Event），**不新建消息注册接口**

**✅ 已立项（2026-09-15）**：需求稿 → `docs/phase14-tray-and-drop-requirements.md` **v1.0**（R1–R13 三组 + 决策点 D0–D9 待拍板）。立项勘察得出三条**会改形态**的事实：

| # | 事实 | 后果 |
|---|---|---|
| **F1** | **message-only window 不接收广播消息**（MSDN「Window Size and Position」；Raymond Chen 补充：它在内部是 `HWND_MESSAGE` 的子窗口，**"broadcasting is done to top-level windows"**） | 托盘承载窗口**不能**用 message-only window ⇒ 必须是**普通（可隐藏的）顶层窗口** |
| **F2** | **`TaskbarCreated` 由 shell 注册并广播给所有顶层窗口**（MSDN「Taskbar Creation Notification」） | explorer 重建后托盘图标可**自愈**（重新 `NIM_ADD`） |
| **F4** | **「最后一个窗口关闭 ⇒ `Exit()`」**（`Application.cpp:115-118`）+ **`PlatformWindow` / `Window` 无 `Hide()`** | **「关闭主窗口 → 最小化到托盘、应用继续运行」当前无法实现** ⇒ 需求稿 R12/R13 列为**隐性前置** |

**★ F2 与 R-1 的机制对照（战略判据——本阶段立项的底气）**：桌面层 A 路线（reparent 到 `WorkerW`）被 explorer 重建**杀死**，因为它持有的是**窗口层级关系**；而托盘图标是**注册关系**——explorer 重建后系统会**主动广播通知**，应用据此重新注册即可。⇒ **同为 shell 集成：注册式可自愈，层级式不可**。这条判据同时是 DesktopNest「桌面常驻」方向选型的依据（§7.1 的 E 路线亦属"注册/跟随式"而非"层级挂载式"）。

**⚠️ 范围提示**：需求稿把 **R12（`Hide()`）/ R13（退出策略）** 列为隐性前置并**倾向纳入本阶段**——不做这两条，托盘做出来也无处可用（用户点关闭 → 应用直接退出 → 图标随之蒸发，而 R1 的"退出时必须移除"会让这个过程看起来"很正常"）。另：R13 与既有两条记账（`~Application` 残留活窗口 / `m_running`-`Run`-`Exit` 语义未定义，见 `README.md` 技术债表）**同一区域**，初设时应一并复核。

### 框架侧残差登记 G-1~G-4（v1.7 新增 · 2026-09-19 代码实证）

Phase 12 与 Phase 14 交付的是**原计划的能力**；以下 4 项是**原计划未覆盖**、而 DesktopNest 真正需要的缺口。命名用 **`G-`（Gap）** 前缀，避免与全项目的决策编号惯例 `D-*`（如 `D-SEAM-1` / `D-DESK-1`）混淆。

| # | 残差 | 代码证据 | 影响里程碑 | 分类 |
|---|---|---|---|---|
| **G-1** ★ | **`WindowLayer::Desktop` 尚未实现——当前降级执行 `Bottom`** | `Win32PlatformWindow.cpp:863-868`（`if (layer == Desktop)` 只记 Warning）→ L882 走 `SetWindowPos(…, HWND_BOTTOM, …)`；**该 Warning 文案仍写 "spike pending"**——而 spike 已于 2026-09-15 六条判据全过（§7.1）⇒ **文案过期 + 能力未交付** | **M1 / M4**（硬前置） | **阻断项** |
| **G-2** | **`HICON` → `Image` 通路缺失** | `Decode/ImageDecoder.h` 仅 `DecodeMemory` / `DecodeFile`；`Core/Image.h` 无工厂；`HBITMAP` 只出现在 `GDIBackend` 内部（该头明写「HDC/HBITMAP/BitBlt 全是实现细节」） | M2 | **阻断项** |
| **G-3** | **无「工作线程 → UI 线程」投递机制** | 全库仅 **1 处** `PostMessageW`（`Win32PlatformApplication.cpp:382`，托盘宿主唤醒）；应用层**够不着 HWND**（框架隐藏之）⇒ 工作线程的通知无法变成 Framework Event | M4 | 记账项（`TimerEvent` 轮询可兜底） |
| **G-4** | **进程为系统级 DPI 感知（非 Per-Monitor V2）** | `Win32PlatformWindow.cpp:977` 注释预留替换点（`GetDeviceCaps` → `GetDpiForWindow`）；框架**无面向应用的屏幕 / DPI 查询 API**（`MONITORINFO` 仅用于最大化修正）；细则已记账于 `roadmap-deferred.md` 条 8 | M4 | 记账项（混合 DPI 下跨屏落点被系统缩放——§7.1 的 ×0.8 即此现象） |

**判据来源**：G-1 为「**已取证但未落地**」；G-2 为「**接口形态已定但通路未提供**」；G-3 / G-4 为「**框架未提供、且应用层够不着**」。四者均**不是**两个 Phase 的欠账，而是框架侧完成后的**二次勘察**结果。

**分类纪律**：G-1 / G-2 属**阻断项**（不做则对应里程碑无意义——G-1 不做则「Win+D 后仍可见」这一核心卖点不成立；G-2 不做则框里显示不出图标）；G-3 / G-4 属**记账项**（存在可接受的降级路径）。两类不混写。

### 7.1 R-1 实测结论（2026-09-15 spike 取证）

**取证环境**：`Windows 11 Pro for Workstations`，build **26220**（25H2 系列，**晚于**架构变更起点 24H2 / 26100）；双屏（主屏 1920×1080 raw DPI 92 / 副屏逻辑 1536×864 raw DPI 113 ⇒ **副屏 125% 缩放**）。
**工具**：`.workbuddy/spike/desktop_spike.cpp`（独立程序：5 条路线 + `--auto` 无人值守取证；被 `.gitignore` 覆盖，**不进仓库**）。

**判据与可信度**：「可见」= 窗口内 **9 点像素采样** ∩ `WindowFromPoint(窗口中心)` 命中自身。该探针**先经对照组验证**——同一台机器、同一份代码跑非 reparent 路线报 `9/9`、中心像素与窗口底色 `#0080A0` 逐位相同 ⇒ `0/9` 方可作实数。

**五条路线判决**：

| 路线 | 做法 | 判决 | 证据 |
|---|---|---|---|
| **A** | reparent 到 `WorkerW` 壁纸层（Wallpaper Engine / Fences 路线） | ❌ **判死（双重否决）** | ① **不可见**：9 点采样 `0/9`，`WindowFromPoint` 命中 `SysListView32`（桌面图标列表控件）② **换壁纸即死**：实测收到 `WM_DESTROY`（归因 = **外部销毁**），机制 = explorer 关闭重建 `WorkerW` ⇒ **父窗口销毁级联**（`DestroyWindow` 先销毁子窗口） |
| **B** | `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` 监测桌面层转前台时置顶自身 | ❌ 判死 | 钩子安装成功且**确实触发了** `SetWindowPos`（`[wpc] #2`）；但 Win+D 生效中窗口仍停在 z 序**最底 #197**、9 点采样 `0/9` ⇒ **置顶动作在 Win+D 期间无效** |
| **C** | 拦截 `WM_WINDOWPOSCHANGING` 的 `(-32000,-32000)` 移动（社区 “Pin Mode”） | ❌ **判死（前提不存在）** | `--raw` 对照组 + `--taskbar` 对照组（**加任务栏按钮**的普通窗口）**双双**证明：Win+D 期间窗口**一条 `WM_WINDOWPOSCHANGING` 都没收到**（全程只有启动时自己那一条）⇒ 该移动在本机**根本不存在**。「消失」的真因是桌面层被抬到所有窗口之上把它**盖住** |
| **D** | 挂到 `Progman` 子窗口 + 把自身放到子窗口 z 序顶端（压图标层之上） | ❌ 判死 | 结构**完全正确**（z 邻居实测「我之上=空 / 我之下=`SHELLDLL_DefView`」、`WindowFromPoint` 命中自身），但**零像素合成**：自身 DC 采样 = `CLR_INVALID`（`0xFFFFFFFF`）、`WM_PAINT` 到达 3 次而屏幕 `0/9` |
| **E** | **紧贴桌面窗口正上方**（插到 `GetWindow(Progman, GW_HWNDPREV)` 之后） | ✅ **通过** | 见下 |

**A 与 D 是同一个根因**：`Progman` 带 `WS_EX_NOREDIRECTIONBITMAP`（**raised desktop**）⇒ **Progman 自己绘制整个桌面、整棵子树不走 DWM 重定向** ⇒ 第三方窗口作为其子树成员**不参与合成**。⇒ **桌面窗口树（`WorkerW` 与 `Progman` 子窗口）整条路堵死**，「框在图标层下方」在本版本上**等价于框不可见**。

**Win+D 的真实机制**（z 序实测，推翻「把窗口移到 -32000」的社区说法）：

| 状态 | 实测 |
|---|---|
| 正常 | `Progman` 在顶层 z 序**底部 #197** |
| **Win+D** | **`Progman` 从 #197 抬到 #26**（所有应用窗口之上）；我们的窗口**位置、尺寸、可见位全部未变** |
| 两者 | topmost 带（#1…#10，含 `Shell_TrayWnd`）**恒在最上** |

⇒ 契约两侧各等价于一个 z 序位置：「Win+D 后仍可见」= 在**桌面窗口之上**；「被应用窗口覆盖」= 在所有**应用窗口之下**。**唯一交集 = 紧贴桌面窗口正上方**。该交集被一组精确对照验证（同一时刻、只差一位、可见性完全相反）：

| 运行 | Win+D 生效中 z 序 | 9 点采样 |
|---|---|---|
| **E** | **#26 本窗口** ｜ #27 `Progman` | **9/9 可见** |
| C（`--raw --taskbar`，作对照） | #26 `Progman` ｜ **#27 本窗口** | **0/9 不可见** |

**E 的实现要点（已实测）**：

1. **落点**：`SetWindowPos(hwnd, GetWindow(progman, GW_HWNDPREV), …)` —— 插到桌面窗口的**上一位之后**，即恰好压其上方；
2. **维持**：`EVENT_SYSTEM_FOREGROUND` 钩子（检测到 `Progman` / `WorkerW` 成为前台即重插）+ 主循环 `IsDirectlyAboveDesktop()` 校验兜底——实测 12 秒内 shell 分步抬升后被**自动重插 3 次**；
3. **对照事实**：`--topmost` 能活过 Win+D（`#8`、9/9 可见），但恒在应用窗口**之上**，不满足契约另一侧 ⇒ **与 E 不可互相替代**。

**顺带取到的平台事实**（与 Phase 13 **L6** 同族，DPI 立项时复核）：`SetParent` 进跨越虚拟屏的 `WorkerW` 后，窗口矩形被 **×0.8**（420×280 → 336×224，相对坐标 (750,80) → (600,64)）。已排除 `GetDpiForWindow`（全程 96）、`WM_DPICHANGED`（未收到）、进程 DPI 感知（=1）⇒ 定性为**跨 DPI 空间的坐标换算**（`0.8 = 96/120` = 副屏 / 主屏逻辑尺寸比，逐位吻合）。**纪律**：**reparent 后落点别指望系统保持，必须显式 `MapWindowPoints` 重定位**——本结论同时**修正**了早期「位移量 = 父客户区原点」的不严谨表述（同一操作两次实测落点不同：`(750,80)` vs `(600,64)`）。

**对框架的意义**：E **完全落在 Win32 平台层内部**——z 序走 `WM_WINDOWPOSCHANGING`、桌面抬升监测走平台层自装的 `SetWinEventHook` ⇒ **公共 API 零变更**，兑现 `WindowLayer.h`「平台如何达成该层级是实现的自由」的承诺；`Desktop` 档**无需向应用层暴露任何新接缝**。

**人工判据进展**（2026-09-15 更新；①②⑥ 依据 z 序 / 9 点采样**自动**实测，②③④ 为**用户手测**）：

### 7.2 R-3 实证：框内图标「功能阻断」+ 跨进程穿透不可行（2026-09-15 实测 + 核实）

**实测**：把图标拖到框矩形下方，**图标不可选中 / 双击**；框矩形之外一切正常。⇒ R-3 不是「视觉遮挡」，而是**功能阻断**——**框的可交互面积 = 它拦下的图标面积**。

**为什么不能「加个点击穿透」**（四方案逐一核实，此前未验；依据为官方文档原文或社区实证）：

| 候选 | 结论 | 依据 |
|---|---|---|
| `WM_NCHITTEST` 返回 `HTTRANSPARENT` | ❌ **跨进程无效** | MSDN：*"In a window currently covered by another window **in the same thread** (the message will be sent to underlying windows **in the same thread** …)"* ⇒ **只在同线程窗口之间传递**；图标层宿主 explorer 属**另一进程** |
| 同上 · 强行跨线程返回 | ❌ **有害** | 社区实证（virtualdub *HTTRANSPARENT is evil*）：跨线程返回会使**整个窗口（含子窗口）失去响应** |
| `WS_EX_TRANSPARENT` | ❌ 不适用 | **全窗口级** —— 框自身也收不到鼠标，等于不可交互 |
| `SetWindowRgn` 挖洞 | ⚠️ 跨进程有效，但有代价 | 区域外的点不属于窗口 ⇒ 鼠标落到下层图标；**代价 = 挖掉的区域无法绘制**，与「框内要显示成员列表」直接冲突 |

⇒ **结论**：R-3 是**结构性的**，只能靠**位置 / 面积**缓解（框倾向贴边·贴角），**无法用点击穿透消除**。本结论已核实依据，非推断。

## 8. 数据模型草案

**合并 / 拆出的语义已拍板**（见 §1.2：视图分组、零文件操作、恒一层、单向收编）。以下**字段格式**为倾向性提案，尚未经用户确认。

### 8.1 配置结构（`config.json`，置于程序目录）

```jsonc
{
  "version": 1,
  "boxes": [
    {
      "id": "box-a",
      "title": "工作文档",
      "state": "expanded",              // collapsed | expanded（只有二态，无 compact）
      "placement": {
        "monitor": "primary",           // 屏幕标识（多屏）
        "x": 0.02, "y": 0.05,           // 屏幕内相对比例
        "w": 220,  "h": 320             // DPI 无关逻辑尺寸
      },
      "members": ["box-b", "box-c"],    // 被本框收编的成员 id（不含自己；空数组 = 普通框）
      "active": "box-a"                 // 当前显示哪个成员，默认是自己
    },
    {
      "id": "box-b",
      "title": "学习资料",
      "state": "expanded",
      "placement": { /* 被收编前的摆放位置 —— 保留，拆出时按 §1.2 默认 1 恢复 */ },
      "members": [], "active": "box-b"
      // box-b 若已被 box-a 收编，则不作为顶层框渲染；其条目仍保留以便拆出恢复
    }
  ]
}
```

**相比 v1.0 的三处简化**：

| v1.0 字段 | v1.1 | 原因 |
|---|---|---|
| `state: compact` | 删除 | 二态模型里没有紧凑态 |
| `mergedChildren` + `activeChild`（索引） | `members` + `active`（**id**，非索引） | 索引在建/删成员后会错位；用 id 天然稳定 |
| `storageDir` | 删除 | 目录恒为 `storage/<id>/`（§8.2），字段冗余且可与 §8.3「磁盘为准」冲突 |

### 8.2 storage 目录结构（倾向）

`storage/<boxId>/` —— **每个框一个真实文件夹**，而非扁平目录 + 索引映射。

理由：配置损坏时文件不会变孤儿；同名文件跨框不冲突；用户在资源管理器里也能直接管理。

### 8.3 真相源（倾向）

**以磁盘为准**：框内列表由磁盘扫描得出，`config.json` 只存布局与分组关系；配合 `ReadDirectoryChangesW` 让外部改动同步到视图。

若反过来以配置为准，`config.json` 会成为"第二真相源"，用户手删文件后框里仍显示、双击报错。

### 8.4 合并语义：纯视图，零文件操作

**合并与拆出都不触碰 `storage/`**，成员各自保留 `storage/<成员id>/`，目录始终平级、不产生嵌套。

| 操作 | 磁盘 | 配置 | 视图 |
|---|---|---|---|
| 合并（B 被 A 收编） | 无变化 | `A.members += B` | B 的窗口消失 |
| 切换成员 | 无变化 | `A.active = 目标id` | A 的标题与内容整体换成该成员 |
| 拆出 B | 无变化 | `A.members -= B` | 新建 B 的窗口，位置按 §1.2 默认 1 恢复 |

**拖入文件的落点**：拖进合并框的文件，落到**当前 `active` 成员**的目录——合并框不额外拥有目录，它自己也只是成员之一（`active == 自己` 时落到自己的目录）。

**这条设计的价值**：把合并在数据层降级为"只写一行配置"，于是用户最大的一次不可逆风险（§7 R-2 移动真实文件）**不会被合并 / 拆出动作放大**——最容易手滑的操作恰好是最便宜的。
