| # | 事实 | 证据 |
|---|---|---|
| **K3** | `CreateWindowExW` 收到的 `w/h` 是**物理直传**（构造期**不**换算） | `src/Platform/Win32/Win32PlatformWindow.cpp:115-126` |
| **K4** | 构造期只把 DIP 目标尺寸**记下来**：`m_startupWidthDip = width; m_startupHeightDip = height;` | 同上 `:159-161` |

| **K6** ★★ | ★★ **为什么在那里——Phase 20 的崩溃修复注释**（本缺口的**成因**）：**调整窗口尺寸会同步派发 `WM_SIZE`**，而构造发生在 `Window` 的**成员初始化列表**中 ⇒ 回调 `Window::OnResized` 访问「声明在 `m_platformWindow` 之后、生命周期尚未开始」的成员 = **UB**（★ 实测：主屏 125% 下崩溃，错误码 **`0xC000041D`**）★ 而 **100% DPI 下"看起来正常"**：`DipToPixels(w, 96) == w` ⇒ 尺寸不变 ⇒ **`SetWindowPos` 是 no-op、一条消息都不发** ⇒ **缺口只在非 96 DPI 下存在** | 同上 `:150-158` |

### 1.3 ★★ 本稿实测（R1–R3，2026-09-28 · 1920×1080 @ DPI **120** = 125%）

> 方式：独立探针，`Application` + `Create("ECDI_Probe22", 800, 600)`（**默认 chrome**，未设 Borderless），三组读数。

| 组 | 时机 | 外框物理 | 客户区物理 | **外框 DIP** | 客户区 DIP | 根 widget（DIP） | 契约 |
|---|---|---|---|---|---|---|---|
| **R1** | **Create 后 / Show 前** | 800×600 | 782×553 | ★ **640×480** | 626×442 | 626×442 | ✗ **不符** |
| **R2** | **Show 后** | 1000×750 | 982×703 | **800×600** | 786×562 | 786×562 | ✓ 符合 |
| **R3** ★★ | Create 后**手动** `SetWindowPos(1000, 750)` | 1000×750 | 982×703 | **800×600** | 786×562 | **786×562** | ✓ 符合 |

★★ **R3 的三条读数（方案可行性的实测依据）**：① **不崩**（`Window` 已**完全构造** ⇒ K6 的 UB 条件不再成立）；② **`WM_SIZE` 同步派发** ⇒ 根 widget **立即**跟着变为 786×562；③ **此后 `Show()` 里的同尺寸调用成为 no-op** ⇒ **不产生二次调整**。

★ **R1 与 K6 的因果闭合**：R1 的 `640×480` **正是** `800 × 96/120` ⇒ 缺口 = 「**`Create` 之后、`Show` 之前，窗口的 DIP 总尺寸是 `w × 96/dpi` 而不是 `w`**」。★ 旁证：Phase 21 修测试时用 `WM_NCHITTEST` 的右边界阈值反推出的正是 **640** —— 与本实测逐位吻合。

### 1.4 缺口的可观测后果

| # | 后果 | 说明 |
|---|---|---|
| **K7-①** | **框架内部几何在 Show 前是"错的"** | 根 widget（= 客户区 DIP）在 Show 前是 **626×442**，Show 后才 **786×562** ⇒ **任何在 `Show` 之前按 DIP 布置/断言的控件都与 `Show` 之后不一致** |
| **K7-②** | **已在唯一处真实暴露** | `CaptionBar.HitTestDelegation` 在 125% 下失败（Bar 硬设 800 DIP 宽，而未 Show 的窗口只有 640 DIP ⇒ 靠右按钮落到窗口外 ⇒ 平台判成右边界）——**即 Phase 21 修的那处"测试 DPI 脆弱性"**。当时的处置是**测试侧规避**（用例开头 `Show()`）；**框架侧未处置** |
| **K7-③** | **纯 `96` DPI 环境不可见** | `DipToPixels(w, 96) == w` ⇒ 无差异（K6）⇒ 这条缺口**在 100% 缩放的机器上永远不会暴露** |

### 1.5 分界判据核对（审计 §3 三条）

| 判据 | 命中 | 依据 |
|---|---|---|
| **① 违反既有原则** | ★★ **命中** | K1 的「公共 API 语义恒为 DIP」在 `Create` → `Show()` 之间**不成立** |
| ② 平台有却被中途丢掉 | — | 不适用（不是"丢了信息"，是"换算落点晚"） |
| **③ 无替代路径** | ★ **命中** | 调用方**没有**干净的绕行方式：`Show()` 之前无法查询/设定正确的 DIP 几何（框架**没有客户区 DIP 查询 API**——**K8**，见 §1.6）；唯一"绕法"是**自己先 `Show()`**，但那会**改变语义**（Show 是配置期/运行期分界线，且会导致窗口提前可见） |

⇒ **判定：`该修` 的缺陷**（命中两条），**不是形态记账**。

### 1.6 附带事实（K8，影响 D2 决策）

| # | 事实 | 证据 |
|---|---|---|
| **K8** | ★ **框架没有"客户区 DIP 尺寸"的查询 API**——`Window.h` 只有**设定型**的 DIP 入参（`SetCaptionHeight` / `SetResizeInset`），而平台层（`GetPlatformWindow()`）自述「**框架自身不用它**——Widget / 布局 / 事件一律 DIP，换算只发生在边界」（`Window.h:103`） | `Window.h` 全文 + `:103` |

### 1.7 ★★ Q2 实测：`WM_SIZE` 计数（2026-09-28 · 探针 v2 新增 SubClass 计数器）

> ★ **量具修正说明**：探针 v1 的 `ok` 判据误用**客户区**折 DIP（契约口径是**外框**，K2）⇒ 会对 R2 **误报"不符"**；v2 已修正，并新增 `WM_SIZE` 计数器（`SetWindowLongPtrW(GWLP_WNDPROC)` SubClass；**先转发、后记录**，记录时读根 widget）。

| 阶段 | 基线（现状） | mode C（模拟「Create 末尾补一次」） |
|---|---|---|
| `Create` 后 | 根 widget **626×442** | 同 |
| `Create` 末尾新增 `SetWindowPos(1000, 750)` | —（不存在此步） | ★ **1 次** `WM_SIZE` ⇒ 786×562 |
| `Show()` 期间 | ★ **2 次** `WM_SIZE`（786×562，然后 **786×562 尺寸未变**） | ★ **1 次**（786×562，尺寸未变） |
| **「挂表后」合计** | **2 次** | **2 次** |

★★ **三条结论**：

1. **总次数不变**——修前修后都是 **2 次**；新增的那一次 `SetWindowPos` 换来的是 `Show()` 里**少一次** ⇒ ★ **本 Phase 不引入额外的布局开销**，只是把「**有效的那一次**」**提前**到 `Create` 末尾（★ 这正是本 Phase 的目的：让 `Create` 返回时状态正确）。★ 如实标注：`Create` 期的布局次数**确实 +1**（626×442 那次之后多一次 786×562），但 `Show()` 期**同步 −1**，净和为 0。
2. ★★ **`SetWindowPos` 在尺寸未变时既不改尺寸、也不派发 `WM_SIZE`**——mode C 的 `Show()` 只剩 1 次，而基线的 `Show()` 有 2 次 ⇒ **差值 1 次归因于那次 `SetWindowPos`**（★ 归因方式 = 两次实验的差值排除，**非直接测量单条消息**）。⇒ ★★ **实测证实了 `Win32PlatformWindow.cpp:181` 注释里的那句「`dpi == 96` 时尺寸不变 ⇒ `SetWindowPos` 为 no-op」**（此前只是推断）。
3. ★★ **直接支撑 D3**——修后 `Show()` 里的 `SetWindowPos` 变成 **no-op ⇒ 连消息都不发** ⇒ **把它作为「跨屏兜底」保留下来的运行期成本 = 0**。★ 评审的表述可直接引用：**`Create` 负责建立契约，`Show()` 负责最终校正**——两者**不重复做功**。

## 2. 需求（R1–R5）

| # | 需求 | 判据 |
|---|---|---|
| **R1** ★★ | **让契约成立**：`Application::Create(title, w, h)` **返回后**（★ **不待 `Show()`**），窗口的**外框 DIP 尺寸 == `w × h`** | 探针 R1 的 `外框 DIP` 列 == 请求值；非 96 DPI 下可测 |
| **R2** ★★ | **零回归**：`dpi == 96` 时与改前**行为一致**（★ v1.1 采纳评审 §8——**拆两层**：**① 数学保证** = G5 恒等 `DipToPixels(w,96) == w` ⇒ 新路径**必须是** no-op；**② 行为验收** = 四工具链既有 **261** 用例全绿 + 关键读数一致） | 96 DPI 下的读数与改前一致；四工具链既有 **261** 用例全绿 |
| **R3** ★ | **不引入 UB**：构造期回调陷阱必须在**设计上排除**（落点必须在 `Window` **完全构造之后**），而不是"恰好没触发" | 落点论证 + 125% 实测不崩（R3 已给先例） |
| **R4** ★ | **不破坏既有语义**：`Show()` 仍是「配置期 → 运行期」的分界线；★ **`Show()` 里的 DPI 复核必须保留**（跨屏场景的兜底——K6 自述"Show 时窗口的显示器关联才确定"） | `Show()` 的分界线语义不变；`Show()` 后几何仍正确（R2） |
| **R5** | **可测**：须有**无头 / 自动化可断言**的判据（沿 Phase 21 的模式：内核逻辑与平台分离，或直接用探针式读数断言） | 新增用例能在四工具链跑；★ 不得只靠目视 |

## 5. 待实测 / 待定（Q1–Q3）

| # | 问题 | 处置 |
|---|---|---|
| **Q1** ★ | **跨屏场景**：窗口 `Create` 在**非主屏**（或下一屏 DPI 不同）时，`Create` 期的 `GetDpiForWindow` 是否**可靠**？（K6 自述"Show 时窗口的显示器关联才确定"⇒ 暗示构造期可能不准） | ★ **本机单屏（1920×1080）⇒ 不可测** ⇒ 记为待实测；★ **缓解 = D3 保留 Show 复核**（即使 Create 期取错，Show 也会修正）⇒ **不阻塞设计**。★★ **口径声明（v1.1 采纳评审 §6）**：`Create` 期应用的 DPI 是「**当前 Win32 窗口状态所能获得的 DPI**」，**不承诺**它等于"最终所在显示器的 DPI"——★ 设计文档与源码注释都须守住这条，**禁止**把这次 `GetDpiForWindow` 描述成"最终显示器 DPI"（否则会误导后来者以为跨屏问题已解决） |

| **Q3** | 若 D0 选 (b)：`Window::OnResized` 访问的成员是否**全部**声明在 `m_platformWindow` 之前 | 读源码逐条核（**选 (a) 则本项作废**） |
