> **不是「框架不能显示图标」，而是「框架拿不到系统图标的像素」。**

`.ico` **文件**走既有 `DecodeFile` 已经能出图（WIC）；缺的是**运行时由系统给出的句柄**（文件类型图标 / 文件夹图标 / 资源图标等）。

## 2. 需求条目（R1–R5）

### R1：新增「系统图标」这一图像来源

**边界**：应用层能**凭一个路径**得到该路径对应的**系统图标**（shell 语义），结果 = 既有的 `Image`。
★ 语义是「**该路径的图标**」，**不是**「该路径指向的图像内容」——后者是 `DecodeFile` 的事。

### R2：零 Win32 类型泄漏

`HICON` / `HBITMAP` / `SHFILEINFOW` **一律不得出现在公共 API**（沿核心不变量「**框架层零 Win32**」）。

### R3：像素契约与既有 `Decode` 一致

输出 = **32bpp premultiplied BGRA** / top-down / `stride == width * 4`（与 `DecodeFile` **同口径**，便于统一断言）。

### R4：错误契约与既有 `Decode` 一致

失败 ⇒ **空 `Image`（`width == 0`）** + `Logger` 记 Error + **不抛异常**（沿 **K5**，不新增错误处理范式）。

### R5：资源生命周期自洽

`HICON` / `HBITMAP` 的销毁必须**无条件**（**含所有失败路径**）；**调用方零负担**（不可要求应用层 Destroy）。

## 3. 决策点（D0–D5，含倾向）

| # | 决策 | 倾向 | 理由 / 备选 |
|---|---|---|---|
| **D0** ★★ | **`SHGetFileInfo` 这一层放框架还是应用层？** | ★ **放框架**——应用层**只给路径** | **A1（框架）**：一行调用、最贴「人人能用」的项目定位 · **A2（应用层）**= 框架只提供 `HICON`→`Image` ⇒ 应用层**必须自己 `#include <shellapi.h>`** 并管句柄 ⇒ 与「应用层不该知道 Win32」相悖 |
| **D1** | **API 落哪个命名空间** | **`ECDI::Decode`**（与 `DecodeFile` 同级） | 它是「得到 `Image`」的**第三个来源**，语义同族；备选 = 另立命名空间（**YAGNI**） |
| **D2** | **图标尺寸** | 倾向**先只支持大图标（32px）** | `SHGetFileInfo` 的 `SHGFI_LARGEICON` / `SHGFI_SMALLICON`；更大（48 / 256）需 `SHGetImageList` ⇒ 待消费者（**N4**） |
| **D3** ★ | **内核 = `HICON`→`Image` 转换器；外层 = 路径→`HICON`** | **两层都要**（内核必需，外层由 **D0** 决定形态） | 内核是**唯一通路**（**K2**）；外层的存在与否正是 **D0** |
| **D4** | **老式图标（无 alpha，靠 mask）如何处理** | ★ 需求**只定「必须正确处理 mask」**——**具体像素算法留初设** | 现代 32bpp 图标自带 alpha；但 `GetIconInfo` 同时给 `hbmColor` + `hbmMask` ⇒ 不处理会让透明区**变黑**。★ **需求阶段不冻结算法**（评审 §6）——否则会把实现方案提前钉死 |
| **D5** | **[预乘 alpha](premultiply) 在哪做** | **必须在框架内做** | `GetDIBits` 产出的是「直通 RGB + alpha」，而 `Image` 契约要求 **premultiplied**（否则混合色偏，Phase 11 已立此契约） |

## 4. 非目标（YAGNI 圈定）

| # | 不做 | 理由 |
|---|---|---|
| **N1** | **文件缩略图**（`IShellItemImageFactory`） | 是**另一条能力**（内容缩略图 ≠ 类型图标）；消费者未出现 |
| **N2** | **图标缓存** | 先看真实调用频率；且 `Decode` 既有 API **亦无缓存**（per-call 风格，不新立范式） |
| **N3** | **异步 / 工作线程解码** | 属 **D-4**（工作线程 → UI 投递）的范围 |
| **N4** | 多尺寸 / **DPI 感知的图标选择** | 与 Phase 20 的 DPI 有交互，但**消费者未出现** ⇒ 记账 |
| **N5** | `.ico` **文件**解码 | ★ **K1：WIC 已支持** ⇒ 无需本阶段做 |
| **N6** ★ | ★★ **为本阶段新建公共抽象**——`IIconProvider` / `Win32IconProvider` / `ShellService` 之类 | ★ **评审 §12 明确警告**：**Q3（可测性）极易把设计带向「造一个 provider 接口」**。但需求只证明了「**需要 `HICON`→`Image`** / **需要 `path`→`HICON`** / **需要测试**」——**没有**证明「**未来有多个 provider**」；也**不应**为「未来可能有 Linux 图标」预建跨平台层。⇒ 落点 = **平台层内部**（如 `src/Platform/Win32/`），**公共面只加一个函数** |

## 5. 待决问题（Q1–Q4）

| # | 问题 | 为何重要 |
|---|---|---|
| **Q1** ★★★ | ★ **初设第一优先级**：**API 的确切形态与命名**（**D0** 拍板后）· 是否用 `SHGFI_USEFILEATTRIBUTES`（拿「类型图标」而**不碰磁盘**）· ★★ **与 Q4 耦合**——该参数正是「不存在路径能否出图标」的决定因素 ⇒ **两者必须一起定** | 决定应用层的调用形态与**副作用**。★ **命名约束（评审 §19）**：**不得与既有 `.ico` 文件解码语义撞车**——`DecodeIcon` 会被读成「`.ico` → `Image`」（★ **该能力 K1 已存在**）⇒ 名称须体现 **System / Shell / FileIcon** 之一（具体待初设定） |
| **Q2** | **COM / shell 初始化边界**——★ **不得直接照搬 WIC 的经验**（评审 §10） | ★ 须回答**四问**：**谁**负责 COM（本函数 / 调用方 / 平台层既有）· **何时**（每次调用 / 一次）· 是否**要求调用线程已初始化** · ★ **本函数自行初始化是否会与现有 COM apartment 冲突**。★ WIC 的 `ComScope` 先例（`WicImageDecoder.cpp:164`）**只能作参考、不能作依据**——两者是不同的 API 族与不同的线程上下文 |
| **Q3** ★ | **可测性**：`SHGetFileInfo` 依赖 shell（**无头测试能否跑？**）⇒ 内核（`HICON`→`Image`）与外壳（shell 调用）如何**分离**以保无头可测 | 决定本阶段**能否代码级闭环**（沿用 Phase 19/20 的「真翻译路径」纪律） |
| **Q4** | 路径**不存在**时的语义（★ **与 Q1 耦合**） | ★ 倾向**仍按「路径类型」取图标**——**R1 定义的是「该路径的图标」，不是「该路径实际存在对象的图标」**；⇒ 「不存在 + 有扩展名」仍可返回该类图标（**实际价值高**）。★ **须实测 Windows API 行为后再冻结，不靠推断**（评审 §9） |

## 6. 验收（A1–A5）

| # | 验收 | 判定方式 |
|---|---|---|
| **A1** | 给定真实路径（**文件** / **文件夹** / **不存在**）⇒ 拿到非空 `Image`，`DrawImage` 能画出 | 应用侧目视 + 断言（★ **场景细化见 A6**） |
| **A2** | 像素契约：**premultiplied BGRA** / top-down / `stride == width*4`（与 `DecodeFile` **同口径**可断言） | 自动化 |
| **A3** | 失败路径：**资源全销毁（无泄漏）** + 返回空 `Image` + 已记 Error | ★ **详设须先冻结「资源清单」**（`HICON` / `hbmColor` / `hbmMask` / `HDC`（若用）/ DIB 缓冲 × **成功路径 / 中途失败路径** 两栏）——**不能只验「没有崩」**（评审 §17）；★ 特别须明确 **`GetIconInfo` 返回的 bitmap ownership**（**不可与 `HICON` 的 ownership 混同**） |
| **A4** | **零回归**：既有 **252** 用例全绿 · **公共头 92 → 92（文件数不变）** · 四工具链 | ★★ **口径须精确**（评审 §18，**本稿原写得不严谨**）：**「头文件数不变」≠「API 无变化」**——本阶段**确实新增 1 个公共 API**（**既有头追加**）⇒ 表述应为「**头文件：0 新增 / 公共 API：+1**」。★ 这与 **Phase 20.1 的 ABI 口径**是**同一类问题**：**数量不变 ≠ 契约不变** |
| **A5** | **无头可测**：至少**内核转换的可测部分**有自动化用例（边界由 **Q3** 的答案决定） | 自动化 |
| **A6** ★ | ★ **Shell 场景矩阵**（评审 §15 补充）——★ **不可只测一个 `.txt` 就宣布完成** | ★ `directory` **有独立 shell 语义**，**不得**当作「没有扩展名的文件」处理：**① 已存在普通文件** ⇒ 类型图标 · **② 已存在文件夹** ⇒ 文件夹图标 · **③ 不存在 + 有扩展名** ⇒ **答案依赖 Q1/Q4** · **④ 不存在 + 无扩展名** ⇒ **答案依赖 Q1/Q4** · **⑤ 异常 / 不支持路径** ⇒ 错误契约（**R4**） |
