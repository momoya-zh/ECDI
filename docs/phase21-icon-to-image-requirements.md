## 1. 背景与现状事实

### 1.1 动机

`desktopnest-roadmap.md` 里程碑 **M2「内容」**（真实文件列表 + **图标提取** + 双击打开 + 拖入落盘）的前置 = Phase 14 ✅ **+ G-2**。§5 分类纪律明写：「**阻断项只余 G-2**（不做则框里显示不出图标）」。

★ 但 **desktop 应用侧已推迟**（2026-09-22，前置 = 框架侧队列走完）⇒ 本阶段的**消费者是未来的**。这一点如实记在 **§8**。

### 1.2 现状勘察（K1–K6，全部带行号）

| # | 事实 | 证据 |
|---|---|---|
| **K1** | ★★ **WIC 已经能解 `.ico` 文件**——`ImageDecoder.h` 明写「实际支持格式由系统 WIC 解码器决定（BMP/PNG/JPEG/GIF/TIFF/**ICO** 等）」 | `include/ECDI/Decode/ImageDecoder.h:12-14` |
| **K2** | ★★ **缺口只在「运行时拿到的 `HICON` 句柄」**——全库 `GetIconInfo` / `GetDIBits` / `SHGetFileInfo` **零命中** | 全库 grep（**0 / 0 / 0**） |
| **K3** | `Image` 契约已定且足够：**32bpp premultiplied BGRA** / top-down / `stride >= width*4` / 空图像语义 | `include/ECDI/Core/Image.h:10-24` |
| **K4** | `Decode` 是**无状态自由函数**（非类），实现在**平台层**——既有两个入口 `DecodeMemory` / `DecodeFile` | `Decode/ImageDecoder.h:22,26` · `src/Platform/Win32/WicImageDecoder.cpp:205,215` |
| **K5** | `Decode` 的既有错误契约：**失败返回空 `Image`（`width==0`）+ `Logger` 记 Error + 不抛异常** | `ImageDecoder.h:11-13` · `WicImageDecoder.cpp:208-210` |
| **K6** | 框架**已有 `HICON` 处理先例**，但都在平台层内部、且只用于「**把图标交给系统显示**」而非「**取像素**」：托盘图标（`LoadImageW` → `NOTIFYICONDATAW`）· 窗口类图标（`wc.hIcon`） | `Win32PlatformApplication.cpp:249,278,308,602` · `Win32WindowClass.cpp:58` |

★★ **K1 + K2 合起来是本阶段的精确边界**：

> **不是「框架不能显示图标」，而是「框架拿不到系统图标的像素」。**

`.ico` **文件**走既有 `DecodeFile` 已经能出图（WIC）；缺的是**运行时由系统给出的句柄**（文件类型图标 / 文件夹图标 / 资源图标等）。

### 1.3 相关子系统现状（不改变，但决定落点）

| 子系统 | 现状 | 对本阶段的意义 |
|---|---|---|
| `Image` | 值类型；premultiplied BGRA 契约（Phase 11 立） | ★ **零新契约**——目标是「产出既有的 `Image`」 |

## 2. 需求条目（R1–R5）

### R1：新增「系统图标」这一图像来源

**边界**：应用层能**凭一个路径**得到该路径对应的**系统图标**（shell 语义），结果 = 既有的 `Image`。
★ 语义是「**该路径的图标**」，**不是**「该路径指向的图像内容」——后者是 `DecodeFile` 的事。

### R2：零 Win32 类型泄漏

`HICON` / `HBITMAP` / `SHFILEINFOW` **一律不得出现在公共 API**（沿核心不变量「**框架层零 Win32**」）。

### R3：像素契约与既有 `Decode` 一致

输出 = **32bpp premultiplied BGRA** / top-down / `stride == width * 4`（与 `DecodeFile` **同口径**，便于统一断言）。

### R4：错误契约与既有 `Decode` 一致

失败 ⇒ **空 `Image`（`width == 0`）** + `Logger` 记 Error + **不抛异常**（沿 **K5**，不新增错误处理范式）。

### R5：资源生命周期自洽

`HICON` / `HBITMAP` 的销毁必须**无条件**（**含所有失败路径**）；**调用方零负担**（不可要求应用层 Destroy）。

## 3. 决策点（D0–D5，含倾向）

| # | 决策 | 倾向 | 理由 / 备选 |
|---|---|---|---|
| **D0** ★★ | **`SHGetFileInfo` 这一层放框架还是应用层？** | ★ **放框架**——应用层**只给路径** | **A1（框架）**：一行调用、最贴「人人能用」的项目定位 · **A2（应用层）**= 框架只提供 `HICON`→`Image` ⇒ 应用层**必须自己 `#include <shellapi.h>`** 并管句柄 ⇒ 与「应用层不该知道 Win32」相悖 |
| **D1** | **API 落哪个命名空间** | **`ECDI::Decode`**（与 `DecodeFile` 同级） | 它是「得到 `Image`」的**第三个来源**，语义同族；备选 = 另立命名空间（**YAGNI**） |
| **D2** | **图标尺寸** | 倾向**先只支持大图标（32px）** | `SHGetFileInfo` 的 `SHGFI_LARGEICON` / `SHGFI_SMALLICON`；更大（48 / 256）需 `SHGetImageList` ⇒ 待消费者（**N4**） |
| **D3** ★ | **内核 = `HICON`→`Image` 转换器；外层 = 路径→`HICON`** | **两层都要**（内核必需，外层由 **D0** 决定形态） | 内核是**唯一通路**（**K2**）；外层的存在与否正是 **D0** |
| **D4** | **老式图标（无 alpha，靠 mask）如何处理** | 倾向**按 mask 合成** | 现代 32bpp 图标自带 alpha；但 `GetIconInfo` 同时给 `hbmColor` + `hbmMask` ⇒ 不处理会让透明区**变黑** |
| **D5** | **[预乘 alpha](premultiply) 在哪做** | **必须在框架内做** | `GetDIBits` 产出的是「直通 RGB + alpha」，而 `Image` 契约要求 **premultiplied**（否则混合色偏，Phase 11 已立此契约） |

## 4. 非目标（YAGNI 圈定）

| # | 不做 | 理由 |
|---|---|---|
| **N1** | **文件缩略图**（`IShellItemImageFactory`） | 是**另一条能力**（内容缩略图 ≠ 类型图标）；消费者未出现 |
| **N2** | **图标缓存** | 先看真实调用频率；且 `Decode` 既有 API **亦无缓存**（per-call 风格，不新立范式） |
| **N3** | **异步 / 工作线程解码** | 属 **D-4**（工作线程 → UI 投递）的范围 |
| **N4** | 多尺寸 / **DPI 感知的图标选择** | 与 Phase 20 的 DPI 有交互，但**消费者未出现** ⇒ 记账 |
| **N5** | `.ico` **文件**解码 | ★ **K1：WIC 已支持** ⇒ 无需本阶段做 |

## 5. 待决问题（Q1–Q4）

| # | 问题 | 为何重要 |
|---|---|---|
| **Q1** ★★ | **API 的确切形态与命名**（**D0** 拍板后）；是否用 `SHGFI_USEFILEATTRIBUTES`（拿「类型图标」而**不碰磁盘**） | 决定应用层的调用形态与**副作用**（不碰磁盘意味着不存在路径也能出图标） |
| **Q2** | **COM / shell 初始化要求**：`SHGetFileInfo` 是否需要 `CoInitializeEx`？ | WIC 路径已有 `ComScope` 先例（`WicImageDecoder.cpp:164`）⇒ 需确认是否同款处理 |
| **Q3** ★ | **可测性**：`SHGetFileInfo` 依赖 shell（**无头测试能否跑？**）⇒ 内核（`HICON`→`Image`）与外壳（shell 调用）如何**分离**以保无头可测 | 决定本阶段**能否代码级闭环**（沿用 Phase 19/20 的「真翻译路径」纪律） |
| **Q4** | 路径**不存在**时的语义 | 返回「未知类型」通用图标（shell 默认行为）还是空 `Image`？两者都不算错，但**必须明确** |

## 6. 验收（A1–A5）

| # | 验收 | 判定方式 |
|---|---|---|
| **A1** | 给定真实路径（**文件** / **文件夹** / **不存在**）⇒ 拿到非空 `Image`，`DrawImage` 能画出 | 应用侧目视 + 断言 |
| **A2** | 像素契约：**premultiplied BGRA** / top-down / `stride == width*4`（与 `DecodeFile` **同口径**可断言） | 自动化 |
| **A3** | 失败路径：**资源全销毁（无泄漏）** + 返回空 `Image` + 已记 Error | 自动化 + 静态审查 |
| **A4** | **零回归**：既有 **252** 用例全绿 · 公共头 **92 → 92**（**净增 0 文件**）· 四工具链 | 用户执行 |
| **A5** | **无头可测**：至少**内核转换的可测部分**有自动化用例（边界由 **Q3** 的答案决定） | 自动化 |
