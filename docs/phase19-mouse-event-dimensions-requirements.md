## 1. 背景与现状勘察

### 1.1 立项由来

**用户口径（2026-09-22）**：「先做缺陷修复的优先级更高」——框架侧修复 / 补齐优先于 desktop demo（详见 `framework-defect-audit.md` §2）。本项排**第 ①** 位，理由：① **契约错误**（不是缺能力）；② **纯追加、零破坏**；③ **已有两处为它写的手工状态，越晚改越贵**；④ 顺带**解锁 `roadmap-deferred` #36**（横向滚轮）；⑤ 它是**将来一切"按住拖动"类交互的地基**。

### 1.3 一条会定形态的事实（F-1）

**Event 层的既有原则是「轻量、只表示已发生的事实、原始值不归一化」**（K6 的 Wheel 注释即其落款，Phase 2 立）。⇒ 本项的形态**不是**"给鼠标事件加一个 `IsDragging()`"这类**语义结论**，而是**把平台已经给出的原始位原样带过来**：按键位与修饰键位。

**这条同时决定了"加在哪"**：它们不是某个子类独有的信息，而是**四类鼠标事件共有的"当时状态"** ⇒ 倾向落在**基类** `MouseEvent`（§3-D1）。

### 1.4 已被证伪的两个替代方案（先排除）

| 方案 | 为什么不成立 |
|---|---|
| **让控件自己维护布尔**（现状做法，K7） | ① 每加一个"按住拖动"的消费者就要重写一遍（**已有 2 份**）；② 各控件自行维护必然**与"捕获"语义纠缠**（拖出控件外、失去焦点、抬起落在别处等边界各自处理）⇒ 状态漂移 |
| **用 `GetKeyState` 在消费侧现查** | ① 它查的是**查询时刻**的状态，而事件描述的是**事件发生时刻**——两者在消息队列积压时**不等价**；② 把一次平台查询推迟到每个消费者各做一次，重复且易错 |

## 2. 需求条目

### 2.1 信息维度 · R1–R3

| # | 需求 | 说明 |
|---|---|---|
| **R1** | **携带"此刻按下的鼠标键集合"** | 来源 = `wParam` 的 `MK_LBUTTON`/`MK_RBUTTON`/`MK_MBUTTON`/`MK_XBUTTON1`/`MK_XBUTTON2`；**是"状态"**，与 `MouseButtonEvent` 已有的"**本次事件是哪个键**"（`MouseButton`）**正交并存** |
| **R2** | **携带"此刻的修饰键状态"** | 来源 = `wParam` 的 `MK_SHIFT`/`MK_CONTROL`；**术语与键盘侧对齐**（K5 的 `KeyModifier`）——「一个概念只用一个词」 |
| **R3** | **四类鼠标事件同源** | Move / ButtonDown / ButtonUp / Wheel **都带**这两维（都是"当时状态"，不是某类独有） |

### 2.2 语义与边界 · R4–R6

| # | 需求 | 说明 |
|---|---|---|
| **R4** | **原始值不归一化** | **照抄平台位**，不做语义解释（不提供 `IsDragging()` 之类结论）、不裁剪、不排序——沿用 K6 的既有落款 |
| **R5** | **零破坏** | 纯**追加**：现有构造点 / 消费点**逐字不动**；无新纯虚、无签名破坏。★ **v1.1 精确化**：该"逐字不动"指**测试 22 处构造点 + 全部消费点**（靠**带默认值的尾形参**实现）；**翻译器 5 处必然修改**——那正是本项的实现本体 ⇒ 口径见初步设计 **§3.2 / 契约 C5** |
| **R6** | **默认值与"没有信息"可区分** | 未按下任何键时集合应为"**空**"，而不是"未知"——即**不引入三态**（有 / 无 / 未知），避免消费者写无意义的分支 |

### 2.3 顺带解锁 · R7（可选纳入）

| # | 需求 | 说明 |
|---|---|---|
| **R7** | **为 #36（横向滚轮）留出接缝** | 本项**不做** `WM_MOUSEHWHEEL` 翻译，但**轴 / 修饰键的表示方式**一旦定下，横向只需在既有维度上加"轴"——§6-Q5 记录该接缝，**由用户决定是否本次一并做** |

## 3. 决策点（含倾向）

| # | 决策点 | 倾向 | 依据 |
|---|---|---|---|
| **D0** | **修饰键用什么类型** | **复用既有 `KeyModifier`**（不新造 `MouseModifier`） | K5 已有现成类型与查询方法；「一个概念只用一个词」；教学型框架不应为同一概念留两套词 |
| **D1** | **落在哪一层** | **基类 `MouseEvent`** | §1.3 F-1：四类共有 + 都是"当时状态"；只有 `MouseButtonEvent` 的 `MouseButton` 才是子类独有 |
| **D2** | **"按下的键集合"用什么表示** | **留初设**（位掩码 / `MouseButton` 的集合语义 / 一组 `bool`），本稿只锁**语义** | 需求阶段不展开接口设计；候选形态见 §6-Q1 |
| **D3** | **`Alt` 要不要** | **不做** | `WM_MOUSEMOVE` 的 `wParam` **不提供** `MK_ALT`（平台事实），要它须额外 `GetKeyState(VK_MENU)`。⚠️ 这会造成**键鼠不对称**（键盘有 `IsAltDown`、鼠标没有）——**须在文档中显式声明为有意取舍**，并记重启条件 |
| **D4** | **是否简化 K7 的两处手工状态** | **不简化** | `m_dragging` / `m_mouseDown` 还承担**捕获语义与拖选职责**（K8），不只是"按键状态"；简化会把本项范围扩成"重构两个控件" ⇒ 违反"纯追加"（R5） |
| **D5** | **命名**（`GetPressedButtons()` / `GetModifiers()` / …） | 留初设 | 与既有 `GetMouseX` / `GetButton` / `GetDelta` 风格一致即可 |
| **D6** | **`R7`（横向滚轮）是否并入本次** | **倾向不并入**（本项保持"补维度"的单一目的）；**但**若评审认为并入更省，则本项升为"输入维度补全" | 单一职责；#36 另有"平台未翻译 `WM_MOUSEHWHEEL`"这一段工作量 |

## 6. 留给初步设计的问题（Q1–Q6）

> ★ **v1.1：六问均已在初步设计定案**——Q1→§2.1 · Q2→§3.3（陷阱表 + 用例 T19-4）· Q3→§3.2（**沿用 `isDoubleClick` 既有先例**）· Q4→§7（**走 `FakeHost` 真翻译路径**）· Q5→§2.4 · Q6→§2.3。

| # | 问题 |
|---|---|
| **Q1** | **D2 的候选形态比较**：位掩码（`0x1 << MouseButton`）vs 一组 `bool` vs 一个小集合类型——各自的 API 可读性、与 `MouseButton` 既有枚举的关系、以及"教学友好"的程度 |
| **Q2** | ★ **`MK_XBUTTON1/2` 的陷阱**：`wParam` 低位是 `MK_XBUTTON1/2`，而**具体是哪个 X 键**在 `wParam` **高位**（`GET_XBUTTON_WPARAM`）——初设须把两处语义写清，避免混用 |
| **Q3** | 构造点如何**最小改动**地传参（现有 4 处构造调用）——是否需要带默认值的尾形参以兼容次级构造点 |
| **Q4** | **测试承载**：`MouseEvent` 的断言怎么写最省（测试内直接构造事件？还是走翻译器 + 假 Host 的既有路径——Phase 7.2 的 `FakeHost` 先例）？ |
| **Q5** | **R7 接缝的精确形态**：若将来做横向滚轮，"轴"是加在 `MouseWheelEvent`（`deltaX/deltaY`）还是新增事件类型 |
| **Q6** | **与 `KeyModifier` 复用后的一致性核对**：键盘侧 `IsAltDown()` 在鼠标事件上**不存在**——是"提供的查询更少"还是"提供一个恒 false 的 `IsAltDown` 会造成误解"（D3 的用户可见后果，须在初设给出措辞） |
