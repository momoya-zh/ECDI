1. ★★ **差值有正有负、且不为常数**（+2 / −2 / 0 / 0 / −1 / 0 / −1 @px=14；+3 / −1 / 0 / −1 / 0 / +1 / +1 @px=20）⇒ **不存在「减一个固定量」的修法** ⇒ 需求稿备选 (a)「让 FT 对齐 GDI」**在数学上不成立**。

### 2.3 ★ GDI 侧的能力边界（实测——决定方案 (b) 在 GDI 侧是否可实现）

| 手段 | 实测结果 | 结论 |
|---|---|---|
| `GetFontData(dc, 'head'/'hhea'/'OS/2', …)` | ★★ **恒返回 `GDI_ERROR`**（屏幕 DC 与内存 DC 均如此；字体确为 TrueType——`TMPF_TRUETYPE` 已置位） | **GDI 侧读不到原始字体表** |
| `GetOutlineTextMetricsW` | **可用**（SimSun 256 B / Arial 342 B…）——给 `otmAscent` / `otmDescent` / `otmEMSquare` / `otmMacAscent` / `otmMacDescent` / `otmMacLineGap` | 唯一可用的「设计度量」通道 |
| `GetTextMetricsW` | 可用——`tmAscent` / `tmDescent` / `tmInternalLeading` / `tmExternalLeading`，且实测 **`tmHeight == tmAscent + tmDescent` 恒成立**（`tmInternalLeading` **含在 `tmAscent` 内**） | 主通道 |

★ **这对设计是硬约束**：**方案 (b) 若把语义定义成「读 `hhea` 计算」，GDI 侧根本无法照做**（`GetFontData` 不可用、OTM 也不含 `hhea`/`OS/2` 的行距字段）。⇒ **语义必须落在「两侧都够得着」的量上**——这是 §3 D31-A 的选型约束。

## §3 决策（D31-A..D31-F）

### D31-A ★★★ 行高语义选型（D1 第 ① 步——**本稿第一决策**）

**三个候选语义**（★ 全部**由 ECDI 定义**，不取自任一现有实现）：

| | **S1 = 行框高度（行推进量）** | **S2 = 字体推荐行距** | **S3 = 内容盒高度** |
|---|---|---|---|
| **定义** | 逐行排布时**相邻两行基线的距离**，= 该字号下容纳「字形盒 + 行间呼吸」的最小行推进量；★ **由 ECDI 定义为「行推进量」这一排版概念**，不宣称等于任何字体表字段 | 「字体设计者期望的行距」——直觉上 = `hhea` 的 `ascender − descender + lineGap` | 仅 `ascent + descent`（不含任何行距），= 字形紧贴的盒高 |
| **两侧可实现性** | ✅ **GDI**：`tmHeight`（现值，即 `tmAscent + tmDescent`，internal leading 已含）；✅ **FT**：`metrics.height`（现值）。⇒ **两侧都有直接量** | ⚠️ **GDI 不可实现**——需读 `hhea`/`OS/2`，而 `GetFontData` **实测恒失败**（§2.3）；OTM **不含**这些字段 | ⚠️ GDI 需**剔除** `tmInternalLeading`（可行）；FT 需 `ascender−descender`（不含 lineGap，可行） |
| **与现状差** | **零改动**（两侧现值即各自对该语义的最佳近似） | 需 GDI 侧新增能力（**不可行**） | 两侧都要改，且**行距归零** ⇒ 多行文本会**粘连**（视觉倒退） |
| **结论** | ★★ **选定 S1** | ✗ 实测不可行 | ✗ 违反观感常识 |

**★ 选定 S1 的实质含义（这是本稿最关键的一句话）**：

> **不把「数值统一」当作目标，而把「语义统一」当作目标**——
> 契约规定 `LineHeight` **返回「该字体在该字号下 ECDI 排版所用的行推进量」**；
> **GDI 用 `tmHeight` 实现它、FT 用 `metrics.height` 实现它**（两者都是各自平台对该语义的**最佳可用实现**）；
> 两者**允许在明确容差内不同**（§1.2 第 2 问），**该容差由专测锚定并写进契约**。

⇒ ★ **由此 (b) 从「让两侧输出同一个数」修正为「让两侧输出同一个语义」**——这既满足评审「口径稳定、第三个后端有明确规则」，又**不引入无法实现的公式**（§2.2/§2.3 已证否另一条路）。

### D31-B 一致性判据与容差（D1 第 ③ 步落点）

- **判据**：同一**字体文件、字重、字号、DPI**下，两侧 `LineHeight` 之差满足**相对字号**的容差式：

  ```
  容差(px) = ceil( fontSizePx × 0.15 ) + 1        // @96dpi（fontSizePx = 该字号下的 em 像素）
  ```

  ⇒ @14 → **4 px** · @20 → **5 px** · @32 → **6 px** · @48 → **9 px** · @64 → **11 px**

- ★ **依据（实测矩阵，pen 全表）**：实测最大差出现在 **SimSun**（`hhea.lineGap` 最大者）：

  | px | 12 | 14 | 16 | 20 | 24 | 32 | 48 | 64 |
  |---|---|---|---|---|---|---|---|---|
  | SimSun 实测差 | +2 | +2 | +2 | +3 | +3 | +4 | +7 | +9 |
  | 本式容差 | 4 | 4 | 4 | 5 | 5 | 6 | 9 | 11 |
  | 余量 | +2 | +2 | +2 | +2 | +2 | +2 | +2 | **+2** |

  ⇒ 该式在 **8 个字号上全部通过**，且**余量恒为 2 px**（可解释：`0.15 ≈ 36/256 + 安全系数`——SimSun 的 lineGap 分量是 `0.1406 em`）。

- ★ **不掩盖 / 诚实记录**：
  1. 需求稿曾写「容差 ≤1 px」——**实测证否**（SimSun @64 差已达 9 px）⇒ 本稿**改用相对式并给出全表**。
  2. 本容差**不是「精度达标」**，而是「**两个都算对、但依据不同**」的**可见差异上界**。★ 语义统一（D31-A）**不能消除**该差异——**它消除的是「不知道谁对」，而非「数值不同」**。
  3. 若评审认为该差异在观感上不可接受 ⇒ 唯一出路是**改实现**（把 FT 侧对齐到 `tmHeight` 的**字体映射语义**），而 §2.2/§2.3 已证其**不可实现** ⇒ 只能**接受并写进契约**（或**放弃 GL 后端与 GDI 的逐行一致**，那是另一个决策，超本 Phase 范围）。
- ★ **容差写进契约**（`TextMeasurer::LineHeight` 的 `@details`，§4.2）——**不是测试的私设**。

### D31-C 窗口几何 API 形态（D2，评审倾向的候选 A 优先评估）

**候选 A（本稿倾向）**：`SetBounds(const Rect&)` + `GetBounds() const`

```cpp
// 语义（公共 API 恒 DIP）
void SetBounds(const Rect& bounds);   // 屏幕坐标：左上角 + 总尺寸（含边框）——★ 请求语义，非保证
Rect GetBounds() const;               // 屏幕坐标（DIP）——如实反映系统当前值
```

| 维度 | 候选 A（合成） | 候选 B（分离 `SetSize`/`SetPosition`/`GetBounds`） |
|---|---|---|
| 与 `Create` 语义一致 | ✅ 都是「**总尺寸（含边框）**」+ 位置 | ⚠️ `SetSize` 需自带「是总尺寸还是客户区」的解释负担 |
| M1 三场景 | 折叠 = 保留 `x/y` 改 `height`；拆出 = 保留 `w/h` 改 `x/y`；级联 = 读→算→写**一次调用** | 每场景 2 次调用，且**两次之间窗口处于中间态**（可能触发出血的双次 `WM_SIZE`） |
| 原子性 | ✅ **一次调用一次 `SetWindowPos`** | ❌ 天然两次 |
| 学习成本（ECDI 定位） | ✅ 一个概念一个方法 | ⚠️ 三方法 |
| 缺点 | `Rect` 复用（下述） | — |

**① `Rect` 是否胜任屏幕坐标边界（§1.3 第 ① 问）——倾向复用 `Rect`**：

- `Rect` 已是公共类型（`Core/Rect.h`），字段 `x/y/width/height` **语义中立**（不隐含「客户区」或「屏幕」）⇒ 表达「屏幕坐标的窗口边界」**不产生歧义**，因为**方法的语义由方法名与文档确定**。
- 引入 `WindowBounds` 的成本：新公共头（**95 → 96**）、新类型的学习成本、与 `Rect` 的**隐式转换需求**——而它**带来的唯一好处**是「单位/坐标系在类型上可见」。
- ★ **反对引入的判据（ECDI 条 95②「不引入投机抽象」）**：**没有第二个消费者**需要区分「窗口边界」与「普通矩形」；M1 的用法就是读-算-写。⇒ **复用 `Rect`**，但**在契约注释里把坐标系与单位写死**（`@details` 明写「屏幕坐标、DIP、含边框总尺寸」）。
- ★ **若评审认为坐标系必须类型可见**，则退路 = 引入 `WindowBounds`（**+1 公共头**），本决策**留为可回退项**（§8 O2）。

**② DIP 语义与换算落点（§1.3 第 ②③ 问）**：

- 公共 API **恒 DIP**（Phase 20 Q1 契约，`Application.h:48-49`）。
- 换算**只在平台边界**：`Win32PlatformWindow::SetBounds/GetBounds` 内用 **`DpiConversion.h`** 的 `DipToPixels` / `PixelsToDip`。
- ★ **不的合并**：**不得**把几何换算与文本测量换算合并（`DpiConversion.h:21-22` 明写）——几何走 **int** 口径（`RoundHalfAwayFromZero`，C10 负数对称舍入），测量走 **float** 口径。
- **跨 DPI**：`SetBounds` 用**当前窗口 DPI**（`GetDpiForWindow`）；系统在 `WM_DPICHANGED` 时给的**建议矩形**（`Win32PlatformWindow.cpp:649-653` 现行为）**优先于**应用请求——⇒ `GetBounds` 随后反映的是**系统的值**（D31-D）。

### D31-D ★ 语义边界：`SetBounds` 是**请求**，不是**保证**（§1.3 第 ④⑤ 问）

契约必须区分**三个不同的量**（评审警示的核心）：

| 量 | 来源 | 特点 |
|---|---|---|
| **① API 输入** | 调用方给的 `Rect` | 可含负坐标 / 超屏 / 任意尺寸 |
| **② 系统实际采用的物理矩形** | `GetWindowRect` 读回 | ★ 系统可调整（超屏部分被移回、尺寸受最小跟踪尺寸约束、最大化态下 `SetWindowPos` 受 `WM_GETMINMAXINFO` 影响） |
| **③ DIP 读回** | `GetBounds` = ② 经 `PixelsToDip` | 与 ① **可能不等**（这是正常的，不是缺陷） |

⇒ **契约**：`SetBounds` **只承诺「已请求」**；`GetBounds` **承诺「如实反映系统当前值」**；**二者之间的差由系统决定，框架不补偿、不臆断**（★ 与 Phase 12 `D-COMP-1`「不引入补偿」同族）。
⇒ **测试**：必须断言**三者各自**（§7 T31-7），**不得**把「`Set` 后 `Get` 必须逐位相等」当判据——**那在系统会调整的情形下是错的**。

### D31-E `Ascent` / 基线处理边界（D3 强化——评审要求「不得被行高统一掩盖」）

- **两条路径分别定义**（不合并）：

| 概念 | 归谁 | 现状 |
|---|---|---|
| **`LineHeight`**——行框高度 / 逐行步进 / 光标高 | `TextMeasurer::LineHeight` | 本 Phase 统一语义（D31-A） |
| **基线定位**——字形在行框内的垂直位置 | GDI：`TextOutW` 的 `TA_LEFT \| TA_TOP`（`pos.y` = **单元顶边**）；GL：`pos.y + FontEngine::Ascent`（`GLRenderer.cpp:215`） | **两侧机制本就不同**，但**输出语义相同**（`pos.y` 都是单元顶边） |

- ★ **本 Phase 的处置（三选一，倾向 1）**：
  1. ★ **不加接口、不在契约里新增基线概念，但补一条「跨后端基线一致性」用例**（`T31-8`）——用**同一字体、同一位置**在两后端绘制，**断言字形栅格落点的垂直偏移一致**（容差 ≤1 px）。⇒ **零 API 增量**，直接回答评审「行高一致而基线偏移，依然可能出现视觉差异」的担忧。
  2. 把 `Ascent` 升格进 `TextMeasurer`（GDI 侧需用 `tmAscent` 实现）⇒ **API +1**，但**当前无消费者**（GL 经 `FontEngine` 内部拿，不经 `TextMeasurer`）。
  3. 显式记为**已知限制**（不做用例）。
- **倾向 1**：它**用一个用例回答了实质问题**，而 2 引入的抽象**没有真实消费者**（ECDI 条 95②/条 22 YAGNI）。
- ★ **明确不做**（评审原话）：**不借此机会把所有字体度量接口一次性泛化**。

### D31-F 平台三步惯例落点（不新建接缝）

沿 `PlatformWindow.h:22-28` 已定稿的 **R9 / D-SEAM-1** 三步：

| 步 | 落点 | 内容 |
|---|---|---|
| ① 接口加能力 virtual | `PlatformWindow.h` | `virtual void SetBounds(const Rect&) = 0;` · `virtual Rect GetBounds() const = 0;` ★ **纯虚 ⇒ 3 个实现者全改**（`Win32PlatformWindow` + 2 个测试替身） |
| ② `Window` 加公共方法透传 | `Window.h` / `.cpp` | `void SetBounds(const Rect&)` · `Rect GetBounds() const`（薄转发） |
| ③ 平台消息在实现内消化 | `Win32PlatformWindow.cpp` | `SetWindowPos` + `GetWindowRect`；`WM_DPICHANGED` 分支**保持现状**（系统建议矩形优先） |

★ **不新建接缝类、不新增消息注册机制**（需求稿已定，评审赞成保持）。

### 4.2 契约表述落点（D1 第 ② 步的实质交付物）

```cpp
// ── TextMeasurer.h:119-121 改写（★ 只改 @details，签名零变化）──

/// @brief 字体行高——★ 单位恒为 DIP
/// @details ★★ **语义（Phase 31 选定）**：本方法返回「**该字体在该字号下，
///          ECDI 逐行排版所用的行推进量**」——即相邻两行**基线**的距离，
///          也是「逐行 y 步进」与「光标高度」的唯一依据。
///          ★ **这是一个由 ECDI 定义的排版概念**，不宣称等于任何字体表字段；
///          两个后端各自以**平台最佳可用量**实现它：
///            · GDI  → `TEXTMETRICW.tmHeight`（`tmAscent + tmDescent`，含 internal leading）
///            · FT   → `face->size->metrics.height`（`ascender − descender + lineGap`）
///          ⇒ ★ **允许两后端在明确容差内不同**——容差 = `ceil(fontSizePx × 0.15) + 1` px
///             （@96dpi；覆盖实测 8 个字号的 SimSun 最大差，余量恒 2 px，
///              见 phase31 初设 §2.2 全表）——**容差是契约的一部分，不是测试的私设**。
/// @note 缺度量 / 度量为零 / 查询失败 ⇒ **统一回退 `font.size`**（两侧现状一致）。
/// @note ★ **基线不是本方法的职责**（`pos.y` = 字符单元顶边；GL 侧自行下移一个
///       `FontEngine::Ascent`——`GLRenderer.cpp:215`）——两者**有关联但不是同一个概念**，
///       详见 phase31 初设 D31-E。
virtual float LineHeight(const Font& font) = 0;
```

## §5 契约（C31-1..C31-7）

| # | 契约 |
|---|---|
| **C31-1** | `LineHeight` 语义 = **行推进量**（D31-A S1）；**由 ECDI 定义**，不取任一现有实现为「标准」 |
| **C31-2** | 两侧一致性 = **明确容差内**（`ceil(fontSizePx × 0.15) + 1` px @96dpi，按 DPI 线性缩放）——**不是逐位相等**；容差**写进契约**（实测全表见 §2.2） |

| **C31-7** | 基线**不新增契约**；以**跨后端用例**（T31-8）锚定一致性（D31-E 倾向 1） |
