### 2.2 K9 ★★ 受控实测：7 字体 × 2 字号（D1 第 ③ 步）

**装置**：探针 `.workbuddy/spike/p31-lineheight/probe_p31_lineheight.cpp`（独立程序，链生产 `libECDI.a`，只读度量、不改框架；读数留存同目录 `readout_px*.txt`）。
**方法**：GDI 侧 `CreateFontIndirectW` + `GetTextMetricsW`（复刻 `GDITextMeasurer::LineHeight` 路径，**用字体族名**）· FT 侧直接读 `hhea` / `OS/2` 表并按 `px/unitsPerEm` 缩放。

| 字体 | GDI `tmHeight` | FT `metrics.height` | 差 | FT 最佳候选 | 候选命中 |
|---|---|---|---|---|---|
| 宋体 SimSun | **14** | 16.0 | **+2** | C1/C3/C4 = 14.00 | ✅ |
| 微软雅黑 MSYH | **20** | 18.0 | **−2** | 无（最佳 18.48） | ❌ |
| Arial | **16** | 16.0 | **0** | C1/C2/C3/C6 = 16.00 | ✅ |
| Segoe UI | **19** | 19.0 | **0** | C1/C2/C3/C6 = 19.00 | ✅ |
| Consolas | **17** | 16.0 | **−1** | 无（最佳 16.39） | ❌ |
| Times New Roman | **16** | 16.0 | **0** | C1/C2/C3/C6 = 16.00 | ✅ |
| Courier New | **17** | 16.0 | **−1** | 无（最佳 15.86） | ❌ |

**同一矩阵在 px=20 的复跑**（★ 用于检验差值是否随字号缩放——**结论：会**）：

| 字体 | GDI | FT | 差 |
|---|---|---|---|
| 宋体 SimSun | **20** | 23.0 | **+3** ★ |
| 微软雅黑 MSYH | **27** | 26.0 | −1 |
| Arial | **23** | 23.0 | 0 |
| Segoe UI | **28** | 27.0 | −1 |
| Consolas | **23** | 23.0 | 0 |
| Times New Roman | **22** | 23.0 | +1 |
| Courier New | **22** | 23.0 | +1 |

★ **最大差随字号放大**（SimSun 系列）：**@14 → +2 · @20 → +3 · @32 → +4 · @48 → +7 · @64 → +9**。
根因可量化：SimSun 的 `hhea.lineGap = 36/256 em` ⇒ 该分量的像素值 = `px × 36/256`（@14 = 1.97、@64 = 9.0）——**与实测差同步**。
⇒ ★★ **容差必须写成「相对字号」的形式**，不能是固定像素数（见 D31-B）。

★★ **harness 读数的独立复现**：`ECDI_fake_harness` 的 `REQ-05` 实测为「**GDI 14 px / GL 16 px**」（8 段 CJK 探针）——本探针 @px=14 的 SimSun 行读数 **14 / 16.0**，**与 harness 逐位吻合**。⇒ ① harness 的读数被独立复现；② 该差异的根因确认为**两侧行高语义不同**（本节），**与 `\n` 消费、行距渲染均无关**。

**两条决定性结论**：

1. ★★ **差值有正有负、且不为常数**（+2 / −2 / 0 / 0 / −1 / 0 / −1 @px=14；+3 / −1 / 0 / −1 / 0 / +1 / +1 @px=20）⇒ **不存在「减一个固定量」的修法** ⇒ 需求稿备选 (a)「让 FT 对齐 GDI」**在数学上不成立**。
2. ★★ **没有任何单一 FT 候选式能普遍复现 GDI 的 `tmHeight`**——最佳命中 **5/8**（C1/C3 @px=14），且**跨字号不稳定**（@px=20 时 C1 降到 3/8、C3 降到 4/8）⇒ **方案 (a) 被实测证否**（不是「精度不够」，是「目标值本身不由字体表决定」——GDI 的 `tmHeight` 是**字体映射器**按 em square 与 internal leading 算出的结果，不能由 `hhea`/`OS/2` 的原始字段直接重建）。

### 2.3 ★ GDI 侧的能力边界（实测——决定方案 (b) 在 GDI 侧是否可实现）

| 手段 | 实测结果 | 结论 |
|---|---|---|
| `GetFontData(dc, 'head'/'hhea'/'OS/2', …)` | ★★ **恒返回 `GDI_ERROR`**（屏幕 DC 与内存 DC 均如此；字体确为 TrueType——`TMPF_TRUETYPE` 已置位） | **GDI 侧读不到原始字体表** |
| `GetOutlineTextMetricsW` | **可用**（SimSun 256 B / Arial 342 B…）——给 `otmAscent` / `otmDescent` / `otmEMSquare` / `otmMacAscent` / `otmMacDescent` / `otmMacLineGap` | 唯一可用的「设计度量」通道 |
| `GetTextMetricsW` | 可用——`tmAscent` / `tmDescent` / `tmInternalLeading` / `tmExternalLeading`，且实测 **`tmHeight == tmAscent + tmDescent` 恒成立**（`tmInternalLeading` **含在 `tmAscent` 内**） | 主通道 |

★ **这对设计是硬约束**：**方案 (b) 若把语义定义成「读 `hhea` 计算」，GDI 侧根本无法照做**（`GetFontData` 不可用、OTM 也不含 `hhea`/`OS/2` 的行距字段）。⇒ **语义必须落在「两侧都够得着」的量上**——这是 §3 D31-A 的选型约束。

| 事实 | 证据 |
|---|---|

## §3 决策（D31-A..D31-F）

### D31-A ★★★ 行高语义选型（D1 第 ① 步——**本稿第一决策**）

> ★★ **v1.1 重大修订（回应评审 P1 / P7）**：v1.0 把「**FT 无法用固定偏移复现 GDI 的 `tmHeight`**」（测量结果）直接推导成「**只能接受 ~15% 的差异并写入契约**」（产品决策）——★ **评审指出这两者之间存在设计空间，而 v1.0 没有去找它**。
> ★ 本版**找到了那个空间**：v1.0 问错了问题（「FT 能否复现 **GDI 的 `tmHeight`**」）。正确的问题是「**两侧能否各自取到同一个源度量**」——**答案是可以**（见 §2.6 的 H1 实测：**12/12 字体、误差 0.00 px**）。
> ⇒ **S1 的语义方向保留，但实现方式改为「两侧同取 hhea 口径」（B-2）**，容差随之从 **15% 经验上界**收敛为 **舍入级 ≤1 px**。

**三个候选语义**（★ 全部**由 ECDI 定义**，不取自任一现有实现）：

| | **S1 = 行框高度（行推进量）** | **S2 = 字体推荐行距** | **S3 = 内容盒高度** |
|---|---|---|---|
| **定义** | 逐行排布时**相邻两行基线的距离**，= 该字号下容纳「字形盒 + 行间呼吸」的最小行推进量；★ **由 ECDI 定义为「行推进量」这一排版概念** | 「字体设计者期望的行距」= `hhea` 的 `ascender − descender + lineGap` | 仅 `ascent + descent`（不含任何行距），= 字形紧贴的盒高 |
| **两侧可实现性** | ✅ **两侧同取 hhea 口径**（v1.1 实测，§2.6） | ✅ **同 S1 的实现路径**（★ v1.1 修正：v1.0 曾判其「GDI 不可实现」——**该判断被 §2.6 的 H1 实测推翻**：`GetFontData` 虽恒失败，但 **`GetOutlineTextMetricsW` 的 `otmMac*` 即 hhea 缩放值**） | ⚠️ GDI 需剔除 `tmInternalLeading`（可行）；⚠️ **行距归零** ⇒ 多行文本粘连（视觉倒退） |
| **与现状差** | ★ **GDI 侧改变行为**（改用 hhea 口径，`tmHeight → BOXG`）：常规字号 ±2 px、大字号最多 +9 px（§2.6 明细）；**FT 侧零改动** | 同左 | 两侧都要改，且观感倒退 |
| **结论** | ★★ **选定 S1，实现口径 = hhea（B-2）** | 与 S1 合并（同一路径） | ✗ 违反观感常识 |

**★ 选定 S1 + B-2 的实质含义**：

> 契约规定 `LineHeight` **返回「该字体在该字号下 ECDI 排版所用的行推进量」**，并**明确其计算口径**：
> **`ascender − descender + lineGap`（按该字号 px 缩放）**——★ **这是一个两侧都能独立算出的统一定义**（评审要的正是「由字体度量推导、各后端一致执行的规则」）。
> · **GDI** 经 **`GetOutlineTextMetricsW`** 的 `otmMacAscent − otmMacDescent + otmMacLineGap` 取（★ 实测即 hhea 缩放值）
> · **FT** 经 **`face->size->metrics.height`** 取（★ 实测其本就是该口径——`|F_BOXG − F_height| ≤ 0.5 px`）
> ⇒ **不是「两个都对但不同」，而是「两个都算同一个数」**。

⇒ ★ **由此 (b) 落成「统一定义 + 两侧各取同源度量」**——**这既满足评审「口径稳定」，又真正消除了跨后端差异**（而非仅仅「允许差异」）。

### D31-B 一致性判据与容差（D1 第 ③ 步落点）

> ★★ **v1.1 修订**：v1.0 的容差式（`ceil(px × 0.15) + 1`，@14 → 4 px、@64 → 11 px）**已被 B-2 取代**——审查 P1/P7 指出它「**把原本要修的缺陷变成了允许存在的差异**」，且「**从 7 字体推广到所有字体证据不足**」。B-2 下残差收敛到舍入级。

- **判据**：同一**字体文件、字重、字号、DPI**下，两侧 `LineHeight` 之差 **≤ 1 px**（@96 dpi，按 DPI 线性缩放）。
- ★ **依据（§2.6 实测，12 字体 × 8 字号）**：`|G_BOXG − F_BOXG|` 与 `|G_BOXG − F_height|` 全表**最大 ≤ 1.5 px**、常规字号（12–24 px）**≤ 1.0 px**，且残差**不随字号增长**（对照：v1.0 口径下的差随字号线性放大到 +9 px）。残差来源可解释且**有界**：GDI 侧 `otmMac*` 是**整数**（先量化再加），FT 侧保留 26.6 定点 ⇒ 差值 = **两侧舍入方向之差**，上界 = 分量个数（3）× 半个单位。
- ★ **不再需要「适用范围限定」**（P7 的诉求）：容差不再是「经验拟合的上界」，而是**由口径定义直接推出的舍入界** ⇒ 对任意字体成立（任何 TrueType/OpenType 字体都有 `hhea`；缺 `hhea` 时走 C31-3 回退）。
- **容差写进契约**（`TextMeasurer::LineHeight` 的 `@details`，§4.2）——**不是测试的私设**。

### D31-C 窗口几何 API 形态（D2，评审倾向的候选 A 优先评估）

**候选 A（本稿倾向）**：`SetBounds(const Rect&)` + `GetBounds() const`

```cpp
// 语义（公共 API 恒 DIP）
void SetBounds(const Rect& bounds);   // 屏幕坐标：左上角 + 总尺寸（含边框）——★ 请求语义，非保证
Rect GetBounds() const;               // 屏幕坐标（DIP）——如实反映系统当前值
```

| 维度 | 候选 A（合成） | 候选 B（分离 `SetSize`/`SetPosition`/`GetBounds`） |
|---|---|---|
| 与 `Create` 语义一致 | ✅ 都是「**总尺寸（含边框）**」+ 位置 | ⚠️ `SetSize` 需自带「是总尺寸还是客户区」的解释负担 |
| M1 三场景 | 折叠 = 保留 `x/y` 改 `height`；拆出 = 保留 `w/h` 改 `x/y`；级联 = 读→算→写**一次调用** | 每场景 2 次调用，且**两次之间窗口处于中间态**（可能触发出血的双次 `WM_SIZE`） |
| 原子性 | ✅ **一次调用一次 `SetWindowPos`** | ❌ 天然两次 |
| 学习成本（ECDI 定位） | ✅ 一个概念一个方法 | ⚠️ 三方法 |
| 缺点 | `Rect` 复用（下述） | — |

**① `Rect` 是否胜任屏幕坐标边界（§1.3 第 ① 问）——倾向复用 `Rect`**：

- `Rect` 已是公共类型（`Core/Rect.h`），字段 `x/y/width/height` **语义中立**（不隐含「客户区」或「屏幕」）⇒ 表达「屏幕坐标的窗口边界」**不产生歧义**，因为**方法的语义由方法名与文档确定**。
- 引入 `WindowBounds` 的成本：新公共头（**95 → 96**）、新类型的学习成本、与 `Rect` 的**隐式转换需求**——而它**带来的唯一好处**是「单位/坐标系在类型上可见」。
- ★ **反对引入的判据（ECDI 条 95②「不引入投机抽象」）**：**没有第二个消费者**需要区分「窗口边界」与「普通矩形」；M1 的用法就是读-算-写。⇒ **复用 `Rect`**，但**在契约注释里把坐标系与单位写死**（`@details` 明写「屏幕坐标、DIP、含边框总尺寸」）。
- ★ **若评审认为坐标系必须类型可见**，则退路 = 引入 `WindowBounds`（**+1 公共头**），本决策**留为可回退项**（§8 O2）。

**② DIP 语义与换算落点（§1.3 第 ②③ 问）**：

- 公共 API **恒 DIP**（Phase 20 Q1 契约，`Application.h:48-49`）。
- 换算**只在平台边界**：`Win32PlatformWindow::SetBounds/GetBounds` 内用 **`DpiConversion.h`** 的 `DipToPixels` / `PixelsToDip`。
- ★ **不的合并**：**不得**把几何换算与文本测量换算合并（`DpiConversion.h:21-22` 明写）——几何走 **int** 口径（`RoundHalfAwayFromZero`，C10 负数对称舍入），测量走 **float** 口径。
- **跨 DPI**：`SetBounds` 用**当前窗口 DPI**（`GetDpiForWindow`）；系统在 `WM_DPICHANGED` 时给的**建议矩形**（`Win32PlatformWindow.cpp:649-653` 现行为）**优先于**应用请求——⇒ `GetBounds` 随后反映的是**系统的值**（D31-D）。

### D31-D ★ 语义边界：`SetBounds` 是**请求**，不是**保证**（§1.3 第 ④⑤ 问）

契约必须区分**三个不同的量**（评审警示的核心）：

| 量 | 来源 | 特点 |
|---|---|---|
| **① API 输入** | 调用方给的 `Rect` | 可含负坐标 / 超屏 / 任意尺寸 |
| **② 系统实际采用的物理矩形** | `GetWindowRect` 读回 | ★ 系统可调整（超屏部分被移回、尺寸受最小跟踪尺寸约束、最大化态下 `SetWindowPos` 受 `WM_GETMINMAXINFO` 影响） |
| **③ DIP 读回** | `GetBounds` = ② 经 `PixelsToDip` | 与 ① **可能不等**（这是正常的，不是缺陷） |

⇒ **契约**：`SetBounds` **只承诺「已请求」**；`GetBounds` **承诺「如实反映系统当前值」**；**二者之间的差由系统决定，框架不补偿、不臆断**（★ 与 Phase 12 `D-COMP-1`「不引入补偿」同族）。
⇒ **测试**：必须断言**三者各自**（§7 T31-7），**不得**把「`Set` 后 `Get` 必须逐位相等」当判据——**那在系统会调整的情形下是错的**。

### D31-E `Ascent` / 基线处理边界（D3 强化——评审要求「不得被行高统一掩盖」）

- **两条路径分别定义**（不合并）：

| 概念 | 归谁 | 现状 |
|---|---|---|
| **`LineHeight`**——行框高度 / 逐行步进 / 光标高 | `TextMeasurer::LineHeight` | 本 Phase 统一语义（D31-A） |
| **基线定位**——字形在行框内的垂直位置 | GDI：`TextOutW` 的 `TA_LEFT \| TA_TOP`（`pos.y` = **单元顶边**）；GL：`pos.y + FontEngine::Ascent`（`GLRenderer.cpp:215`） | **两侧机制本就不同**，但**输出语义相同**（`pos.y` 都是单元顶边） |

- ★ **本 Phase 的处置（三选一，倾向 1）**：
  1. ★ **不加接口、不在契约里新增基线概念，但补一条「跨后端基线一致性」用例**（`T31-8`）——用**同一字体、同一位置**在两后端绘制，**断言字形栅格落点的垂直偏移一致**（容差 ≤1 px）。⇒ **零 API 增量**，直接回答评审「行高一致而基线偏移，依然可能出现视觉差异」的担忧。
  2. 把 `Ascent` 升格进 `TextMeasurer`（GDI 侧需用 `tmAscent` 实现）⇒ **API +1**，但**当前无消费者**（GL 经 `FontEngine` 内部拿，不经 `TextMeasurer`）。
  3. 显式记为**已知限制**（不做用例）。
- **倾向 1**：它**用一个用例回答了实质问题**，而 2 引入的抽象**没有真实消费者**（ECDI 条 95②/条 22 YAGNI）。
- ★ **明确不做**（评审原话）：**不借此机会把所有字体度量接口一次性泛化**。

### D31-F 平台三步惯例落点（不新建接缝）

沿 `PlatformWindow.h:22-28` 已定稿的 **R9 / D-SEAM-1** 三步：

| 步 | 落点 | 内容 |
|---|---|---|
| ① 接口加能力 virtual | `PlatformWindow.h` | `virtual void SetBounds(const Rect&) = 0;` · `virtual Rect GetBounds() const = 0;` ★ **纯虚 ⇒ 3 个实现者全改**（`Win32PlatformWindow` + 2 个测试替身） |
| ② `Window` 加公共方法透传 | `Window.h` / `.cpp` | `void SetBounds(const Rect&)` · `Rect GetBounds() const`（薄转发） |
| ③ 平台消息在实现内消化 | `Win32PlatformWindow.cpp` | `SetWindowPos` + `GetWindowRect`；`WM_DPICHANGED` 分支**保持现状**（系统建议矩形优先） |

★ **不新建接缝类、不新增消息注册机制**（需求稿已定，评审赞成保持）。

## §5 契约（C31-1..C31-7）

| # | 契约 |
|---|---|
| **C31-1** | `LineHeight` 语义 = **行框高度（行推进量）**（D31-A S1），★ **且口径明确定义为 `(ascender − descender + lineGap) × px / unitsPerEm`**——**由 ECDI 定义、两侧各自独立算出**（不取任一现有实现为「标准」） |
| **C31-2** | 两侧一致性 = **同一个数**，允许差异仅**舍入级 ≤1 px**（@96dpi，按 DPI 缩放，**不随字号增长**）——容差**写进契约**（实测全表见 §2.6） |
| **C31-3** | 回退：缺 face / 字体无 `hhea` 表 / `unitsPerEm == 0` / 查询失败 ⇒ `font.size`（**两侧一致**） |
| **C31-4** | ★ `SetBounds` = **请求**；`GetBounds` = **系统当前事实**；**二者可不等且不补偿** |
| **C31-5** | 公共 API **恒 DIP**；换算只经 `DpiConversion.h`；**几何（int）与测量（float）两条链路不得合并** |
| **C31-6** | `SetBounds`/`GetBounds` **运行期 API**（`Show()` 前 Warning + 忽略/空值——与 `Minimize` 同组） |
| **C31-7** | ★ **v1.1 修订（评审 P2）**：**光标高度 = 行框高度**（`TextBox::GetLineHeight()` 即返回 `LineHeight()`——**不是**「行框内另有偏移」）；★ **基线**不新增公共契约，以**跨后端用例**（T31-8）锚定。★ **三概念分离**（评审 P2 要求）：**① 行推进量**（本方法）· **② 字形垂直定位**（基线——后端内部实现，`pos.y` 恒为**字符单元顶边**）· **③ 光标高度**（= ①）。**`LineHeight` 是 ECDI 的排版行框参数，不是「后端所有字体度量的统一替代品」** |

## §7 测试方向（T31-1..T31-8）

| # | 场景 | 断言核心 |
|---|---|---|
| **T31-1** | 两链行高一致性（**受控**：同一字体文件、字重、字号、DPI） | 差 **≤1 px**（C31-2）；★ **必须锚同一文件**（§1.2 第 4 问）——装置见 T31-6；★ **覆盖 12–64 px 字号区间**（残差不随字号增长——这是 B-2 的核心判据） |

| **T31-5** | ★ 几何**退化输入四类**（评审补强） | **负坐标** · **跨 DPI**（DPI 变化后读回） · **尺寸大于屏幕** · **系统实际调整**——★ 分别断言「**API 输入 / 系统物理矩形 / DIP 读回**」三者（C31-4）；★ **测试须区分「转换误差」与「Windows 主动调整」**（评审 P6：不得把系统行为误报为框架转换错误） |

| **T31-7** | 几何 API 生命周期（C31-6） | `Show()` 前调用 ⇒ Warning + 无副作用/空值；`Show()` 后正常。★ **v1.1 补（评审 P6）**：`GetBounds` 在**未显示时的空值语义**须与同组运行期 API 一致（返回空 `Rect` + Warning） |
| **T31-8** | ★ **跨后端基线一致性**（D31-E 倾向 1） | ★★ **v1.1 补（评审 P3）：必须可复现、可测量**——① **固定字体文件、固定字号、固定 DPI**（与 T31-6 同源前提）；② **固定字形样本**：**单一字形**（如 `H`——避免下伸部/中文字形边界差异），必要时补 `g`（下伸）与 `测`（CJK）作**对照组**；③ **明确测量指标** = 「**非背景像素的最小 Y 与最大 Y**」（字形包围盒的纵向两端），**不是**基线（基线不可直接从像素读出）；④ **避免把光栅化差异误判为定位错误**：两后端 hinting/AA 不同 ⇒ **容差须显式放宽到 ±1 px**，且**只比较「同一 pos 下的落点偏移」而非绝对像素相等**；⑤ 断言 = GDI 与 GL 的包围盒顶端/底端偏移**各自在 ±1 px 内** |
