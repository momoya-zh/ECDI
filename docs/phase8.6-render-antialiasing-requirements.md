## 1. 动机与现状勘察

### 1.1 动机

`DrawRoundedRect` 是 Phase 8 交付的能力，当前被 **6 个控件 + 焦点框**消费（§1.2 实证）。GDI 的 `RoundRect` 与现有 DIB 逐像素路径**都不做几何抗锯齿**，圆角/圆弧呈现阶梯状边缘。这在高对比度主题（深色背景 + 亮色描边）和真圆场景（Radio）下尤其明显。

「抗锯齿升级」早已被识别并**登记为延期项**，但只写在 Phase 9.5 详设的「明确不做（YAGNI）」清单里，**未进入 `roadmap-deferred.md` 总表**（§1.2 末行）。本次职责确认同时补齐该登记（§7）。

### 1.2 代码事实（2026-09-11 读源码实证）

| 事实 | 证据 |
|---|---|
| `DrawRoundedRect` 有**两条独立路径** | `a == 1` → GDI `RoundRect()`（一次调用）；`a < 1` → `BlendAlphaSolid()`（临时 32bpp 预乘 DIB + **逐像素二值判定** `(dx²+dy²) <= r²` + AlphaBlend） |
| 两条路径都是**硬边** | `a==1`：GDI RoundRect 无 AA；`a<1`：判定结果是 bool，像素非全色即全透明 |
| 「不引入抗锯齿」是**写死的约束** | 代码：`GDIBackend.cpp:19` / `:102` / `:389` 三处注释「约束 2」；文档：`phase9.5-alpha-primitive-detailed-design.md` §3「约束 2（圆角无抗锯齿）」——**来源为 9.5 外部评审写死** |
| 抗锯齿**已登记为延期项但总表缺失** | 9.5 详设 §4「明确不做」列出「抗锯齿升级」；`roadmap-deferred.md` **零命中**（grep 实证） |
| 真实消费方（6 控件 + 焦点框） | `Button.cpp:236` / `CheckBox.cpp:80,89` / `Panel.cpp:58,69,80` / `ProgressBar.cpp:106,116` / `Radio.cpp:103,104,111` / `TextBox.cpp:1068,1080,1088`；焦点框 `Button.cpp:253` / `TextBox.cpp:1098`（`DrawFocusRect` 亦带圆角） |
| **两个消费方无条件走圆角** | `Radio` 半径 = `size/2`（真圆）；`ProgressBar` 半径 = `configured > 0 ? configured : height/2`（胶囊）——**即使主题 `cornerRadius = 0` 也存在可见锯齿** |
| 其余消费方取决于主题 | `DefaultTheme` 的 `cornerRadius` 默认为 `0.0f`（Button/Panel/TextBox 仅在 >0 时画圆角）；CheckBox 随主题 |
| **GDI 后端是 Internal** | `GDIBackend.h` 位于 `ECDI/src/Render/`（非 Public 头）——本阶段**无公共 API 变更** |

### 1.3 作用域划分的数学依据（本阶段最重要的勘察结论）

`DrawRoundedRect` 内部对矩形与半径做了 `std::lround`（`BlendAlphaSolid` 用 `std::lround(rect.x)`，主路径 `static_cast<LONG>`）——**几何全部落在整数像素边界上**。

推论：**轴对齐直边上的任一像素，覆盖度只可能是 0 或 1**，抗锯齿算出来是恒等变换（no-op）。所以「只对圆弧/圆角做 AA」不是折中取舍，而是当前坐标取整行为的**数学推论**。

⚠️ **唯一前提**：`phase8-rendering-enhancement-requirements.md` R4「渲染坐标浮点化」（P2）**未完成**。一旦直边也开始跨像素，本阶段的作用域划分即失效、直边同样需要 AA。因此本阶段的设计**不得在结构上排除**该扩展（D10）。

## 3. 关键决策点（含倾向）

### D1 【正式修订】Phase 9.5「约束 2」——圆角无抗锯齿

**原文**（`phase9.5-alpha-primitive-detailed-design.md` §3）：

> **约束 2（圆角无抗锯齿）**：`DrawRoundedRect` 半透明分支只做颜色 alpha 合成，**不引入几何抗锯齿**（圆角边缘与现有 GDI RoundRect 同款非 AA 语义）。防膨胀成 alpha compositor。

**修订为**：

> **约束 2（修订版，2026-09-11）**：`DrawRoundedRect` 的**颜色 alpha 合成**与**几何抗锯齿**是两个正交关注点。9.5 版本把前者作为「不做后者」的理由——该捆绑关系解除：
> - **颜色 alpha 合成**：仍属 9.5 已交付能力，语义与实现不变（约束 1 预乘规则继续有效，且**被本阶段复用**）。
> - **几何抗锯齿**：自本阶段起由**独立能力**提供，作用于圆角/圆弧的覆盖度；`a == 1` 与 `a < 1` 两条路径**语义一致**（同一几何、同一覆盖度）。
> - **9.5 原约束的立法意图继续有效**：「防膨胀成 alpha compositor」的边界不变——本阶段**仍然不做** Global/Widget Opacity、PushOpacity、Alpha batching、GPU compositor（§4）。约束 2 修订的是**抗锯齿与 alpha 的捆绑**，不是放开 alpha 的范围。

**为什么必须显式修订而不是默默实现**：9.5 详设的约束 2 是**外部评审写死的**，代码里三处注释直接引用它。若实现 AA 而不修订文档，代码注释与设计文档将互相矛盾，后续任何人读 `GDIBackend.cpp:102`「不引入抗锯齿」都会得到错误结论。按项目「设计链一致性」要求，约束变更必须回写。

### D2 作用域：只做圆角 vs 全几何？

- 候选：① 只圆角/圆弧 ② 圆角 + 斜线（`DrawLine` AA）③ 全几何（含直边）
- **倾向 ①**。理由：直边因整数像素边界无需 AA（§1.3 数学依据）；斜线是**另一个独立议题**——`DrawLine` 目前连 alpha 路径都没有（同属 9.5 不做项），线宽/端帽/合成顺序都要另行设计，混进来会让本阶段失焦。
- **接口不阻碍扩展**：因 D3 已把「覆盖度生成」与「形状装配」拆成两层，斜线未来只需**新增第二层装配**、复用同一覆盖度机制即可，不必改动第一层。

### D3 覆盖度生成方式：超采样 vs 解析覆盖度？（v1.1 修订）

- 候选：① 超采样（N× 光栅化后降采样得覆盖度）② 解析覆盖度（精确计算像素落在圆内的面积占比）③ 距离场近似（SDF + smoothstep）
- **倾向 ①（**MVP 优先实现超采样**）**，且只用于「生成覆盖度」这一步、只生成一次（按半径缓存，见 D4）——常规反对超采样的「每帧 16× 计算」在缓存后不成立。
- ⚠️ **v1.1 措辞修订（评审 §6/§17）：不把 4× 锁死。** v1.0 写「倾向 ① 超采样」读起来像定案；本阶段的立场是「**优先级**」而非「定案」：
  - **MVP 优先实现超采样**（简单、覆盖度生成机制可复用、面积正确）
  - **但覆盖度生成器必须保持实现可替换**——若日后发现 4× 视觉仍有轻微阶梯（升 8×）、或解析法更快（换解析），**只替换生成器**，`GDIBackend` / `RenderCommand` / `Widget` 零改动
  - 这与 ECDI 既有理念一致：**能力接口稳定，实现策略可替换**
- 选 ① 而非 ② 的理由：**覆盖度生成机制与形状装配解耦、可复用**（措辞的精确含义见下方「两层概念拆分」）。解析法要对每个形状类型单独推导面积公式（圆角象限是圆—矩形交集、斜线是线段—方形交集），超采样对任何形状都是同一套代码。
- 选 ① 而非 ③ 的理由：SDF 的过渡带宽度是人为选定的美学参数，而覆盖度是需要**面积正确**的量（R5 面积守恒直接检验）——SDF 不保证面积守恒。
- 超采样倍率：倾向 4×（可调，**属实现参数，不写进契约**）。**4× vs 8× vs 解析的对比归初设。**

#### 两层概念拆分（v1.1 新增——评审 §4，修正 v1.0 的概念混淆）

v1.0 的 D3 写「形状无关」、D4 写「r×r 四分之一圆角掩码」——这两句话放在一起是**矛盾的**：象限掩码明明依赖于「圆角象限」这个形状。矛盾根源是把**两层不同的东西混成了一层**。v1.1 明确拆开：

```text
第一层 · 覆盖度生成（机制可复用）
    GenerateCornerMask(radius) → CornerCoverageMask
    只回答一个问题：「半径 r 的单象限，每个像素被覆盖多少」

第二层 · 形状装配（与形状有关，各自组装）
    RoundedRect = 3 条实心带 + 4 个象限掩码（或：扫描线端点覆盖）
    Circle      = 4 个象限掩码拼合
    Capsule     = 左右各 2 个象限掩码 + 中间带
```

- **「形状无关」的准确含义**：指**第一层（覆盖度生成机制）可复用**，**不是**「整个 AA 算法与形状无关」。
- **为什么真的可复用**：圆角矩形的角、真圆的象限、胶囊的端部——三者的边界几何**都是同一个四分之一圆盘**。所以同一份 `CornerCoverageMask` 能服务全部三种形状；差异只在**第二层怎么摆**。
- **四方向复用**：四个角是同一掩码的镜像/转置（掩码只需生成一份）。
- 拆分后的直接好处：R5 面积守恒的测试对象自然落在**第一层**（测试对象明确化，见 D9），而「第二层装配对不对」由 L2 集成测试覆盖——两层各测各的，诊断清晰。

### D4 缓存策略：缓存什么、键是什么？（v1.1 修订——评审 §7/§17）

- 候选：① 缓存**单象限覆盖度掩码**，键 = 半径 ② 缓存**整张已完成圆角矩形位图**，键 = (尺寸, 半径, 颜色)
- **倾向 ①**，并显式写清三个要素（v1.0 只有「键」一句，太含糊）：

| 要素 | 取值 | 说明 |
|---|---|---|
| **缓存对象** | `CornerCoverageMask`——**单象限**覆盖度掩码（r×r，每像素 0~255） | 四角通过镜像/转置复用同一份（D3） |
| **缓存键** | **离散化后的 radius** | `DrawRoundedRect` 现有实现本就 `lround` 半径 → 天然已是整数，离散化几乎零成本 |
| **失效条件** | **永不主动失效**（与颜色/尺寸/位置/主题无关）；仅后端析构时清理 | 这正是它优于「整图缓存」的地方 |

- 理由：
  - **命中率**：半径取值是**离散小集合**（主题里几个常量 + `ProgressBar` 的 `height/2` + `Radio` 的 `size/2`），而尺寸组合多得多——键越小命中率越高。
  - **颜色正交**：颜色随主题/悬停/按下变化，若进键会让缓存条目爆炸或频繁失效；掩码与颜色无关，正好把变化的部分留在热路径上。
  - **内存可忽略**：半径 8 的掩码是 8×8 = 64 字节；半径 32 = 1KB。
- ⚠️ **「形状无关」的正确读法**（评审 §4）：指**覆盖度生成机制可复用**（同一 `CornerCoverageMask` 被圆角矩形/圆/胶囊共同消费），**不是**所有形状的装配过程相同。两层拆分见 D3。
- ② 作为可选优化（对某个高频固定尺寸的控件）**不在本阶段做**。

### D5 两种「复用」的职责拆清（v1.1 修订——评审 §10/§17）

v1.0 把「掩码缓存」与「scratch DIB」写在同一个决策点里，容易被读成同一个东西。v1.1 拆成两个**独立**关注点——它们解决的问题、键、生命周期全都不同：

| | `CornerMaskCache`（几何数据缓存） | `ScratchDIB`（绘制工作缓冲） |
|---|---|---|
| **解决什么** | 重复计算**几何覆盖度** | 重复创建**临时绘制目标** |
| **键 / 复用方式** | radius（离散化） | 无键——单个实例反复复用，按需扩容 |
| **生命周期** | 后端存活期（跨帧） | 后端存活期（跨调用复用） |
| **内容** | 覆盖度值（纯几何，与颜色无关） | 像素（每次调用覆写） |
| **归属** | `GDIBackend` 私有 | `GDIBackend` 私有 |

- **倾向**：两个都要有，但**必须分开实现、分开命名**——禁止合并成一个笼统的「缓存」（否则后人会把 `ScratchDIB` 误解成 DIB cache）。
- **明确不等于「DIB 缓存池」**：9.5 的「不做 DIB 缓存池」约束继续有效——`ScratchDIB` 是**单个复用缓冲**（按需扩容），不是分配器、不做多尺寸池。
- 现状背景：`BlendAlphaSolid` 注释写着「每次调用创建/销毁 DIB（低频场景可接受，YAGNI 不做缓存池）」——该假设在 AA 让**所有**圆角矩形都进入此路径后**不再成立**（20 个复选框 ≈ 每帧 60 次 DIB 建销）。这是本决策的存在理由。

### D6 开关粒度：后端级 vs 命令流参数？

- 候选：① 后端级（`GDIBackend` 上的开关，默认开）② `DrawRoundedRectCommand` 增加质量参数 ③ 全局配置
- **倾向 ①**，并**明确禁止 ②**。
- 理由：把绘制质量塞进 `RenderCommand` = **把表现层策略泄漏进 Widget 契约**——与 R9 否决「Win32 消息号进公共 API」是同一类分层错误。`DrawRoundedRect(rect, radius, color)` 的签名与命令字段**必须零改动**。
- ① 的存在理由仅是测试需要「开/关」对照（R4/R5 断言——见 D9 的 L2 层）。**不进 Public 头**（`GDIBackend.h` 是 Internal 头）。

### D7 覆盖度与颜色 alpha 的合成顺序？

- **倾向**：`最终 alpha = color.a × coverage`，RGB 按约束 1 的预乘规则随之缩放（`B = b × color.a × coverage`，A 同理）。即**覆盖度是一次额外的 alpha 调制**，不引入新的合成通道。
- 依据：约束 1（预乘规则）继续有效——AA 只改变每个像素的 alpha 值，不改变预乘语义。
- 与 D11 的关系：该合成公式对 `a == 1` 与 `a < 1` **是同一条**（`color.a == 1` 时退化为 `alpha = coverage`）——这从公式层面支持了「统一路径」的可行性；性能代价与取舍见 D11。

### D8 形状装配：四角 patch vs 扫描线？（v1.1 升为初设重点比较项——评审 §5/§17）

- 问题：「3 条轴对齐实心带 + 4 个角补丁」的装配在 `2r >= min(w, h)` 时退化（`Radio` 真圆、`ProgressBar` 胶囊的高 = 2r）。
- **`Radio` 是本阶段最容易出问题的验证对象**：半径恒为 `size/2`，必然落进退化区间。
- 候选（两者**都消费同一个 `CornerCoverageMask`**，差异只在第二层装配——D3）：

| 候选 | 做法 | 退化情形 |
|---|---|---|
| **A. 四角掩码 + 中间矩形** | 3 条实心带 + 4 个象限掩码 | 需专门分支处理 `h - 2r <= 0` |
| **B. 扫描线 + 象限掩码** | 逐行确定被覆盖的 x 区间与端点覆盖度 | `h = 2r` 天然成立，**无需退化分支** |

- **倾向 B**（与 v1.0 一致，但**升级为初设重点比较项**）。评审（§5）亦倾向 B，理由：扫描线模型对普通矩形 / 圆角矩形 / 胶囊 / 真圆**天然统一**，不必维护 `if (degenerate)` 特殊路径。
- **代价**：扫描线模型设计稍复杂（需定义「端点部分覆盖」的宽度与取值），且与 GDI 矩形填充原语的交互方式需要设计。
- **归初步设计正式比较 A/B 并定案**——这是初设的两个核心技术锚点之一（另一个见 D11）。

### D9 测试手段：两层（v1.1 重写——评审 §7/§8/§9/§14）

v1.0 把「面积守恒」与「真窗口像素读回」写在一起，有两个隐患：① 面积守恒的**测试对象**未写明，极易误测成整个圆角矩形；② 全部依赖 `HWND`/`HDC`/`GetPixel`，导致「算法错了」与「算法对但合成错了」无法区分。v1.1 拆成两层：

#### L1 · `CornerCoverageMask` 数学测试（核心算法层，**零窗口依赖**）

- **测试对象 = 第一层覆盖度生成器的输出**（`GenerateCornerMask(r)`），**不是** `DrawRoundedRect` 的渲染结果。
  - ⚠️ 必须写明（评审 §8）：一个 `100 × 50`、`radius = 8` 的圆角矩形，**总面积显然不是** πr²/4——拿整个圆角矩形做面积守恒是**测错的**。
- 断言：

| # | 断言 | 形式 |
|---|---|---|
| L1-a | **面积守恒** | `abs(Σcoverage − πr²/4) <= tol(倍率, r)`——**容差不等式，不是相等**；容差必须与超采样倍率挂钩（4× 与 8× 允许的误差不同——评审 §7） |
| L1-b | 覆盖度值域 | 所有像素 `0 <= c <= 255` |
| L1-c | 存在部分覆盖 | 边缘存在 `0 < c < 255` 的像素（硬边掩码只有 0/255，此条必失败） |
| L1-d | 单调性 | 沿外法向（远离圆心）覆盖度单调不增 |
| L1-e | 四方向对称 | 镜像/转置后掩码一致（验证「一份掩码四角复用」的正确性——D3） |

- **多半径覆盖**：`r = 1, 2, 3, 4, 8, 16`（含小半径——`r = 1` / `r = 2` 是掩码退化与边界效应的高危区）。
- **无需 `HWND` / `HDC` / `GetPixel` / `AlphaBlend`**——纯计算测试，可在既有**无窗口测试框架**内直接跑。这比 v1.0 的全窗口方案更适合做**算法正确性**测试。

#### L2 · `GDIBackend` 集成测试（后端合成层，真窗口像素）

- 复用 `RendererTests.cpp::TestGDIBackendAlphaBlend` 的「真窗口 + `GetPixel` 像素读回」模式（**注意**：该模式要求窗口在屏幕内——屏幕外窗口 DC 裁剪区为空、`GetPixel` 恒返 `CLR_INVALID`，该坑已在原测试注释中记录）。
- 断言：
  - **AA 开 ≠ AA 关**（同一几何、同一颜色，像素输出存在差异）
  - **存在 `0 < alpha < 255` 的过渡像素**（证明 AA 确实生效，而非只改了别的）
- **`r == 0` 零回归的测法（评审 §14）**：**不引入 Golden Image / 基准截图**——直接用 D6 的开关做对照：

  ```text
  (AA 关, r = 0)  ==  (AA 开, r = 0)     逐像素一致
  ```

  这同时验证「AA 关闭时旧路径行为完全不变」，比基准图更强、且无外部依赖。**不需要为这个测试引入任何截图基线机制。**

#### 为什么分两层（诊断价值）

```text
L1 失败 → 算法 / 数学错了
L2 失败 → 算法对，但 GDI 合成 / 预乘 / AlphaBlend 环节错了
```

把「算法坏了」与「算法正确但合成错了」分开定位——比全部塞进 `RendererTests` 的诊断效率高得多。

- **归初步设计给完整用例表。**

### D10 与 Phase 8 R4「渲染坐标浮点化」的边界？

- R4 是 P2 未完成项，本阶段**不做**浮点化。
- 但本阶段的设计**不得在结构上排除**它：一旦直边跨像素，同一套覆盖度机制应能覆盖。这是 §1.3「作用域划分的前提」的直接后果——**倾向**让第一层覆盖度生成器与第二层形状装配解耦（D3 两层拆分已满足）。

### D11【初设核心决策点】`a == 1` 是否统一进入覆盖度路径？（v1.1 新增——评审 §11/§12）

**问题**：现状 `a == 1` 走 GDI `RoundRect()`（一次调用、无 AA），`a < 1` 走 DIB 路径。若 AA 只加在 `a < 1` 分支上，会得到：

```text
不透明 Button（a == 1）  → 有锯齿
半透明 Button（a < 1）   → 无锯齿
```

**同一个 `DrawRoundedRect`，按 alpha 得到两种视觉质量**——这与本阶段的核心契约（「圆角几何获得覆盖度抗锯齿」）直接冲突。v1.0 只在 D7 末尾把它记为「开放项」，v1.1 提升为**初设核心决策点**。

**候选**：

| 候选 | 做法 | 后果 |
|---|---|---|
| ① 统一 | 所有 `DrawRoundedRect` 走「统一圆角几何 → coverage → alpha × coverage → 合成」 | 语义一致；**可能失去 `RoundRect()` 单次调用快路径** |
| ② 分离 | `a == 1` 保留 `RoundRect` 无 AA；`a < 1` 走 AA | 快；但两种视觉语义——**不接受** |
| ③ 先统一、再找等价比路径 | 语义先行；随后在**数学等价**的前提下识别可安全走旧快路径的情形（如 coverage 全为 0/1 时） | 推荐 |

- **倾向 ③**，并确立**优化顺序原则**（评审 §12）：

  ```text
  先统一视觉语义   →   再寻找数学上等价的快路径
  ```

  **而不是**「先保留快路径、接受两种视觉结果」。理由：视觉语义一致性是本阶段的**核心契约**，不能被性能优化动摇；性能是语义确定后可独立优化的次要目标。
- **性能代价必须实测**（归初设）：对比「旧 GDI `RoundRect`」与「新 AA DIB 路径」在典型 UI 帧下的耗时。建议基线场景（评审 §11）：

  ```text
  20 × Button + 20 × CheckBox + 1 × Radio + 1 × ProgressBar
  ```

- **连带影响**：R3（两条路径语义统一）因此由 P1 升为 **P0**——它不是「消除重复代码」的整洁性问题，而是本阶段契约能否成立的前提。
- **初设须给出结论**：这一条与 D8（A/B 装配路线）并列为本阶段两个核心技术锚点——前者保**视觉语义一致性**，后者保**实现简洁性**；R5 面积守恒则保**数学正确性**。

## 4. 范围外（YAGNI）

- **`DrawLine` 的几何抗锯齿**（斜线）——独立议题：`DrawLine` 无 alpha 路径、线宽/端帽/合成顺序需另行设计
- **`DrawText` 抗锯齿**——GDI 文本由系统字体光栅化处理，不在本阶段
- **Phase 8 R4 渲染坐标浮点化**——P2 未完成项，本阶段不做
- **直边的抗锯齿**——当前整数像素边界下为 no-op（§1.3）
- **全屏超采样 / 多重采样（MSAA）缓冲**——只做覆盖度掩码，不做帧级超采样
- **DIB 缓存池 / Alpha batching / PushOpacity / Global Opacity / GPU compositor**——9.5 边界继续有效（D1 修订后依然不做）
- **其他后端（D2D/Skia）的抗锯齿**——它们自带 AA，本能力是 GDI 专属补强
- **Golden-image（逐像素基准图）测试体系**——AA 结果含后端实现差异，不适合做基准图比对
- **主题层的 AA 配置项**——不做（D6：后端级开关即可，不进主题）
